## §1 Unity Catalog

### Q: What is Unity Catalog?
It is the account-level governance layer for Azure Databricks. It provides one metastore per region that is shared by all attached workspaces, and covers:
- ANSI-SQL privileges on a 3-level namespace (`catalog.schema.object`)
- Governed storage access through storage credentials and external locations
- Fine-grained access through row filters, column masks, dynamic views, and ABAC
- Automatic lineage, audit and billing system tables, Delta Sharing, and data discovery (tags, search, `BROWSE`)

### Q: How is it used?
Attach a workspace to a regional metastore, create catalogs and schemas, grant privileges to **account groups**, and query with 3-part names on UC-capable compute (SQL warehouse, standard access mode, or dedicated access mode):
```sql
GRANT USE CATALOG ON CATALOG sales TO `analysts`;
SELECT * FROM sales.gold.orders;
```

### Q: Advantages?
- Define access once and enforce it in every workspace.
- Identity is centralized (Entra ID → account).
- Lineage and audit come for free, without instrumentation.
- No more mount points or credentials embedded in clusters.
- Managed tables get predictive optimization and automatic cleanup.

### Q: Disadvantages / limitations?
- Only one metastore per region, so metadata is not physically isolated by environment (isolation is logical: catalogs plus bindings).
- Needs UC-compatible compute and access modes. Older runtimes on dedicated mode can't read FGAC objects.
- Workspace-local groups can't be used.
- Enabling UC on a workspace can't be reversed.

### Q: Current adoption / what replaced what?
UC replaces the per-workspace **Hive metastore** and **table ACLs** ("legacy table access control"), and also **DBFS mounts** (replaced by volumes and external locations) and credential passthrough. New workspaces are UC-enabled automatically and get a **workspace catalog**. HMS remains available as the `hive_metastore` catalog for migration.

### Q: How does UC compare to the Hive metastore?
| | Hive metastore | Unity Catalog |
|---|---|---|
| Scope | One workspace | Account and region (many workspaces) |
| Namespace | 2-level (`db.table`) | 3-level (`catalog.schema.table`) |
| Access control | Table ACLs, per workspace | ANSI GRANTs, inheritance, FGAC |
| Storage access | Mounts, cluster credentials | Storage credentials + external locations |
| Lineage / audit | None built in | Automatic, plus system tables |
| `DROP` managed | Data deleted immediately | `UNDROP` window (default 7 days) |

### Q: Exam trap: "Users can query HMS tables in workspace A but not workspace B." What's the UC answer?
Register the data in UC and grant to an **account group**. UC grants apply in every workspace attached to the metastore, unless a workspace-catalog binding restricts them.

## §2 Metastore & object hierarchy

### Q: What is the metastore and what does the hierarchy look like?
The metastore is the top-level UC container, **one per region per account**.
```
Metastore
├── Catalog ─► Schema ─► Table | View | Materialized view | Volume | Function | Registered model
├── Storage credential · External location · Connection · Service credential   (metastore-level)
└── Share · Recipient · Provider                                              (Delta Sharing)
```

### Q: How is it used?
An account admin creates the metastore (optionally with metastore-level managed storage) and assigns workspaces. Each catalog you create gets the `default` and `information_schema` schemas automatically.

### Q: What is the unit of data isolation?
The **catalog**, per Microsoft's recommendation. The metastore only isolates regions. Separate dev, test, and prod with **catalogs** plus **workspace-catalog bindings**.

### Q: Advantages / limitations of a single regional metastore?
- Advantage: one shared namespace and policy plane for every workspace in the region.
- Limitation: you can't create a second metastore in the same region. Physical metadata isolation requires a different region or a different Databricks account.

### Q: How do registered models fit the hierarchy?
Models live in a schema. For grants they are **functions**:
```sql
GRANT EXECUTE ON FUNCTION prod.ml.iris_model TO `ml-team`;
```

### Q: Exam trap: "Create a separate metastore for dev in East US to isolate it from prod." Valid?
No. There is one metastore per region. Use a `dev` catalog bound to the dev workspace.

### Q: Exam trap: Where do storage credentials and external locations live?
At the **metastore** level, not inside a catalog or schema. Their names are unqualified and must be unique within the metastore.

## §3 Privileges & inheritance

### Q: What is privilege inheritance?
A privilege granted on a container applies to all **current and future** children:
- catalog → its schemas → their tables, views, volumes, and functions
- schema → its tables, views, volumes, and functions

Denials also inherit. **Metastore-level grants do not inherit.** `READ METADATA` on the metastore is the exception.

### Q: What exactly is needed to query a table?
All three:
- `USE CATALOG` on the catalog
- `USE SCHEMA` on the schema
- `SELECT` on the table, or inherited from the schema or catalog

The usage privileges give **no** data access by themselves.

### Q: How is it used? (minimal read-only analyst grant)
```sql
GRANT USE CATALOG ON CATALOG sales TO `analysts`;
GRANT USE SCHEMA, SELECT ON SCHEMA sales.gold TO `analysts`;  -- all current + future tables/views
```

### Q: Privilege cheat-sheet?
| Operation | Needs |
|---|---|
| Read table or view | `USE CATALOG` + `USE SCHEMA` + `SELECT` |
| Write table | usage + `MODIFY` (+ `SELECT` for anything that reads, e.g., MERGE) |
| Create table | usage + `CREATE TABLE` on schema |
| Create schema | `USE CATALOG` + `CREATE SCHEMA` on catalog |
| Create catalog | `CREATE CATALOG` on **metastore** |
| Run a UDF | usage + `EXECUTE` |
| Read or write volume | usage + `READ VOLUME` / `WRITE VOLUME` |
| Tag | usage + `APPLY TAG` (+ `ASSIGN` on a governed tag) |
| Refresh MV | `REFRESH` |

### Q: What is `BROWSE`?
It lets a user discover objects and view their metadata (name, comment, tags, lineage, `information_schema`) and **request access**, with **no** data access and **without** `USE CATALOG`/`USE SCHEMA`. It is grantable **on catalogs only** (for data objects). Recommended:
```sql
GRANT BROWSE ON CATALOG sales TO `account users`;
```

### Q: What is `ALL PRIVILEGES`?
It implies all applicable privileges and is **evaluated at check time**, so new privileges Databricks adds later are covered automatically.
- It **excludes** `MANAGE`, `READ METADATA`, `EXTERNAL USE SCHEMA`, and `EXTERNAL USE LOCATION`.
- `SHOW GRANTS` shows only `ALL PRIVILEGES`, not the implied individual privileges.
- `REVOKE ALL PRIVILEGES` removes it and any implied individual grants, but leaves `MANAGE` intact.

### Q: What is `MODIFY`?
Write access: INSERT, UPDATE, DELETE, MERGE. Fine-grained `INSERT`/`UPDATE`/`DELETE` privileges exist in Beta. Best practice: give prod `MODIFY` only to **service principals**.

### Q: GRANT / REVOKE / SHOW syntax essentials?
```sql
GRANT SELECT, MODIFY ON TABLE c.s.t TO `etl-app-id`;
GRANT CREATE CATALOG ON METASTORE TO `platform`;   -- no metastore name
REVOKE SELECT ON TABLE c.s.t FROM `analysts`;      -- succeeds even if never granted
SHOW GRANTS ON SCHEMA c.s;
SHOW GRANTS `u@contoso.com` ON TABLE c.s.t;
```
- Use backticks (not quotes) for principals that contain `@`, `-`, or spaces.
- Reference a service principal by its **application ID**.

### Q: Advantages / disadvantages of granting at catalog level?
- Advantage: one grant covers everything, including future objects.
- Disadvantage: very broad blast radius. Prefer schema-level grants for data, and catalog-level only for `USE CATALOG` and `BROWSE`.

### Q: Exam trap: User has `SELECT` on the table but gets PERMISSION_DENIED. Why?
They are missing `USE SCHEMA` and/or `USE CATALOG` on the parents.

### Q: Exam trap: Does `GRANT CREATE CATALOG ON METASTORE` let the user read existing catalogs?
No. Metastore grants don't inherit downward.

## §4 Ownership, MANAGE, and who can grant

### Q: What does ownership give you?
Every object has exactly **one** owner (a user, SP, or group). The owner implicitly has all privileges on the object, can grant and revoke, transfer ownership, and drop it. The owner also gets **`MANAGE` on children**, but **ownership does not inherit**: the catalog owner does not own the tables in it.

### Q: What is `MANAGE`?
A delegable, near-owner privilege: grant and revoke, transfer ownership, and drop.
- It does **not** grant data access, but the holder can grant themselves `SELECT`.
- It cascades to children when granted on a container.
- Many principals can hold it.
- `MANAGE` on a catalog needs **no** usage privileges. `MANAGE` on a schema needs `USE CATALOG`. On a table, it needs both usage privileges.

### Q: Who can GRANT privileges on an object?
1. The object owner
2. The owner of the parent catalog or schema
3. A holder of `MANAGE` on the object (direct or inherited)
4. A metastore admin

Account admins can grant on the metastore itself.

### Q: How is it used?
```sql
ALTER TABLE sales.gold.orders OWNER TO `data-owners`;      -- ownership to a group (best practice)
GRANT MANAGE ON SCHEMA sales.gold TO `gold-stewards`;      -- delegate without transferring ownership
DESCRIBE TABLE EXTENDED sales.gold.orders;                 -- shows Owner
```

### Q: How does owner compare to `MANAGE`?
| | Owner | MANAGE |
|---|---|---|
| Data capabilities | Implied | No (can self-grant) |
| Grant/revoke, transfer, drop | Yes | Yes |
| Principals | Exactly 1 | Many |
| Included in `ALL PRIVILEGES` | n/a | **No** |

### Q: Exam trap: User has `ALL PRIVILEGES` on a schema and tries to `GRANT SELECT` to a colleague. Result?
It fails. `ALL PRIVILEGES` excludes `MANAGE`. Grant `MANAGE`, or make the user (or their group) the owner.

### Q: Exam trap: Who can transfer ownership of a share?
Only a **metastore admin**. Shares are the exception to the normal owner/`MANAGE` rules.

## §5 Principals: account groups vs workspace-local groups; admin roles

### Q: What principals can receive UC grants?
- Account users
- **Account groups**, including External groups synced from Entra ID
- The `account users` system group
- Service principals

**Workspace-local groups can't**, and that includes the workspace system groups `users` and `admins`.

### Q: What is a workspace-local group and why is it legacy?
A group created inside one workspace (source "Workspace"). It can't be assigned to other workspaces, receive UC privileges, or hold account roles. Databricks recommends converting such groups to account groups. UCX automates the conversion.

### Q: What are the admin roles?
- **Account admin:** account console; creates metastores, assigns workspaces, grants on the metastore. The first account admin must be an Entra **Global Administrator** at first login.
- **Metastore admin** (optional): can manage any object's privileges and ownership. Best practice is to assign the role to a group.
- **Workspace admin:** workspace-level. In auto-enabled workspaces, also owns the workspace catalog and gets extra UC defaults. Account admins can restrict this with `RestrictWorkspaceAdmins`.

### Q: How is it used?
```sql
GRANT SELECT ON SCHEMA sales.gold TO `analysts`;   -- analysts = account group (Entra-synced)
```

### Q: Exam trap: `GRANT SELECT ON TABLE c.s.t TO users;` What's wrong?
`users` is a **workspace-local** system group. Use an account group, or `account users`.

## §6 Managed vs external tables, managed storage

### Q: What is a managed table?
A Delta or Iceberg table whose storage location UC chooses: the managed storage of the schema, else the catalog, else the metastore. On `DROP`, the data is deleted after the recovery period (default **7 days**, recoverable with `UNDROP`; the async purge can take up to about 30 days).

### Q: What is an external table?
A table registered over a path you specify (`LOCATION 'abfss://…'`) inside an external location. Formats: Delta, CSV, JSON, AVRO, PARQUET, ORC, TEXT. On `DROP`, only metadata is removed and the **files remain**.

### Q: How are they used?
```sql
CREATE TABLE sales.gold.orders (id BIGINT, amt DECIMAL(18,2));                 -- managed
CREATE TABLE sales.bronze.raw (id BIGINT, payload STRING)
  LOCATION 'abfss://raw@contosolake.dfs.core.windows.net/orders/';              -- external
UNDROP TABLE sales.gold.orders;                     -- or SHOW TABLES DROPPED + UNDROP TABLE WITH ID '<id>'
CREATE SCHEMA sales.tmp RETAIN DROPPED FOR 0 HOURS; -- recovery period: 0 or 7–30 days (Public Preview)
```

### Q: Advantages of managed tables?
- Predictive optimization and automatic liquid clustering
- Metadata caching
- Automatic file deletion after a drop
- `UNDROP`
- Automatic upgrades to new features

Managed tables are also readable by external engines through the UC REST and Iceberg REST APIs, so there is no lock-in. **They are the default and the recommendation.**

### Q: Disadvantages of managed tables / advantages of external tables?
Managed tables have a UC-chosen layout, so you can't point arbitrary non-UC tools at the path. External tables fit when existing data must stay in place, when external systems need direct path access, or when the format is non-Delta (CSV, Parquet, ...). The cost is that you own file lifecycle, optimization, and cleanup yourself.

### Q: How is managed storage resolved?
**Schema > catalog > metastore**: the lowest level that defines a location wins.
- Catalog level is recommended.
- The metastore level is optional and absent in new auto-enabled setups. **If the metastore has no root, `CREATE CATALOG` must specify `MANAGED LOCATION`.**
- Setting a managed location requires **`CREATE MANAGED STORAGE`** on the target external location.
- Changing it affects only **new** objects.
```sql
CREATE CATALOG finance MANAGED LOCATION 'abfss://fin@contosolake.dfs.core.windows.net/uc';
CREATE SCHEMA finance.restricted MANAGED LOCATION 'abfss://finsec@contosolake.dfs.core.windows.net/uc';
```

### Q: What replaced what?
`ALTER TABLE ... SET MANAGED` converts UC external or foreign Delta tables to managed (rollback with `UNSET MANAGED` within 14 days). Metastore-level root storage was required in early UC; catalog-level storage is the current pattern.

### Q: Exam trap: `CREATE SCHEMA c.s LOCATION 'abfss://…'` in UC?
Wrong keyword. UC uses **`MANAGED LOCATION`**. `LOCATION` is the HMS syntax.

### Q: Exam trap: `DROP SCHEMA ... CASCADE` in UC deletes which files?
Managed table files only. External table files remain. (In HMS, CASCADE deletes everything under the schema location.)

## §7 Storage credentials (Azure managed identity via Access Connector)

### Q: What is a storage credential?
A metastore-level securable that wraps a long-term cloud identity, either an **Azure managed identity** (through an Access Connector) or an Entra ID service principal. UC uses it to access ADLS Gen2.

### Q: What is the Access Connector for Azure Databricks?
A first-party Azure resource that holds a **system-assigned and/or user-assigned managed identity** and connects it to the Databricks account. Create it in the **same region** as the storage.

### Q: How is it used? (setup order)
1. Azure portal: create the Access Connector and note its resource ID (`/subscriptions/…/providers/Microsoft.Databricks/accessConnectors/<name>`).
2. On the storage account: grant the MI **Storage Blob Data Contributor**. You need Owner or User Access Administrator to assign it. For least privilege, use Storage Blob Delegator on the account plus Storage Blob Data Contributor on the container.
   For file events (Auto Loader notifications), also grant **Storage Queue Data Contributor**. Add Storage Account Contributor and EventGrid EventSubscription Contributor if Databricks should auto-configure the events.
3. Databricks: create the storage credential (type Azure Managed Identity) with the connector ID. Use Catalog Explorer, CLI, API, or Terraform. This requires **`CREATE STORAGE CREDENTIAL`** on the metastore. Optional settings: **read-only**, and workspace binding.
```sql
GRANT CREATE EXTERNAL LOCATION ON STORAGE CREDENTIAL lake_mi_cred TO `platform-team`;
ALTER STORAGE CREDENTIAL lake_mi_cred OWNER TO `platform-team`;
```

### Q: Advantages of a managed identity over a service principal?
- No secret to rotate.
- It **can access storage accounts protected by network rules or firewalls** (trusted access), which a service principal can't.
- It is Microsoft's recommended option.

### Q: Disadvantages / limitations?
- Needs Azure RBAC rights (Owner or User Access Administrator) to assign roles.
- One credential can cover a broad scope, so scope it with external locations, not by handing out credential privileges.

### Q: When NOT to grant privileges on the credential directly?
Almost always. Grant on **external locations** (path-scoped) instead. Credential privileges like `READ FILES` and `WRITE FILES` are broad.

### Q: How does a storage credential compare to a service credential?
A storage credential is used to access **storage** (external locations and tables). A service credential is used to reach **external cloud services** through SDKs, with the `ACCESS` privilege.

### Q: Exam trap: "No secrets; storage firewall enabled." Which identity?
A managed identity through the Access Connector, wrapped in a storage credential.

## §8 External locations

### Q: What is an external location?
A securable that pairs a **cloud path (URL)** with a **storage credential**. It authorizes external tables and volumes, direct file access, and managed storage under that path.

### Q: How is it used?
```sql
CREATE EXTERNAL LOCATION IF NOT EXISTS raw_zone
  URL 'abfss://raw@contosolake.dfs.core.windows.net/'
  WITH (STORAGE CREDENTIAL lake_mi_cred)
  COMMENT 'Raw landing';
GRANT READ FILES, WRITE FILES ON EXTERNAL LOCATION raw_zone TO `data-engineers`;
GRANT CREATE EXTERNAL TABLE, CREATE EXTERNAL VOLUME ON EXTERNAL LOCATION raw_zone TO `data-engineers`;
GRANT CREATE MANAGED STORAGE ON EXTERNAL LOCATION raw_zone TO `catalog-admins`;
```
Creating one requires `CREATE EXTERNAL LOCATION` on **both the metastore and the storage credential**. Names with `-` need backticks.

### Q: Which privileges exist on an external location?
| Privilege | Allows |
|---|---|
| `READ FILES` / `WRITE FILES` | Direct path access. **`WRITE FILES` requires `READ FILES`.** |
| `CREATE EXTERNAL TABLE` | Register external tables under the path |
| `CREATE EXTERNAL VOLUME` | Register external volumes under the path |
| `CREATE MANAGED STORAGE` | Use the path as a catalog or schema `MANAGED LOCATION` |
| `CREATE FOREIGN SECURABLE` | Authorized paths for HMS-federated catalogs |

### Q: Advantages?
- Path-scoped, auditable storage access.
- Can be marked read-only.
- Can be bound to specific workspaces.
- "Fallback mode" eases migrations by falling back to legacy cluster credentials.

### Q: Disadvantages / limitations?
- Paths can't overlap with managed storage or other tables and volumes.
- Granting broad `READ FILES` bypasses table-level governance. Once a table or volume exists on a path, **the table or volume privileges govern that path**, not the location grants.

### Q: Best practice on paths?
Create external tables and volumes in **sub-directories**, never at the location root.

### Q: Exam trap: User has `WRITE FILES` only and writes fail. Fix?
Also grant `READ FILES`.

### Q: Exam trap: User owns the storage credential but can't create an external location. Why?
They lack `CREATE EXTERNAL LOCATION` on the **metastore**. Both are required.

## §9 Volumes

### Q: What is a volume?
A UC securable in a schema that governs **non-tabular files** (any format) in cloud storage. It is a sibling of tables. **Managed** volumes live in the schema's managed storage. **External** volumes are registered on a directory inside an external location.

### Q: How is it used?
```sql
CREATE VOLUME sales.raw.landing;                                       -- managed
CREATE EXTERNAL VOLUME sales.raw.vendor_drop
  LOCATION 'abfss://raw@contosolake.dfs.core.windows.net/vendor/';     -- external
GRANT READ VOLUME, WRITE VOLUME ON VOLUME sales.raw.landing TO `ingest-sp-app-id`;
SELECT * FROM read_files('/Volumes/sales/raw/landing/2026/*.csv', format => 'csv');
```
- File path: `/Volumes/<catalog>/<schema>/<volume>/<path>` (`dbfs:/Volumes/...` also works). The DDL name is `catalog.schema.volume`.
- Volumes are not queried as objects (no SELECT). Use path access, `read_files`, Auto Loader, or `COPY INTO`.

### Q: Privileges?
- Create: `USE CATALOG`, `USE SCHEMA`, `CREATE VOLUME`. An external volume also needs **`CREATE EXTERNAL VOLUME`** on the location.
- Read: `READ VOLUME`. Write: `WRITE VOLUME`.
- Drop, rename, or manage grants: owner or `MANAGE`.

### Q: Advantages?
- Replaces DBFS mounts with governed, audited, lineage-tracked file access.
- A good home for Auto Loader landing zones, checkpoints, libraries, ML artifacts, images, and PDFs.

### Q: Disadvantages / limitations?
- Only path-based access, no SQL object queries.
- Managed volumes have no cloud-URI access (only `/Volumes`).
- External volumes can be reached by external systems directly, bypassing UC.
- Paths can't overlap with tables or other volumes.

### Q: Managed vs external volume?
| | Managed | External |
|---|---|---|
| DROP | Files deleted (`UNDROP VOLUME` within 7 days) | Files remain |
| Access | `/Volumes` path only | `/Volumes` path or cloud URI |
| Use | New governed file storage | Files that already exist in ADLS or are shared with other tools |

### Q: Exam trap: `GRANT SELECT ON VOLUME ...`?
That privilege doesn't exist. Use `READ VOLUME`.

## §10 Dynamic views

### Q: What is a dynamic view?
A view whose SQL uses identity functions to filter rows or mask columns per user:
- `session_user()` / `current_user()` (`current_user` is now an alias; `session_user` is preferred)
- `is_account_group_member()` (account groups, recommended in UC)
- `is_member()` (legacy, workspace-scoped)

### Q: How is it used?
```sql
CREATE OR REPLACE VIEW sales.gold.orders_secure AS
SELECT order_id,
       CASE WHEN is_account_group_member('finance') THEN card_number ELSE '****' END AS card_number,
       region, amount
FROM sales.gold.orders
WHERE is_account_group_member('global_sales') OR region = 'EMEA';
GRANT SELECT ON VIEW sales.gold.orders_secure TO `analysts`;   -- do NOT grant the base table
```
The reader needs `SELECT` on the **view** plus usage privileges. They need **nothing on the base tables**, because the view owner's privileges resolve them. Exception: dedicated compute on DBR 15.3 and below checks both.

### Q: Compute requirements?
A SQL warehouse, standard access mode, or dedicated access mode on **DBR 15.4 LTS+** (filtering runs on serverless, so serverless must be enabled).

### Q: Advantages?
- Can span or join **multiple tables** and reshape data.
- Can be **Delta Shared**.
- Full predicate pushdown, so often faster than row filters.
- Users can't modify the base tables through the view.

### Q: Disadvantages?
- Introduces a new object, so users must query a different name.
- **Weaker auditing**: no policy or tag metadata in system tables.
- **Vulnerable to probing attacks**: there is no `SecureView` barrier.
- Grant hygiene matters: base-table grants make the view pointless.

### Q: When to use / when NOT?
Use dynamic views for multi-table logic, aggregated or reshaped exposure, or sharing filtered data. For per-table security under the same table name, use row filters or masks. For rules across many tables, use ABAC.

### Q: What replaced what?
For single-table row and column security, row filters, column masks, and ABAC are the modern recommendation. Dynamic views remain valid for multi-table and sharing cases.

### Q: Exam trap: A view uses `is_member('finance')`, and members of the account group `finance` see masked data. Fix?
Use `is_account_group_member('finance')`. `is_member` checks workspace-scoped groups.

## §11 Row filters

### Q: What is a row filter?
A SQL UDF that returns `BOOLEAN`, bound to a table. At scan time, rows where it returns false or null are removed. It applies to tables, materialized views, and streaming tables.

### Q: How is it used?
```sql
CREATE OR REPLACE FUNCTION sec.fn.region_filter(region STRING)
RETURNS BOOLEAN
RETURN is_account_group_member('admins_global') OR region = 'US';

ALTER TABLE sales.gold.orders SET ROW FILTER sec.fn.region_filter ON (region);   -- columns map positionally
ALTER TABLE sales.gold.orders DROP ROW FILTER;
CREATE TABLE t (x INT, region STRING) WITH ROW FILTER sec.fn.region_filter ON (region);
-- ON ()  → filter with no column args;  ON (region, 'US') → literals allowed
```

### Q: Who can attach it?
- `EXECUTE` on the function, plus `USE CATALOG` and `USE SCHEMA`
- **and** table ownership, or `MANAGE` **and** `SELECT` on the table
- For a new table: `CREATE TABLE` on the schema
- Add `MODIFY` if the same statement changes the schema

### Q: Whose rights does it run with?
**Definer's rights**, except identity functions (`session_user`, `is_account_group_member`), which evaluate as the **invoker**. Querying users therefore don't need access to mapping tables used inside the UDF.

### Q: Compute?
- SQL warehouse
- Standard access mode on DBR 12.2 LTS+
- Dedicated access mode on DBR 15.4 LTS+ with serverless enabled (reads only; writes need 16.3+ and patterns such as `MERGE INTO`)

Older runtimes **fail closed** and return no data.

### Q: Advantages?
- In-place security: users keep querying the same table name.
- Metadata is visible in `information_schema.row_filters` and `DESCRIBE EXTENDED`.
- Secure against probing.

### Q: Disadvantages / limitations?
- One filter per table.
- Can't be applied to **views**.
- **No time travel, no clones.**
- **A table with a table-level filter can't be Delta Shared.**
- Python UDFs must be wrapped in a SQL UDF.
- Some optimizations are lost. Keep UDFs simple, deterministic, and non-throwing (e.g., `try_divide`).
- `REPLACE TABLE` keeps the filter.

### Q: Exam trap: You `DROP FUNCTION` and now every query on the table fails. Why, and what's the fix?
The table still references the function. Run `ALTER TABLE ... DROP ROW FILTER`, which you should always do **before** `DROP FUNCTION`.

### Q: Exam trap: Filter UDF `f(r STRING)` applied with `ON (region, country)`. Result?
Error. The argument count and types must match the function's parameters positionally.

## §12 Column masks

### Q: What is a column mask?
A SQL UDF bound to a single column. Its first parameter is the column value, and it returns the original or masked value. **The return type must match, or be castable to, the column type.** There is one mask per column.

### Q: How is it used?
```sql
CREATE OR REPLACE FUNCTION sec.fn.ssn_mask(ssn STRING)
RETURN CASE WHEN is_account_group_member('hr') THEN ssn ELSE '***-**-****' END;

ALTER TABLE hr.core.employees ALTER COLUMN ssn SET MASK sec.fn.ssn_mask;
ALTER TABLE crm.core.customers ALTER COLUMN address
  SET MASK sec.fn.mask_by_country USING COLUMNS (country, '_address_viewers');   -- extra args
ALTER TABLE hr.core.employees ALTER COLUMN ssn DROP MASK;
CREATE TABLE hr.core.users (name STRING, ssn STRING MASK sec.fn.ssn_mask);
```

### Q: Behavior detail?
The mask applies as soon as rows are fetched. Joins, predicates, and sorting then operate on the **masked** values. Nested STRUCT fields can be masked by rebuilding the struct with `named_struct()`.

### Q: Advantages / limitations?
Same profile as row filters (§11): in-place, auditable, no time travel, no clones, can't be shared, can't be applied to views, privileges `EXECUTE` + owner or (`MANAGE` + `SELECT`). Extra limitations: you can't mask columns referenced by generated columns, and ANSI-off type mismatches can silently become `NULL`.

### Q: Column mask vs dynamic view masking?
A mask keeps the table name and is tracked as metadata. A view adds a new object but can combine tables and can be shared.

### Q: Exam trap: Mask function returns `INT` for a `STRING` SSN column.
Type mismatch. The return type must match the masked column or the first parameter.

## §13 Tags & ABAC

### Q: What are tags and governed tags?
Tags are key/value metadata on catalogs, schemas, tables, columns, volumes, functions, and more. **Governed tags** are account-level tags with an enforced allowed-value list and assignment permissions (`ASSIGN`).

### Q: How are tags used?
```sql
ALTER TABLE c.s.t SET TAGS ('domain' = 'finance');
ALTER TABLE c.s.t ALTER COLUMN ssn SET TAGS ('pii' = 'ssn');   -- one column per statement
SET TAG ON TABLE c.s.t `system.certification_status` = `certified`;   -- DBR 16.1+
UNSET TAG ON COLUMN c.s.t.ssn pii;
```
Tagging requires `APPLY TAG` (or ownership) plus usage privileges, and `ASSIGN` on a governed tag.

### Q: What is ABAC?
Attribute-based access control. You attach policies at **catalog or schema** level, and they apply row filters or column masks automatically to every table or column that matches a tag condition:
```sql
CREATE POLICY mask_pii ON CATALOG prod
COLUMN MASK prod.governance.mask_value
TO `account users` EXCEPT `etl_service_principal`
FOR TABLES
MATCH COLUMNS has_tag_value('pii', 'ssn') AS ssn
ON COLUMN ssn;
```

### Q: Advantages?
- Define once and it applies to new tables automatically.
- Scales to thousands of tables.
- **Recommended** by Microsoft over per-table filters and masks for consistency.
- Exempt principals (via `EXCEPT`) can clone and share.

### Q: Disadvantages / limitations?
- Requires DBR **16.4+** or serverless, and **fails closed** on older runtimes.
- Only one distinct filter can resolve per user and table, and one mask per column. Conflicts error out.
- Deleting a governed tag or UDF that a policy references breaks queries.
- Tag keys are **case-sensitive**. Max 50 tags per object.
- You can't drop a column that has governed tags until you unset them.

### Q: ABAC vs table-level filters and masks vs dynamic views?
- ABAC: many tables, tag-driven.
- Table-level filters and masks: one table, owner-managed.
- Dynamic views: multi-table logic or sharing.

### Q: Exam trap: Tag `Sales` vs `sales`?
They are two different tags. Keys are case-sensitive.

## §14 Service principals

### Q: What is a service principal?
An API-only identity for automation (jobs, CI/CD, BI tools). You grant it UC privileges like any user. There are two kinds:
- **Azure Databricks-managed SP**: authenticates with Databricks OAuth (M2M) or a PAT. The recommended default for Databricks-only automation.
- **Microsoft Entra ID-managed SP**: authenticates with Databricks OAuth or **Entra ID tokens**. Use it when the same identity must also authenticate to other Azure resources.

### Q: How is it used?
```sql
GRANT USE CATALOG ON CATALOG prod TO `7f1c...-app-id`;
GRANT USE SCHEMA, SELECT, MODIFY ON SCHEMA prod.silver TO `7f1c...-app-id`;
```
Then set the job's **Run as** to the SP. You need the **Service Principal: User** role on it. The creator gets Manager by default, **not** User, so grant User explicitly. Authenticate tools (CLI, JDBC/ODBC, dbt, Power BI) with **OAuth M2M** (client credentials).

### Q: Advantages?
- Jobs don't break when a person leaves.
- Least-privilege, auditable identity.
- No user PATs in pipelines.
- You can disable it without affecting any user.

### Q: Disadvantages?
- More identities to manage.
- Needs workspace entitlements (e.g., cluster creation) and `CAN USE` on warehouses.
- Entra-managed SP M2M with Power BI has a 1-hour token refresh limit.

### Q: What replaced what?
OAuth M2M replaced PATs as the recommended service authentication. Run-as-SP replaced "job owner = a human".

### Q: SP vs storage-credential managed identity?
An SP is a **workload identity**: who runs the job, and whose UC grants apply. The Access Connector MI is **UC's own identity for storage**: how UC reaches ADLS. They are different layers.

### Q: Exam trap: A production job fails after its creator leaves. Fix?
Set **Run as** to a service principal and grant the SP the UC privileges it needs.

## §15 Workspace-catalog binding

### Q: What is it?
A catalog-level setting that restricts which workspaces can access a catalog. The default isolation mode is **OPEN** (all attached workspaces). **ISOLATED** plus bound workspaces makes access from any other workspace **denied, even with explicit grants**. Each binding can be **read-write or read-only**.

### Q: How is it used?
In Catalog Explorer (catalog → **Workspaces** tab → clear "All workspaces have access" → assign), or the CLI:
```bash
databricks catalogs update prod --isolation-mode ISOLATED
databricks workspace-bindings update-bindings catalog prod \
  --json '{"add":[{"workspace_id":1234,"binding_type":"BINDING_TYPE_READ_ONLY"}]}'
```
Who: metastore admin, catalog owner, or `MANAGE` on the catalog. `READ METADATA` is enough to view bindings. **It is not a SQL GRANT.**

### Q: Advantages?
- Enforces environment boundaries (prod only from prod workspaces).
- Prevents certain data domains from being joined.
- Read-only consumption from other workspaces.
- Enforced across `information_schema`, lineage, and Catalog Explorer.

### Q: Limitations?
- Logical, not physical: metadata still lives in the shared metastore.
- The default workspace catalog is pre-bound to its own workspace. If you extend it, re-grant to account groups, because the workspace `admins` group is workspace-local.

### Q: Do other objects support binding?
Yes: **external locations and storage credentials**. Bindings are checked when the privilege is exercised. An external table keeps working if its location is later unbound, and the catalog binding still applies.

### Q: Exam trap: "Engineers with grants must not read prod from the dev workspace." Revoke grants or bind?
**Bind** the prod catalog to the prod workspaces. The binding overrides grants.

## §16 Delta Sharing (OpenSharing)

### Q: What is Delta Sharing?
An open protocol for secure, read-only sharing of live data without copying it. Objects:
- **Share** (provider side): tables, schemas, views, MVs, volumes, models, notebooks
- **Recipient** (provider side): who you share with
- **Provider** (recipient side): represents the sharer

### Q: What are the two protocols?
| | Databricks-to-Databricks (D2D) | Open sharing (Databricks-to-Open) |
|---|---|---|
| Recipient | Has a UC-enabled workspace (any region or cloud) | Any client (pandas, Spark, Power BI, ...) |
| Auth | Recipient's **sharing identifier** `<cloud>:<region>:<uuid>` (they run `SELECT current_metastore()`). Auth type `DATABRICKS`. | **Bearer token** in a **credential file** via an **activation link** (downloadable **once**), or **OIDC federation**. Auth type `TOKEN`. |
| SQL | `CREATE RECIPIENT r USING ID '…';` | `CREATE RECIPIENT r;` then `DESCRIBE RECIPIENT r` (shows `activation_link`) |
| Extras | History sharing, views, volumes, models, notebooks; no token management | Token rotation and expiry |

### Q: How is it used? (provider)
```sql
CREATE SHARE IF NOT EXISTS retail_share;
ALTER TABLE retail.gold.orders SET TBLPROPERTIES (delta.enableChangeDataFeed = true);  -- before sharing, if CDF needed
ALTER SHARE retail_share ADD TABLE retail.gold.orders AS retail.orders WITH HISTORY;
ALTER SHARE retail_share ADD TABLE retail.gold.sales PARTITION (region = 'EU');
ALTER SHARE retail_share ADD TABLE retail.gold.stock PARTITION (country = CURRENT_RECIPIENT().country);
ALTER SHARE retail_share ADD SCHEMA retail.ref;               -- DBR 13.3+; history included by default
CREATE RECIPIENT fabrikam USING ID 'azure:westeurope:19a8…' PROPERTIES ('country' = 'DE');
GRANT SELECT ON SHARE retail_share TO RECIPIENT fabrikam;     -- SELECT is the only share privilege
```

### Q: How is it used? (D2D recipient)
```sql
CREATE CATALOG fabrikam_retail USING SHARE contoso_provider.retail_share;
GRANT USE CATALOG ON CATALOG fabrikam_retail TO `bi-team`;
SELECT * FROM fabrikam_retail.retail.orders VERSION AS OF 12;          -- needs WITH HISTORY
SELECT * FROM table_changes('fabrikam_retail.retail.orders', 5);      -- needs CDF + WITH HISTORY
```
Shared data is **read-only** for the recipient.

### Q: What does `WITH HISTORY` do?
It shares the table's history, enabling **time travel, streaming reads, and (if CDF is enabled at the source) `table_changes()`**. For D2D it also shares the Delta log for better performance.
- It is the **default on DBR 16.2+ and DBSQL**. Earlier runtimes default to `WITHOUT HISTORY`. `WITH HISTORY` itself needs DBR 12.2+.
- `WITH CHANGE DATA FEED` is deprecated.
- Partitioned shares don't get the performance boost.

### Q: Privileges?
- Create a share or recipient: `CREATE SHARE` / `CREATE RECIPIENT` on the metastore, or metastore admin.
- Add a table: **share owner** + `USE SCHEMA` + `SELECT` on the table, kept for as long as the table is shared. Volumes need `READ VOLUME`.
- Grant a share to a recipient: metastore admin, or (share owner or `USE SHARE` + `SET SHARE PERMISSION`) **and** (recipient owner or `USE RECIPIENT`).
- Share ownership transfer: **metastore admin only**.
- Recipient side, creating the catalog: `CREATE CATALOG` + `USE PROVIDER` (or provider ownership).

### Q: Advantages?
- No copies or ETL; recipients read live data.
- Works cross-region, cross-cloud, and cross-platform.
- Partition and recipient-property filtering.
- Revocable instantly.
- Shares are audited.

### Q: Disadvantages / limitations?
- Read-only.
- **Tables with table-level row filters or masks can't be shared**. Share a dynamic view, or use ABAC with the share owner exempt.
- An alias hides the original name: recipients must use the alias.
- Open-sharing tokens are bearer secrets: rotate them, and use OIDC where possible.

### Q: Delta Sharing vs copying data (export/ETL)?
Sharing is zero-copy and always current, with governance staying with the provider. A copy duplicates storage and goes stale, but lets the consumer write.

### Q: Exam trap: Recipient gets an error calling `table_changes()` on a table shared `WITH HISTORY`.
CDF wasn't enabled on the source table **before** sharing. Enable `delta.enableChangeDataFeed`. CDF only captures changes made after it was enabled.

### Q: Exam trap: Partner has no Databricks. What do they receive?
An **activation link**, from which they download a credential file **once** (or use OIDC federation). Not a sharing identifier.

## §17 Lineage

### Q: What is UC lineage?
Automatically captured **table- and column-level** data flow for queries on UC-enabled compute. It covers notebooks, jobs, pipelines, dashboards, and models, and is shown on the Catalog Explorer **Lineage** tab.

### Q: How is it used?
In Catalog Explorer (table → Lineage → graph), the lineage API, or system tables:
```sql
SELECT source_table_full_name, target_table_full_name, entity_type, created_by, event_time
FROM system.access.table_lineage
WHERE source_table_full_name = 'sales.gold.orders';
```

### Q: Advantages?
- No instrumentation needed.
- Impact analysis before schema changes.
- Root-cause tracing.
- Lineage visibility is privilege-filtered: `BROWSE` lets users see lineage metadata.

### Q: Limitations?
- Captured only when it can be inferred (some path-based or external-engine operations are missed).
- System-table lineage retains about 365 days (the UI/API keeps lineage indefinitely since Sept 2024).
- Filtered by workspace bindings.

### Q: Lineage vs audit log?
Lineage shows **data flow** (what feeds what). The audit log shows **who did what, when**.

### Q: Exam trap: "Which dashboards break if I drop column X?"
**Column lineage** (`system.access.column_lineage`), not the audit log.

## §18 System tables

### Q: What are system tables?
Databricks-hosted, **read-only** analytical tables in the `system` catalog. They hold operational data for your account, delivered via Delta Sharing from a Databricks-hosted storage account in the metastore's region.

### Q: Which ones matter for DP-750?
| Table | Contents |
|---|---|
| `system.access.audit` | Audit events: `event_date` (**partition, filter on it**), `event_time`, `user_identity.email`, `service_name` (e.g., `'unityCatalog'`), `action_name` (e.g., `'getTable'`), `request_params`, `source_ip_address`, `identity_metadata.run_by/run_as`. Regional (account-level events are global). |
| `system.billing.usage` | DBUs: `usage_date`, `sku_name`, `usage_quantity`, `billing_origin_product`, `usage_metadata.job_id`, `custom_tags`, `identity_metadata`. **Global.** |
| `system.billing.list_prices` | Join to usage for $ (`pricing.effective_list.default`) |
| `system.access.table_lineage` / `column_lineage` | Lineage |
| `system.compute.*`, `system.lakeflow.*` | Compute and job observability |

### Q: How is it used?
```sql
SELECT event_time, user_identity.email, action_name, request_params
FROM system.access.audit
WHERE service_name = 'unityCatalog' AND action_name = 'getTable'
  AND event_date >= current_date() - INTERVAL 7 DAYS;

SELECT usage_metadata.job_id, SUM(usage_quantity) AS dbus
FROM system.billing.usage WHERE usage_metadata.job_id IS NOT NULL
GROUP BY 1 ORDER BY dbus DESC;
```

### Q: Access control?
Account admins have access by default. To open the tables to others, a principal who is **both a metastore admin and an account admin** grants `USE CATALOG` on `system`, `USE SCHEMA` on the schema, and `SELECT`. Schemas are enabled per metastore. Requires at least one UC workspace.

### Q: Advantages?
- SQL-queryable, streamable observability across all workspaces in the region.
- Free retention, typically 365 days.
- Usage and pricing tables are free.

### Q: Limitations?
- Read-only.
- Billing records arrive with latency (about 12 hours).
- Some `request_params` keys (view or function definitions) are masked unless you are an account admin or in `databricks_pii_access`.
- Dedicated compute needs DBR 15.4+ with serverless to query audit.

### Q: What replaced what?
Audit system tables replace parsing diagnostic-log JSON delivered to storage or Log Analytics for most analytics. Diagnostic settings still exist.

### Q: Exam trap: "Show who queried PII tables last month."
`system.access.audit`. Not `information_schema` (current state only) and not lineage.

## §19 information_schema

### Q: What is it?
SQL-standard metadata views:
- `<catalog>.information_schema` covers **that catalog** only.
- `system.information_schema` covers **all catalogs** in the metastore.

Views include `TABLES`, `COLUMNS`, `VIEWS`, `SCHEMATA`, `TABLE_PRIVILEGES`, `SCHEMA_PRIVILEGES`, `CATALOG_PRIVILEGES`, `ROUTINES`, `VOLUMES`, `TABLE_TAGS`, `COLUMN_TAGS`, `ROW_FILTERS`, `COLUMN_MASKS`, and more.

### Q: How is it used?
```sql
SELECT grantee, privilege_type FROM sales.information_schema.table_privileges
WHERE table_schema = 'gold' AND table_name = 'orders';
SELECT * FROM system.information_schema.column_tags WHERE tag_name = 'pii';
```

### Q: Advantages / limitations?
- Advantage: standard SQL inventory of objects, grants, tags, filters, and masks.
- Limitation: results are **filtered to what the caller can see**, and to catalogs bound to the current workspace. It shows **current state only**, with no history.
- Known gap: `MANAGE` holders see only their own grants there (use `SHOW GRANTS` instead).

### Q: information_schema vs system tables?
information_schema answers "what exists and who has access **now**". System tables answer "what **happened**" (audit, billing, lineage).

### Q: Exam trap: "Find all PII-tagged columns across every catalog."
`system.information_schema.column_tags`, not a single catalog's `information_schema`.

## §20 Hive metastore federation

### Q: What is it?
It makes UC govern tables still registered in a Hive metastore by mirroring the HMS into a **foreign catalog**. Queries run with HMS semantics, while UC does access checks, lineage, and audit.
- **Internal** (workspace) HMS: **read and write**. DDL and DML write through to HMS.
- **External** HMS: **read-only**.

### Q: How is it used?
1. Create a connection (type Hive Metastore, Internal). This needs `CREATE CONNECTION`.
2. Create a storage credential and external location for the table paths. Optionally enable **fallback mode** so legacy workloads keep working during migration.
3. Create the foreign catalog:
```sql
CREATE FOREIGN CATALOG IF NOT EXISTS hms_in_uc USING CONNECTION hms_conn
OPTIONS (authorized_paths 'abfss://c@acct.dfs.core.windows.net/demo',
         storage_root     'abfss://c@acct.dfs.core.windows.net/meta');
```
4. Grant on it like any UC catalog. Compute must be standard access mode on DBR 13.3/14.3/15.1+.

### Q: Advantages?
- Incremental migration: workloads move independently while data stays visible in both HMS and UC.
- UC governance applies immediately.

### Q: Disadvantages?
- Not a true migration: tables remain foreign, and you don't get managed-table benefits until converted.
- **DROP through the foreign catalog drops in HMS, with no `UNDROP`.**
- External HMS is read-only.

### Q: Federation vs SYNC vs DEEP CLONE?
Federation **governs in place**. SYNC **creates UC external tables**. DEEP CLONE **creates UC managed tables**.

### Q: Exam trap: "Teams migrate at different paces; HMS and UC must both stay usable with writes."
HMS federation for the **internal** HMS.

## §21 UCX

### Q: What is UCX?
A **Databricks Labs** toolkit (GitHub `databrickslabs/ucx`, not officially supported). Its CLI and workflows **assess** a workspace's UC readiness and migrate **groups, permissions, storage credentials, locations, and tables**.

### Q: How is it used?
1. Install it with the Databricks CLI and run the **assessment** workflow.
2. Migrate groups (workspace-local → account).
3. Run the prep commands (`create-table-mapping`, `create-uber-principal`, `migrate-credentials`, `migrate-locations`, `create-catalogs-schemas`).
4. Run the table migration workflow: HMS external tables go through `SYNC` to UC external; DBFS-root managed tables go through `DEEP CLONE` to UC managed.

### Q: Advantages?
- Comprehensive and suited to large estates.
- **The only option for bulk upgrade to UC managed tables.**

### Q: Disadvantages?
- Script-heavy, and community-supported only.
- Overkill for a few tables, where `SYNC` or `CLONE` is simpler.

### Q: Exam trap: "Large workspace; assess readiness and bulk migrate, including to managed tables."
UCX.

## §22 SYNC

### Q: What is SYNC?
A SQL command that upgrades HMS tables to **UC external tables**, for one table or a whole schema. It can be rerun on a schedule to keep UC in step with HMS changes. The Catalog Explorer **upgrade wizard** runs SYNC under the hood.

### Q: How is it used?
```sql
SYNC TABLE main.sales.orders FROM hive_metastore.sales.orders SET OWNER `data-owners` DRY RUN;
SYNC TABLE main.sales.orders FROM hive_metastore.sales.orders SET OWNER `data-owners`;
SYNC SCHEMA main.sales FROM hive_metastore.sales;
SYNC TABLE main.sales.dim AS EXTERNAL FROM hive_metastore.sales.dim;   -- HMS *managed* table stored OUTSIDE DBFS root
```

### Q: Requirements?
- A storage credential and external location that cover the path, plus `CREATE EXTERNAL TABLE` on that location.
- A target UC schema you can create in.
- **Ownership** of the source HMS table or schema.
- If the target table already exists, you must own it too.

### Q: Common DRY RUN status codes?
| Code | Meaning / fix |
|---|---|
| `DRY_RUN_SUCCESS` | Can be upgraded |
| `DBFS_ROOT_LOCATION` | Table is in the DBFS root, which UC doesn't support. **Use DEEP CLONE.** |
| `HIVE_SERDE` | Hive SerDe tables aren't supported. Convert to Delta. |
| `EXTERNAL_TABLE_IN_MANAGED_LOCATION` | Path is under UC managed storage |
| `LOCATION_OVERLAP` / `MULTIPLE_EXT_LOCATIONS` | Path conflicts |

### Q: Advantages?
- Fast, SQL-only, and idempotent.
- `DRY RUN` checks before committing.
- Supports hybrid HMS and UC periods.

### Q: Disadvantages?
- **External tables only**, never managed.
- Can't handle DBFS-root managed tables.
- **Writes a bookkeeping table property to the source HMS table** (a new Delta commit). You can disable this with `spark.databricks.sync.command.disableSourceTableWrites`.

### Q: Exam trap: "Use SYNC to create UC managed tables from HMS managed tables in DBFS root."
Impossible: it returns `DBFS_ROOT_LOCATION`. Use `CREATE TABLE ... DEEP CLONE` (or CTAS), or UCX.

## §23 Master decision table — "if the scenario says X, pick Y"

| Scenario keyword | Answer |
|---|---|
| Can see the table in Catalog Explorer but can't query | Missing `USE CATALOG`/`USE SCHEMA`/`SELECT`; `BROWSE` is metadata-only |
| Org-wide discovery and access requests | `GRANT BROWSE ON CATALOG … TO \`account users\`` |
| Delegate grant management without changing owner | `MANAGE` |
| Read all current **and future** tables in a schema | `GRANT SELECT ON SCHEMA` + usage |
| ADLS behind a firewall, no secrets | Access Connector MI → storage credential |
| Governed raw files / replace mounts | Volume (external if files already exist) |
| Data must survive `DROP TABLE` | External table |
| Auto optimization and cleanup | Managed table |
| Row security on one table, same name | Row filter |
| Mask SSN except HR | Column mask + `is_account_group_member('hr')` |
| One rule for hundreds of tables by tag | ABAC policy + governed tags |
| Share filtered data | Dynamic view in a share |
| Prod catalog only from prod workspace | Workspace-catalog binding (ISOLATED) |
| Job independent of a person | Run as service principal; OAuth M2M |
| Partner on Databricks | D2D sharing, `USING ID` |
| Partner not on Databricks | Open sharing, token / activation link |
| Recipient needs CDF | Enable CDF, then `WITH HISTORY` |
| Who did what | `system.access.audit` |
| DBU cost by job or tag | `system.billing.usage` (+ `list_prices`) |
| Downstream impact | Column lineage |
| HMS external → UC quickly | `SYNC` (DRY RUN first) |
| HMS DBFS-root managed → UC managed | `DEEP CLONE` |
| Govern HMS in place during migration | HMS federation |
| Bulk assessment + migration | UCX |
