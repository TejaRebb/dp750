## 1. Delta table

### Q: What is a Delta table?
Parquet data files plus a `_delta_log/` transaction log in the table directory. The log is the source of truth: a file is part of the table only if the log says it is. That gives ACID transactions, snapshot isolation, time travel, schema enforcement and DML (`UPDATE`/`DELETE`/`MERGE`) on object storage. On Azure Databricks, Delta is the **default table format**: `CREATE TABLE t (...)` with no `USING` gives you Delta.

### Q: How is it used?
```sql
CREATE TABLE main.sales.orders (id BIGINT, amount DECIMAL(10,2), ts TIMESTAMP);
```
```python
df.write.saveAsTable("main.sales.orders")            # Delta by default
spark.read.table("main.sales.orders")
from delta.tables import DeltaTable
DeltaTable.forName(spark, "main.sales.orders")       # programmatic API (merge, vacuum, history, ...)
```

### Q: Advantages?
ACID on a data lake. Concurrent readers and writers (optimistic concurrency). Time travel and audit history. Schema enforcement and evolution. File-level statistics for data skipping. DML support. CDF. Works with batch and streaming alike.

### Q: Disadvantages / limitations?
Features that upgrade the protocol (DVs, column mapping, liquid clustering) lock out older or third-party readers. You need maintenance (OPTIMIZE/VACUUM) unless predictive optimization is on. Retention settings cost storage.

### Q: Managed vs external in Unity Catalog — why does it matter for this module?
**Predictive optimization and `CLUSTER BY AUTO` work only on UC managed tables.** UC managed shallow clones are also protected from source VACUUM, and managed tables get automatic file-size tuning.

### Q: Exam trap — "Create a Delta table" and the option list has `USING DELTA` vs no `USING` clause?
Both are correct on Databricks. Delta is the default, so don't eliminate an answer just because it omits `USING DELTA`.

## 2. Transaction log (`_delta_log`)

### Q: What is it?
An ordered series of JSON commit files (`000...0.json`, `000...1.json`, ...). Each commit records actions: `add`/`remove` file (each with a `dataChange` flag), metadata (schema, properties), protocol, and commit info. The JSON is periodically aggregated into **Parquet checkpoint** files, so readers don't replay every JSON. Databricks tunes the checkpoint frequency.

### Q: How are concurrent writes handled?
**Optimistic concurrency control.** A writer reads a snapshot, writes files, then tries to commit the next version. If a conflicting commit landed first, it retries or fails with a `Concurrent...Exception`. Isolation levels: `WriteSerializable` (default) and `Serializable`. **Row-level concurrency** (DVs + row tracking, the default with liquid clustering) reduces conflicts between writers touching different rows of the same files.

### Q: How long is the log kept?
`delta.logRetentionDuration`, default **30 days**. Old log files are removed **automatically after checkpoints**. VACUUM does **not** remove log files.

### Q: What is `dataChange` and why care?
`OPTIMIZE` writes add/remove actions with `dataChange=false`, so streaming readers ignore them. `RESTORE` writes `dataChange=true`, so downstream streams treat the restored files as new data and can produce **duplicates**.

### Q: Exam trap — "VACUUM cleans up old transaction log entries"?
False. VACUUM deletes **data** files only and skips any directory starting with `_`. Log cleanup is automatic, governed by `logRetentionDuration`.

## 3. Liquid clustering

### Q: What is liquid clustering?
A data layout technique that **replaces partitioning and ZORDER**. Data is organised by up to **4 clustering keys**. It's incremental: `OPTIMIZE` rewrites only data that isn't clustered yet. Keys can be changed **without rewriting existing data**. It's recommended for **all new tables**, including streaming tables and materialized views. GA for Delta in DBR 15.4 LTS+.

### Q: How is it used?
```sql
CREATE TABLE sales (id BIGINT, cust_id BIGINT, order_ts TIMESTAMP) CLUSTER BY (cust_id, order_ts);
CREATE TABLE sales2 CLUSTER BY (cust_id) AS SELECT * FROM sales;   -- CTAS: CLUSTER BY after name
CREATE TABLE sales3 LIKE sales;                                    -- copies clustering config
ALTER TABLE existing_unpartitioned CLUSTER BY (cust_id);           -- enable on existing
ALTER TABLE sales CLUSTER BY (region, order_ts);                   -- change keys (metadata only)
ALTER TABLE sales CLUSTER BY NONE;                                 -- turn off (no rewrite)
OPTIMIZE sales;                                                    -- incremental clustering
OPTIMIZE sales FULL;                                               -- recluster everything (DBR 16.0+)
DESCRIBE DETAIL sales;                                             -- clusteringColumns
```
```python
df.write.clusterBy("cust_id").saveAsTable("sales2")
df.writeTo("sales2").using("delta").clusterBy("cust_id").create()
DeltaTable.create(spark).tableName("t").addColumn("id","BIGINT").clusterBy("id").execute()
```

### Q: What does `CLUSTER BY AUTO` do?
Databricks picks (and later changes) the clustering keys from the table's historical query workload. A key change only happens when the predicted data-skipping savings outweigh the reclustering cost. **Requirements: UC managed table and predictive optimization** (DBR 15.4+). It runs asynchronously.
```sql
CREATE OR REPLACE TABLE t (a INT, b STRING) CLUSTER BY AUTO;
ALTER TABLE t CLUSTER BY AUTO;                       -- also works on a table with manual keys
ALTER TABLE t CLUSTER BY (c1, c2); ALTER TABLE t CLUSTER BY AUTO;   -- give hints first
```
```python
df.write.format("delta").option("clusterByAuto", "true").saveAsTable("t")   # create/overwrite only
```
Check it with `DESCRIBE TABLE` / `SHOW TBLPROPERTIES`: `clusterByAuto = true`.

### Q: What triggers clustering?
- `OPTIMIZE` (manual, or by predictive optimization).
- Clustering on write (`INSERT INTO`, CTAS/RTAS, `COPY INTO` from Parquet, append) happens **only above a size threshold**. For UC managed tables that's 64 MB with 1 key, up to 1 GB with 4 keys; non-UC tables have higher thresholds.
- Without predictive optimization, Databricks recommends scheduling `OPTIMIZE` every 1–2 hours on busy tables. Because clustering is incremental, these runs are cheap.

### Q: Advantages?
Flexible keys with no rewrite on change. Good for high-cardinality filters, skew, fast-growing tables, changing access patterns, and concurrent writers (row-level concurrency). No small-partition problem. Can cluster on struct fields (`CLUSTER BY (s.field)`).

### Q: Disadvantages / limitations?
- **Incompatible with partitioning and ZORDER** on the same table.
- At most 4 keys. On tables < 10 TB, more keys hurt single-column filter performance.
- Keys must have statistics (first 32 columns by default) and be supported types. No map, array or struct columns, only struct fields.
- It upgrades the protocol to reader 3 / writer 7 (no downgrade) and turns on DVs, row tracking and checkpoint v2 by default.
- The DataFrame API can set `clusterBy` only on create/overwrite, **not in append mode**.

### Q: Converting a partitioned table?
`ALTER TABLE t REPLACE PARTITIONED BY WITH CLUSTER BY (cols | AUTO)` (DBR 18.1+). With no column list, the partition columns become the clustering keys. Alternatives: CTAS/RTAS with `CLUSTER BY`. Migration guidance: use the old partition columns and ZORDER columns as keys. For a generated column (e.g. date derived from a timestamp), cluster on the **original** column instead.

### Q: What is hierarchical clustering?
DBR 17.1+. The property `delta.liquid.hierarchicalClusteringColumns = 'event_date,store_id'` gives priority to some keys. Every listed column must also be a clustering key. Order them from low to high cardinality, and keep high-cardinality columns as standard keys.

### Q: When to use / not use?
Use it for basically every new table, especially ones with high-cardinality filters, skew, growth, concurrent writes, or changing patterns. Don't add it if you must keep compatibility with old readers or clients that don't support writer v7.

### Q: Current adoption / what replaced what?
Liquid clustering is the recommended default and **replaces Hive-style partitioning and Z-ORDER**. `CLUSTER BY AUTO` further replaces manual key selection on UC managed tables.

### Q: How does it compare to partitioning and Z-ORDER?
| | Partitioning | Z-ORDER | Liquid |
|---|---|---|---|
| Change layout | Full rewrite | Rerun OPTIMIZE ZORDER | `ALTER ... CLUSTER BY`, no rewrite |
| Cardinality | Low only | Any | Any |
| Incremental | n/a | No (rewrites selected data) | **Yes** |
| Combine | + Z-order (on non-partition columns) | + partitioning | **Neither** |
| Concurrency | Writers isolated by partition | — | Row-level concurrency |

### Q: Exam trap — "After `ALTER TABLE t CLUSTER BY (new_col)` queries are not faster."
Existing files are **not rewritten** when keys change. Run `OPTIMIZE t FULL` to recluster existing data. Plain `OPTIMIZE` only clusters unclustered data.

### Q: Exam trap — "`CREATE OR REPLACE TABLE t AS SELECT ...` on an auto-clustered table."
Without `CLUSTER BY AUTO` in the replace statement, **auto clustering is turned off and the selected keys are lost**.

## 4. Partitioning

### Q: What is it?
Hive-style physical subdirectories per value of the partition column(s) (`PARTITIONED BY (date)`). Queries filtering on that column skip whole directories (partition pruning).

### Q: How is it used?
```sql
CREATE TABLE logs (msg STRING, log_date DATE) PARTITIONED BY (log_date);
```
```python
df.write.partitionBy("log_date").saveAsTable("logs")
```

### Q: Advantages?
Predictable pruning on a low-cardinality filter column. Concurrent writers can be isolated per partition. Partition-scoped `OPTIMIZE ... WHERE` and dynamic partition overwrites.

### Q: Disadvantages?
Static layout that needs a full rewrite to change. Over-partitioning leads to many small files and slow queries. Useless or harmful on high-cardinality columns. Partition columns must be top-level (no struct fields).

### Q: When to use / not use?
Microsoft guidance: **< 1 TB, don't partition. 1–100 TB, use liquid clustering instead. ≥ 100 TB, partitioning might help, but test liquid first.** Each partition should hold **≥ 1 GB**. Only partition low-cardinality columns (date, region). Unpartitioned tables already get **ingestion-time clustering**.

### Q: Current adoption?
Legacy. It has been replaced by liquid clustering for new tables. Managed Iceberg tables treat `PARTITIONED BY` as clustering keys.

### Q: Exam trap — "300 GB table, queries filter on `customer_id`; the team proposes `PARTITIONED BY (customer_id)`."
Wrong on both counts: the table is too small and the column's cardinality is too high. Use liquid clustering on `customer_id`.

## 5. Z-ORDER

### Q: What is it?
A multi-dimensional co-locality sort applied by `OPTIMIZE`. It improves min/max data skipping on the Z-ordered columns.

### Q: How is it used?
```sql
OPTIMIZE events WHERE event_date >= '2025-01-01' ZORDER BY (device_id, user_id);
```
```python
DeltaTable.forName(spark, "events").optimize().where("event_date='2025-01-01'").executeZOrderBy("device_id")
```

### Q: Advantages?
Works on high-cardinality columns. Can be combined with partitioning (it works within each partition).

### Q: Disadvantages?
Not incremental: each run rewrites the selected data. The effect weakens with each added column. It **can't use partition columns**, never crosses partition boundaries, and needs stats on the columns. **Predictive optimization never runs ZORDER.** It is **incompatible with liquid clustering**.

### Q: When to use?
Only on existing legacy (often partitioned) tables you can't migrate yet. For anything new, use liquid clustering.

### Q: Exam trap — "`OPTIMIZE t ZORDER BY (c)` on a liquid-clustered table."
Error. Liquid tables cluster through plain `OPTIMIZE`.

## 6. OPTIMIZE (compaction)

### Q: What is it?
Rewrites small files into larger ones (bin-packing). On liquid tables it also clusters the data, and with ZORDER BY it Z-orders. The log entries use `dataChange=false`. Readers are unaffected thanks to snapshot isolation, and streams that use the table as a source aren't affected.

### Q: How is it used?
```sql
OPTIMIZE t;                                -- compact (and cluster if liquid)
OPTIMIZE t WHERE date >= '2025-01-01';     -- partition predicate only (non-liquid)
OPTIMIZE t FULL;                           -- liquid: recluster all
OPTIMIZE t FULL WHERE event_date >= '2025-01-01';  -- liquid partial recluster (DBR 18.1+)
```
```python
DeltaTable.forName(spark, "t").optimize().executeCompaction()
```

### Q: Advantages / limitations?
Faster reads with fewer files. Bin-packing is **idempotent**, so a second run does nothing. It also applies DV soft deletes on a best-effort basis. It costs compute, and the old files stay on storage until VACUUM.

### Q: When to use?
Schedule it on tables without predictive optimization. For tables > 1 TB, schedule it even if auto compaction is on. With predictive optimization enabled, **disable your scheduled OPTIMIZE jobs**.

### Q: Exam trap — "OPTIMIZE ran, but storage went up."
Expected. The old files are only logically removed. VACUUM deletes them after the retention period.

## 7. Optimized writes & auto compaction

### Q: What are they?
- **Optimized writes**: shuffle data **before** writing so each partition gets fewer, larger files. Best for partitioned tables and many small inserts. Property `delta.autoOptimize.optimizeWrite`, session conf `spark.databricks.delta.optimizeWrite.enabled`.
- **Auto compaction**: **after** a successful write, synchronously compacts small files **on the same cluster**, only files not compacted before. Property `delta.autoOptimize.autoCompact` (`auto` recommended / `true` = 128 MB target / `legacy` / `false`), session conf `spark.databricks.delta.autoCompact.enabled`.
- `delta.targetFileSize` (e.g. `'100mb'`) is a best-effort target for OPTIMIZE, clustering, auto compaction and optimized writes. On UC managed tables with DBR 11.3+, only OPTIMIZE respects it.

### Q: How is it used?
```sql
ALTER TABLE t SET TBLPROPERTIES ('delta.autoOptimize.optimizeWrite'='true','delta.autoOptimize.autoCompact'='auto');
```

### Q: Advantages / disadvantages?
They reduce the small-file problem without scheduled jobs. The cost is extra write latency (shuffle, synchronous compaction), and they **don't fully replace OPTIMIZE**.

### Q: Compare with predictive optimization?
They're independent. Auto compaction runs synchronously on the writer's cluster. Predictive optimization runs OPTIMIZE/VACUUM/ANALYZE asynchronously on serverless compute, only for UC managed tables.

### Q: Exam trap — "Disable optimized writes for MERGE to speed it up."
You can't. Auto compaction and optimized writes are **always on for MERGE, UPDATE and DELETE**.

## 8. Predictive optimization

### Q: What is it?
A Databricks-managed service that automatically runs **OPTIMIZE, VACUUM, ANALYZE** (and REFRESH INDEX) on **Unity Catalog managed tables**. It decides what each table needs from its usage, runs on **serverless jobs compute** (billed under a serverless jobs SKU), and drives `CLUSTER BY AUTO` key selection.

### Q: How is it used?
```sql
ALTER CATALOG main ENABLE PREDICTIVE OPTIMIZATION;
ALTER SCHEMA main.sales DISABLE PREDICTIVE OPTIMIZATION;
ALTER TABLE main.sales.orders INHERIT PREDICTIVE OPTIMIZATION;
DESCRIBE TABLE EXTENDED main.sales.orders;   -- "Predictive Optimization: ENABLE (inherited from ...)"
```
The setting is inherited account → catalog → schema → table, and an explicit setting at a lower level overrides it. Changing it takes account admin at account level, or owner/`MANAGE` on the object.

### Q: Advantages?
No maintenance jobs to schedule, no wasted runs, statistics kept up to date for the cost-based optimizer. It's enabled by default for accounts.

### Q: Limitations?
UC **managed** tables only (not external). Requires the Premium plan, a supported region, and SQL warehouses or DBR 12.2 LTS+. It **never runs ZORDER**. Its VACUUM uses `deletedFileRetentionDuration` but never goes below **7 days**.

### Q: Exam trap — "Enable predictive optimization so the external table is vacuumed automatically."
It doesn't work on external tables. Schedule VACUUM yourself, or convert the table to a managed one.

## 9. Deletion vectors (DVs)

### Q: What are they?
A storage optimization. `DELETE`/`UPDATE`/`MERGE` write a small file marking rows in an existing Parquet file as removed (a soft delete), instead of rewriting the whole file. Readers apply the DVs at query time. This is **merge-on-read**, as opposed to copy-on-write.

### Q: How are they used?
```sql
ALTER TABLE t SET TBLPROPERTIES ('delta.enableDeletionVectors' = true);
CREATE TABLE t (...) TBLPROPERTIES ('delta.enableDeletionVectors' = true);
REORG TABLE t APPLY (PURGE);                 -- physically rewrite files that carry DVs
ALTER TABLE t DROP FEATURE deletionVectors;  -- remove the feature + downgrade (DBR 16.4+)
```
A workspace setting can auto-enable DVs on new tables (SQL warehouse / DBR 14.3+). Liquid clustering turns them on by default.

### Q: Advantages?
Much faster DML with less write amplification. **Photon predictive I/O for updates** relies on them, and they're a prerequisite for **row-level concurrency** (DBR 14.2+).

### Q: Disadvantages / limitations?
- Read overhead until the files are compacted.
- Enabling them **upgrades the protocol**, so clients without DV support can't read the table (old OSS Delta < 2.3, Iceberg v2 reads). Setting the property to `false` **doesn't downgrade the protocol**; `DROP FEATURE` does.
- No `GENERATE symlink_format_manifest` while DV files exist (purge first).
- On materialized views and streaming tables, DVs can only be set at `CREATE`.
- Reads need DBR 12.2+. Writes without Photon: DELETE 12.2+, UPDATE 14.1+, MERGE 14.3+.

### Q: How do soft deletes become physical?
`OPTIMIZE` (best effort), **`REORG TABLE ... APPLY (PURGE)`** (guaranteed for the affected files), or auto compaction (best effort). For **GDPR**: `DELETE` → `REORG TABLE t APPLY (PURGE)` → `VACUUM`. On big tables, `spark.databricks.delta.reorg.purgeMode = rows` restricts the purge to files with soft-deleted rows.

### Q: When to use / not?
Use them on tables with frequent DML, which is most tables on Databricks. Avoid them on tables that must be read by external engines without DV support.

### Q: Compare with copy-on-write?
Copy-on-write rewrites the full file on every change: fast reads, slow writes. DVs make writes fast and reads slightly slower until compaction.

### Q: Exam trap — "User data was DELETEd and VACUUM ran 8 days later, but the bytes are still in storage."
With DVs, the deleted rows can still sit in a **currently referenced** file. You must `REORG ... APPLY (PURGE)` first, then VACUUM after the retention period.

## 10. VACUUM

### Q: What is it?
It deletes data files that are **not referenced by the current table version** and were **logically removed more than the retention threshold ago** (default **7 days / 168 h**). Age is measured from removal in the log, not from the file's modification time. In FULL mode it also deletes untracked files in the table directory. It skips `_`-prefixed directories (so keep stream checkpoints in `_checkpoints`) but **does clean `_change_data` (CDF) files**.

### Q: How is it used?
```sql
VACUUM t;                       -- FULL mode, table retention (7d default)
VACUUM t RETAIN 240 HOURS;
VACUUM t DRY RUN;               -- list up to 1000 files, delete nothing
VACUUM t RETAIN 240 HOURS DRY RUN;
VACUUM t LITE;                  -- log-based (DBR 16.1+)
ALTER TABLE t SET TBLPROPERTIES ('delta.deletedFileRetentionDuration' = 'interval 30 days');
SET spark.databricks.delta.retentionDurationCheck.enabled = false;   -- allow < 168 h (dangerous)
```
```python
DeltaTable.forName(spark, "t").vacuum()       # default
DeltaTable.forName(spark, "t").vacuum(240)    # hours
```

### Q: Advantages?
Lower storage cost, and compliance: removed records become physically unrecoverable.

### Q: Disadvantages?
**You lose time travel (and RESTORE)** to versions whose files are gone. A retention that's too short can delete uncommitted files of long-running writers, which is why the 168 h safety check exists. FULL mode lists the entire directory, which is slow on big tables. On HMS/path-based tables it breaks shallow clones of the source.

### Q: What is VACUUM LITE vs FULL?
LITE finds the files to delete from the **transaction log** instead of listing storage, so it's faster on huge tables. It needs at least one successful VACUUM within the log retention window (30d), otherwise it errors with `DELTA_CANNOT_VACUUM_LITE` and you run `VACUUM FULL`. LITE **won't delete unreferenced files** such as leftovers from aborted transactions. FULL is the default.

### Q: When to use?
Regularly on all tables (predictive optimization does it for UC managed tables). Recommended compute: autoscaling 1–4 workers with 8 cores each, and a driver with 8–32 cores (the deletes run on the driver).

### Q: Newer behaviour to recognise?
DBR 18+ (and 2026 SQL warehouses): time travel beyond `deletedFileRetentionDuration` is blocked, that property can't exceed `logRetentionDuration`, and VACUUM ignores a non-zero `RETAIN` argument. Exam questions still assume "7-day data files / 30-day log".

### Q: Exam trap — "`VACUUM t RETAIN 24 HOURS` fails."
The `retentionDurationCheck` safety check blocks anything under 168 h. Only set `spark.databricks.delta.retentionDurationCheck.enabled=false` if no operation runs longer than the new retention.

### Q: Exam trap — "Disk cache returns data VACUUM already deleted."
That's possible: cached Parquet copies survive on the cluster. Restarting the cluster clears them.

## 11. Time travel

### Q: What is it?
Querying an earlier table version by version number or timestamp, using the log plus the still-existing data files. Use cases: audit, reproducing ML/report outputs, fixing mistakes, consistent snapshots.

### Q: How is it used?
```sql
SELECT * FROM t VERSION AS OF 12;
SELECT * FROM t TIMESTAMP AS OF '2025-03-01T10:00:00Z';
SELECT * FROM t TIMESTAMP AS OF date_sub(current_date(), 1);
SELECT * FROM t@v12;                    -- @v + version
SELECT * FROM t@20250301100000000;      -- @yyyyMMddHHmmssSSS
INSERT INTO t SELECT * FROM t TIMESTAMP AS OF date_sub(current_date(),1) WHERE userId = 111;  -- undo a delete
```
```python
spark.read.option("versionAsOf", 12).table("t")
spark.read.option("timestampAsOf", "2025-03-01").table("t")
spark.read.table("t@v12")
```

### Q: How far back can I go?
You need **both** the log (30d) and the data files (7d after removal), so the effective default is **7 days**. For 30 days, set `delta.deletedFileRetentionDuration = 'interval 30 days'`. Past 30, raise `logRetentionDuration` as well. Longer retention means more storage cost.

### Q: Limitations?
The version or timestamp **can't be a subquery**. Timestamp travel uses commit timestamps (in-commit timestamps make them robust to copying files). It isn't a backup strategy; use a deep clone for that.

### Q: Compare with RESTORE?
Time travel is **read-only** and leaves the current state unchanged. RESTORE makes an old state the current one.

### Q: Exam trap — "Set `delta.logRetentionDuration = 60 days` to allow 60-day time travel."
Not enough on its own. `deletedFileRetentionDuration` (7d) is the binding limit once VACUUM runs.

## 12. RESTORE

### Q: What is it?
It rolls a table back to an earlier version or timestamp **by writing a new commit**. History isn't rewritten: restoring v12 → v8 creates v13, which equals v8.

### Q: How is it used?
```sql
DESCRIBE HISTORY t;                         -- find the good version
RESTORE TABLE t TO VERSION AS OF 8;
RESTORE TABLE t TO TIMESTAMP AS OF '2025-03-01';
```

### Q: Advantages?
Fast, atomic undo of a bad write, with no data copy beyond the needed metadata. You can restore a restore, and restore a cloned table.

### Q: Limitations?
Requires **MODIFY**. **It fails if the target version's files were VACUUMed.** A partial restore is possible with `spark.sql.files.ignoreMissingFiles = true`. Its commits have `dataChange=true`, so downstream **streams may reprocess the files and produce duplicates**. It reports metrics such as `num_restored_files`, `num_removed_files`, `table_size_after_restore`.

### Q: Exam trap — "After RESTORE to v8, versions 9–12 are deleted."
False. They remain in history (and stay time-travelable within retention). RESTORE only adds a version.

## 13. DESCRIBE HISTORY / DESCRIBE DETAIL

### Q: What does each return?
- `DESCRIBE HISTORY t [LIMIT n]`: one row per commit, **newest first**, with `version, timestamp, userId, userName, operation, operationParameters, operationMetrics, readVersion, isolationLevel, isBlindAppend, job, notebook, clusterId, userMetadata, engineInfo`. Retained for `logRetentionDuration` (30d).
- `DESCRIBE DETAIL t`: one row of **current** metadata with `format, id, name, location, createdAt, lastModified, partitionColumns, clusteringColumns, numFiles, sizeInBytes, properties, minReaderVersion, minWriterVersion, tableFeatures`.
- `DESCRIBE TABLE EXTENDED t`: the schema plus UC info (owner, predictive optimization status, clustering).
- `SHOW TBLPROPERTIES t`: properties only.

### Q: Exam trap — "Which command shows how many rows the last MERGE updated?"
`DESCRIBE HISTORY` → `operationMetrics` (e.g. `numTargetRowsUpdated`). DETAIL only shows the current state. Auto compaction shows up in history as `OPTIMIZE` with `operationParameters.auto = true`.

## 14. Change Data Feed (CDF)

### Q: What is it?
Row-level change records between table versions (inserts, deletes, and updates as before/after images). It must be **enabled per table** (legacy CDF), and it **only captures changes from the commit where it was enabled onward**.

### Q: How is it used?
```sql
ALTER TABLE silver.customers SET TBLPROPERTIES (delta.enableChangeDataFeed = true);
SET spark.databricks.delta.properties.defaults.enableChangeDataFeed = true;   -- all new tables in session
SELECT * FROM table_changes('silver.customers', 5);            -- v5 → latest (inclusive)
SELECT * FROM table_changes('silver.customers', 5, 10);
SELECT * FROM table_changes('silver.customers', '2025-03-01 00:00:00', '2025-03-02 00:00:00');
```
```python
spark.read.option("readChangeFeed","true").option("startingVersion",5).option("endingVersion",10).table("silver.customers")
spark.read.option("readChangeFeed","true").option("startingTimestamp","2025-03-01 00:00:00").table("silver.customers")
(spark.readStream.option("readChangeFeed","true").option("startingVersion",76).table("silver.customers")
   .writeStream.option("checkpointLocation", ckpt).toTable("gold.customers"))
```

### Q: What extra columns does it add?
| Column | Values |
|---|---|
| `_change_type` | `insert`, `delete`, `update_preimage`, `update_postimage` |
| `_commit_version` | BIGINT table version |
| `_commit_timestamp` | commit timestamp |

An UPDATE yields **two rows** (pre + post). A table that already has columns with these names can't use CDF.

### Q: Batch vs streaming start?
**Batch requires** `startingVersion`/`startingTimestamp` (start and end are inclusive). **Streaming without a starting version** first emits the current snapshot as `insert` rows, then the changes. Use `startingVersion` to skip the snapshot, e.g. when recovering with a new checkpoint. Rate limits (`maxFilesPerTrigger`, `maxBytesPerTrigger`) apply.

### Q: Advantages?
Incremental ETL that processes only changed rows, audit of row changes, replication. It pairs with MERGE and AUTO CDC downstream.

### Q: Limitations?
- Changes from before enablement don't exist. Asking for a version before CDF was enabled is an **error**.
- Change files (`_change_data/`) follow table retention and **are VACUUMed**. CDF is **not a permanent history**: archive it to a table if you need one.
- A start beyond the latest commit errors with `timestampGreaterThanLatestCommit`, unless `spark.databricks.delta.changeDataFeed.timestampOutOfRange.enabled=true`.
- Storage and write overhead. Limitations across column-mapping and non-additive schema changes.

### Q: Current adoption?
**Automatic CDF** (DBR 19+, UC tables with row tracking or Iceberg v3) computes changes at read time with no property needed and the same APIs, and it can't be combined with legacy CDF. Exam questions still expect `delta.enableChangeDataFeed = true`.

### Q: Compare with DESCRIBE HISTORY and time travel?
HISTORY is commit-level metadata with no row data. Time-travel diffs (`EXCEPT` between versions) are expensive and lose the update semantics. CDF gives row-level changes efficiently.

### Q: Exam trap — "Build the latest state per key from CDF."
Filter out `update_preimage`, then take the row with the max `_commit_version` per key (window/row_number) before you MERGE. Otherwise the MERGE hits the multiple-match error.

## 15. MERGE

### Q: What is it?
An atomic upsert/delete of a target Delta table from a source, evaluated per row with `WHEN MATCHED`, `WHEN NOT MATCHED [BY TARGET]` and `WHEN NOT MATCHED BY SOURCE` clauses.

### Q: How is it used?
```sql
MERGE WITH SCHEMA EVOLUTION INTO tgt t
USING (SELECT * FROM src QUALIFY row_number() OVER (PARTITION BY id ORDER BY ts DESC) = 1) s
ON t.id = s.id
WHEN MATCHED AND s.op = 'D' THEN DELETE
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
WHEN NOT MATCHED BY SOURCE THEN DELETE;
```
```python
(DeltaTable.forName(spark,"tgt").alias("t")
   .merge(src.alias("s"), "t.id = s.id")
   .withSchemaEvolution()
   .whenMatchedDelete(condition="s.op = 'D'")
   .whenMatchedUpdateAll()
   .whenNotMatchedInsertAll()
   .whenNotMatchedBySourceDelete()
   .execute())
```

### Q: Clause rules?
- `MATCHED` allows UPDATE or DELETE. `NOT MATCHED` allows **INSERT only**. `NOT MATCHED BY SOURCE` allows UPDATE or DELETE and **can't reference source columns** (use literals or target columns).
- Within each clause type, clauses are evaluated in order, and **every clause except the last must have a condition**. Otherwise you get `NON_LAST_MATCHED_CLAUSE_OMIT_CONDITION`, or the `..._NOT_MATCHED_BY_SOURCE_...` equivalent.
- `UPDATE SET *` / `INSERT *` assume the source has all target columns. Without evolution, extra source columns are ignored and a target column missing from the source is an error. `* EXCEPT (c)` exists (DBR 12.2+).
- `WHEN NOT MATCHED BY TARGET` is an alias for `WHEN NOT MATCHED`.

### Q: What is the multiple-match error?
`DELTA_MULTIPLE_SOURCE_ROW_MATCHING_TARGET_ROW_IN_MERGE`: two or more source rows match the same target row and try to update it. **Fix: dedupe the source** (latest per key). The exception is an **unconditional DELETE**, which tolerates multiple matches. In DBR 15.4 and below, only the `ON` condition is considered for this check.

### Q: How does schema evolution work in MERGE?
Use `MERGE WITH SCHEMA EVOLUTION` (DBR 15.2+, per statement), `.withSchemaEvolution()` in Python, or the session setting `spark.databricks.delta.schema.autoMerge.enabled = true`. New source columns get added to the target through `*` actions. A target column missing from the source keeps its value on update and gets NULL on insert. The **`mergeSchema` writer option doesn't apply to MERGE**.

### Q: Advantages / disadvantages?
It's the standard way to do idempotent upserts, SCD1/SCD2 and CDC apply, and it benefits from DVs, low shuffle merge and Photon dynamic file pruning. It's the most expensive DML, it conflicts with concurrent writers on the same files (row-level concurrency mitigates that), and the source must be deduplicated.

### Q: Compare with INSERT OVERWRITE / replaceWhere?
MERGE is row-level and key-based. Overwrite and replaceWhere swap whole slices of data. For "replace this day's data entirely", replaceWhere is simpler and cheaper.

### Q: Exam trap — "Remove target rows that no longer exist in the full source snapshot."
`WHEN NOT MATCHED BY SOURCE THEN DELETE`. `WHEN NOT MATCHED THEN DELETE` is invalid syntax.

## 16. Schema enforcement vs schema evolution

### Q: What is schema enforcement?
Delta rejects writes whose schema doesn't match the table: extra columns or incompatible types. A source **missing** a nullable column is accepted, and the column is written as NULL.

### Q: What is schema evolution, and how is it used?
Letting the table schema change as part of a write:
```python
df.write.mode("append").option("mergeSchema","true").saveAsTable("t")          # add new columns
df.write.mode("overwrite").option("overwriteSchema","true").saveAsTable("t")   # replace schema (type change/rename/drop by rewrite)
spark.conf.set("spark.databricks.delta.schema.autoMerge.enabled","true")       # session-wide
```
```sql
INSERT WITH SCHEMA EVOLUTION INTO t SELECT ...;
ALTER TABLE t ADD COLUMNS (c INT);
```

### Q: mergeSchema vs overwriteSchema?
| | mergeSchema | overwriteSchema |
|---|---|---|
| Mode | append or overwrite | **overwrite only** |
| Adds columns | Yes | Yes |
| Type change / rename / drop | No (only safe upcasts) | Yes, **rewrites all data** |
| Combinable with `partitionOverwriteMode=dynamic` | — | **No** |

### Q: Advantages / disadvantages of evolution?
Pipelines survive upstream column additions. The downside: silently accepting columns can let garbage into curated layers, so keep enforcement on gold tables.

### Q: What about type widening?
`delta.enableTypeWidening = true` allows widening changes (e.g. INT → BIGINT) without a rewrite.

### Q: Exam trap — "Append fails with a schema mismatch because the DataFrame has a new column. Fix with minimal impact."
`.option("mergeSchema","true")`. `overwriteSchema` would replace data, and disabling enforcement isn't an option.

## 17. Column mapping

### Q: What is it?
It decouples logical column names from the physical Parquet column names, which makes **RENAME COLUMN and DROP COLUMN metadata-only** operations. It also allows spaces and `,;{}()\n\t=` in column names.

### Q: How is it used?
```sql
ALTER TABLE t SET TBLPROPERTIES ('delta.columnMapping.mode' = 'name');   -- existing table OK
CREATE TABLE t2 (id INT) TBLPROPERTIES ('delta.columnMapping.mode' = 'id');  -- id: create time only
ALTER TABLE t RENAME COLUMN old_name TO new_name;
ALTER TABLE t DROP COLUMN obsolete;
ALTER TABLE t DROP COLUMNS (c1, c2);
```

### Q: Modes?
`none` (default), `name` (new or existing tables), `id` (**must be set at creation**).

### Q: Advantages?
Instant rename and drop on huge tables, and raw CSV/JSON headers can be ingested without sanitising.

### Q: Disadvantages?
Protocol upgrade to **reader 2 / writer 5**, which older readers can't read. DROP COLUMN **doesn't delete the data**: purge with `REORG TABLE ... APPLY (PURGE)` + `VACUUM`. Streaming reads across a rename/drop need `schemaTrackingLocation`. Partition directories get random prefixes. Removing it (`mode='none'`) rewrites all files. `DROP FEATURE columnMapping` (DBR 15.4+) downgrades the protocol.

### Q: Compare with overwriteSchema?
Both achieve a rename or drop. Column mapping is metadata-only. overwriteSchema rewrites the full table.

### Q: Exam trap — "`ALTER TABLE t RENAME COLUMN a TO b` errors."
Column mapping isn't enabled. Set `delta.columnMapping.mode = 'name'` first.

## 18. CTAS, CREATE OR REPLACE, INSERT OVERWRITE, replaceWhere

### Q: What are the options and how do they differ?
| Command | Schema | History | Notes |
|---|---|---|---|
| CTAS `CREATE TABLE x AS SELECT` | From the query | New | Fails if the table exists |
| `CREATE OR REPLACE TABLE ... [AS SELECT]` | **Replaced** (schema, partitioning/clustering, properties as you specify) | **Kept**: old versions time-travelable | Atomic. Readers keep working. Preferred over DROP + CREATE |
| DROP + CREATE | New | **Lost** | Not atomic. Readers briefly see the table as missing |
| `INSERT OVERWRITE t SELECT` | **Kept**, mismatch fails | Kept | Keeps properties, constraints and layout. No `overwriteSchema` in SQL |
| `df.write.mode("overwrite")` | Kept unless `overwriteSchema` | Kept | |
| `replaceWhere` / `INSERT INTO t REPLACE WHERE pred SELECT` | Kept | Kept | Atomically replaces **only rows matching the predicate**, which can use any columns. By default, source rows outside the predicate cause an **error** (`replaceWhere.constraintCheck`). An empty source can delete rows |
| `INSERT INTO t REPLACE USING (cols) SELECT` | Kept | Kept | Dynamic overwrite by key equality (DBR 16.3+). Works on all compute. Recommended over `partitionOverwriteMode` |
| `partitionOverwriteMode=dynamic` | Kept | Kept | **Legacy**. Replaces only partitions present in the new data. SQL only on classic compute. Can't combine with `replaceWhere` or `overwriteSchema` |

### Q: How is replaceWhere used?
```python
(df.write.mode("overwrite")
   .option("replaceWhere", "order_date >= '2025-01-01' AND order_date < '2025-02-01'")
   .saveAsTable("sales"))
```
```sql
INSERT INTO sales REPLACE WHERE order_date >= '2025-01-01' AND order_date < '2025-02-01'
SELECT * FROM staged_jan;
```

### Q: When to use which?
- Full rebuild with a changed schema, keeping history: `CREATE OR REPLACE`.
- Full reload with the same schema: `INSERT OVERWRITE`.
- Reload one slice: `replaceWhere` or `REPLACE USING`.
- Row-level changes: MERGE.

### Q: Exam trap — "Replace the table and its schema while preserving the ability to query the old version for audit."
`CREATE OR REPLACE TABLE`. DROP + CREATE loses history.

### Q: Exam trap — "CREATE OR REPLACE kept my table properties / clustering"?
No. Anything you don't re-specify (clustering, `CLUSTER BY AUTO`, TBLPROPERTIES) is reset.

## 19. CLONE

### Q: What is it?
A copy of a Delta table at a given version. A **deep** clone copies the data and metadata. A **shallow** clone copies only the metadata and references the source's data files.

### Q: How is it used?
```sql
CREATE TABLE dev.sales SHALLOW CLONE prod.sales;
CREATE TABLE bkp.sales DEEP CLONE prod.sales;               -- plain CLONE = DEEP
CREATE OR REPLACE TABLE bkp.sales CLONE prod.sales;         -- incremental re-sync: copies only new files
CREATE TABLE ml.train_v15 CLONE prod.sales VERSION AS OF 15;
CREATE TABLE x SHALLOW CLONE prod.sales TIMESTAMP AS OF '2025-03-01';
```
```python
DeltaTable.forName(spark,"prod.sales").clone("dev.sales", isShallow=True, replace=False)
DeltaTable.forName(spark,"prod.sales").cloneAtVersion(15, "ml.train_v15", isShallow=False)
```

### Q: What's copied?
**Both types:** schema, partitioning, constraints and invariants, nullability, **TBLPROPERTIES**. **Deep clone only:** stream and COPY INTO metadata, so a stream writing to the source can continue on the clone. **Never copied:** **table history** (the clone starts its own), the table description, user commit metadata, **UC tags**.

### Q: Shallow vs deep?
| | Shallow | Deep |
|---|---|---|
| Data copied | No | Yes |
| Cost | Cheap, fast | Expensive |
| Source VACUUM | Breaks the clone for HMS/path tables (`FileNotFoundException`). UC managed: protected | Independent |
| Use | Short-term dev/test, trying a destructive change | Backup, DR, archival, ML snapshot, migration |

### Q: Limitations?
In UC you **can't `CREATE OR REPLACE` an existing shallow clone** (drop and create it again). Streaming tables and materialized views can't be the source or target of a clone. Changes to a clone never affect the source. Time travel on a clone uses the clone's own version numbers.

### Q: Compare with CTAS?
CTAS copies only the data and the schema from the query, so you must respecify partitioning, properties and so on. A clone carries the metadata and properties along, and deep clones can be synced incrementally.

### Q: Exam trap — "Cheapest way to test an UPDATE on prod data without touching prod."
`SHALLOW CLONE`. A deep clone works but costs far more. Time travel is read-only, so it can't be used to test an UPDATE.

## 20. Table properties (quick reference)

### Q: Which properties should I recognise instantly?
| Property | Default | Purpose |
|---|---|---|
| `delta.enableChangeDataFeed` | false | CDF |
| `delta.enableDeletionVectors` | workspace setting | DVs |
| `delta.deletedFileRetentionDuration` | `interval 7 days` | VACUUM threshold, time-travel window |
| `delta.logRetentionDuration` | `interval 30 days` | History retention |
| `delta.columnMapping.mode` | `none` | `name` / `id` |
| `delta.autoOptimize.optimizeWrite` | — | Optimized writes |
| `delta.autoOptimize.autoCompact` | — | Auto compaction (`auto`) |
| `delta.targetFileSize` | none | Target file size |
| `delta.dataSkippingNumIndexedCols` | 32 | Stats on the first N columns (`-1` = all) |
| `delta.dataSkippingStatsColumns` | none | Explicit stats columns (overrides N) |
| `delta.appendOnly` | false | Block UPDATE/DELETE |
| `delta.enableRowTracking` | — | Row-level concurrency, automatic CDF |

### Q: How are they set?
```sql
ALTER TABLE t SET TBLPROPERTIES ('delta.logRetentionDuration'='interval 60 days',
                                 'delta.deletedFileRetentionDuration'='interval 60 days');
ALTER TABLE t UNSET TBLPROPERTIES ('delta.enableChangeDataFeed');
SHOW TBLPROPERTIES t;
```
For session defaults on new tables, use `spark.databricks.delta.properties.defaults.<name without delta.>`.

### Q: Exam trap — "Clustering key column not in the first 32 columns."
Clustering and Z-order keys need statistics. Reorder the columns or set `delta.dataSkippingStatsColumns` / `dataSkippingNumIndexedCols`.

## 21. Final sweep: "if the question says X → answer Y"

| X | Y |
|---|---|
| Slow filters on a high-cardinality column | Liquid clustering on that column |
| Query patterns unknown or changing, UC managed table | `CLUSTER BY AUTO` |
| Keys changed, old data not reorganised | `OPTIMIZE t FULL` |
| Stop scheduling OPTIMIZE/VACUUM | Predictive optimization (UC managed only) |
| Small files from frequent appends | Auto compaction / optimized writes |
| Undo yesterday's bad write | `RESTORE TABLE ... TO VERSION AS OF` |
| Read an old state without changing anything | `VERSION AS OF` / `TIMESTAMP AS OF` / `@v` |
| 30-day time travel | `deletedFileRetentionDuration = 30 days` |
| Preview VACUUM | `VACUUM t DRY RUN` |
| VACUUM slow on a huge directory | `VACUUM t LITE` |
| Slow UPDATE/DELETE on big files | Deletion vectors |
| Physically remove soft-deleted rows | `REORG TABLE ... APPLY (PURGE)` then `VACUUM` |
| Only changed rows downstream | CDF (`table_changes`, `readChangeFeed`) |
| Delete target rows missing from the source | `WHEN NOT MATCHED BY SOURCE THEN DELETE` |
| Source has a new column during MERGE | `MERGE WITH SCHEMA EVOLUTION` |
| Append fails on an extra column | `mergeSchema = true` |
| Rename/drop a column without a rewrite | Column mapping `name` |
| Replace one month atomically | `replaceWhere` / `REPLACE WHERE` |
| Replace a table and its schema, keep history | `CREATE OR REPLACE TABLE` |
| Quick dev copy of prod | `SHALLOW CLONE` |
| Backup / DR that can resume prod's stream | `DEEP CLONE` |
