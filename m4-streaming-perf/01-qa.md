## §1 Structured Streaming (the engine itself)

### Q: What is Structured Streaming?
It is Spark's streaming engine built on the DataFrame/SQL API. A stream is treated as an unbounded table, and Spark incrementalizes the same query plan you would write for batch. There are two execution models. **Micro-batch** is the default: each trigger runs a small batch job and commits it. **Real-time mode** uses long-running tasks and processes each record as it arrives, giving sub-second latency. Fault tolerance comes from a replayable source, a checkpoint, and an idempotent or transactional sink. Delta and file sinks give exactly-once results. Kafka and `foreach` sinks are at-least-once.

### Q: How is it used?
```python
q = (spark.readStream.table("c.s.bronze")                 # or format("cloudFiles"), "kafka"
       .filter("amount > 0")
       .writeStream
       .option("checkpointLocation", "/Volumes/c/s/v/chk/silver")
       .trigger(availableNow=True)
       .toTable("c.s.silver"))
```

### Q: Advantages?
- You reuse batch code and the Catalyst optimizer.
- With Delta you get exactly-once results.
- The same code can run as an always-on stream or as a scheduled incremental batch (availableNow).
- Watermarks bound late data and state.

### Q: Disadvantages/limitations?
- Some batch operations are unsupported on streams: sort without aggregation in complete mode, most `limit`, multiple aggregations before DBR 13.3 chaining, and others.
- Stateful queries need careful tuning of watermarks, state store and partitions.
- AQE does not apply to streaming queries.

### Q: When to use / when NOT to use?
- Use it for incremental ingestion and transforms, CDC, near-real-time aggregates, and event correlation.
- Don't use it when the result must be fully recomputed whenever upstream changes. A materialized view does that for you.
- Don't use it when you want declarative orchestration with checkpoints managed for you. Use Lakeflow (Spark Declarative) Pipelines instead.

### Q: Current adoption / what replaced what?
- Structured Streaming replaced DStreams (Spark Streaming, RDD-based).
- Databricks positions **Lakeflow pipelines** (formerly DLT) for most new streaming work, and raw Structured Streaming in jobs when you need full control.
- Real-time mode replaces the experimental OSS continuous processing, which Azure Databricks does not support.

### Q: How does it compare to Lakeflow pipelines?
| | Structured Streaming in a job | Lakeflow pipeline |
|---|---|---|
| Checkpoints and triggers | you manage them | the pipeline manages them |
| Autoscaling | classic autoscaling scales streams down poorly | enhanced autoscaling |
| Control | full (foreachBatch, custom sinks) | declarative, with sinks / foreach_batch_sink |

### Q: Exam trap: "Run Structured Streaming in production on an all-purpose cluster with autoscaling"?
Wrong on both counts. Production streams go on **job compute**, scheduled as a Jobs **continuous** job, without autoscaling. If you need autoscaling, use Lakeflow pipelines.

## §2 Output modes

### Q: What are output modes?
They decide which rows of the result table are written to the sink on each trigger.

| Mode | Emits | Aggregations | State dropped |
|---|---|---|---|
| **append** (default) | only rows that will never change again | allowed **only with a watermark** | yes, after the watermark passes |
| **update** | rows changed since the last trigger | yes | yes, if a watermark is set |
| **complete** | the whole result table | **aggregations only** | **never** |

### Q: How is it used?
```python
agg.writeStream.outputMode("append").option("checkpointLocation", chk).toTable("c.s.gold")
```

### Q: Advantages of each?
- **Append** writes each result once and final. That suits downstream consumers that act once per row, such as notifications.
- **Update** gives the freshest partial values and the lowest latency for aggregates.
- **Complete** keeps the sink a full, consistent snapshot.

### Q: Disadvantages/limitations?
- **Append** output for aggregates is delayed by at least the watermark delay. A 1-hour watermark means at least 1 hour of delay.
- **Update** writes the same key many times, so the sink must handle overwrites. **The Delta sink does not support update mode.**
- **Complete** state grows forever and the sink is rewritten every batch, so it scales badly.

### Q: Which operators restrict the mode?
- Stream-stream joins support **append only**.
- Chained multiple stateful operators (DBR 13.3+) support append only.
- Dedup ignores the output mode.
- `(flat)mapGroupsWithState` and `transformWithState` emit by their own logic.
- Sorting is allowed only after an aggregation in complete mode.
- For stateless queries, all modes behave the same.

### Q: When to use / when NOT to use?
- Use append into Delta for final windowed results.
- Use update into Kafka, or into Delta through foreachBatch + MERGE, for live dashboards and feature serving.
- Avoid complete at scale. Databricks suggests a materialized view instead.

### Q: How do sinks compare?
- Kafka supports all three modes.
- Delta (and therefore every Unity Catalog managed table) supports **append + complete** only.

### Q: Exam trap: "Use outputMode('update') to write a streaming aggregate to a UC managed table"?
It fails, because the Delta sink has no update mode. The correct pattern is `foreachBatch` with `MERGE INTO` and `.outputMode("update")` on the writer.

### Q: Exam trap: "Aggregation in append mode without a watermark will emit nothing"?
No. The query fails at analysis time. Append with an aggregation requires a watermark.

## §3 Checkpoints

### Q: What is a checkpoint?
It is the directory (`checkpointLocation`) that holds a query's identity and progress:
- **offsets**: what each batch read
- **commits**: which batches reached the sink
- **state**: state store files and the state schema
- **metadata**: the query `id`

Configs such as `spark.sql.shuffle.partitions` are recorded in the offset log.

### Q: How is it used?
```python
.writeStream.option("checkpointLocation", "/Volumes/cat/sch/vol/chk/orders_silver")
```
With Unity Catalog the path must be in a UC external location or a volume. Never use driver-local storage.

### Q: Advantages?
Exactly-once recovery: a restart resumes from the last committed batch and reloads state.

### Q: Disadvantages/limitations?
- The checkpoint is tied to the query plan, so many changes require a new checkpoint.
- A new checkpoint means reprocessing from the start. For a Delta source that means the full snapshot, unless you set `startingVersion`/`startingTimestamp`. Those options are honoured **only for new checkpoints**.

### Q: Which changes are allowed on the same checkpoint?
| Change | Allowed? |
|---|---|
| filters/projections | generally yes |
| trigger interval | yes |
| `maxFilesPerTrigger`/`maxOffsetsPerTrigger` | yes |
| number/type of sources, Kafka topic, Auto Loader path | **no** (unless source naming is used) |
| grouping keys, aggregates, dedup keys, join type, state schema | **no** |
| sink type | **no** |
| state store provider (HDFS ↔ RocksDB) | **no** |
| `spark.sql.shuffle.partitions` (stateful) | **no effect**: it is fixed when the checkpoint is created. DBR 18 LTS+ adds on-demand state repartitioning, and DBR 18.0+ stateless queries can change it |

### Q: When to use a new checkpoint?
When you make an incompatible stateful/source/sink change, or when you deliberately want a full reprocess.

### Q: How does a query `id` compare to `runId`?
`id` persists across restarts because it is stored in the checkpoint. `runId` is new on every start.

### Q: Exam trap: "Two streaming writers to the same Delta table share one checkpoint to save storage"?
Never do this. Use **one checkpoint per query**. Sharing corrupts recovery and causes duplicates, skipped data or failed restarts.

### Q: Exam trap: "Changed shuffle partitions from 200 to 64, restarted, nothing changed. Why?"
The partition count is stored in the checkpoint. To apply the new count you need a new checkpoint, or DBR 18 LTS+ state repartitioning.

## §4 Triggers

### Q: What is a trigger?
It controls when micro-batches run and whether the query stops.

| Trigger | Syntax | Behaviour |
|---|---|---|
| default | none | next batch starts as soon as the previous one ends (≡ `processingTime='0 seconds'`) |
| fixed interval | `.trigger(processingTime="10 seconds")` | checks for data every interval |
| **AvailableNow** | `.trigger(availableNow=True)` | processes all data available at start **in multiple batches, honouring rate limits**, then stops |
| Once | `.trigger(once=True)` | one batch, then stops. **Deprecated in DBR 11.3+** |
| Continuous | `.trigger(continuous="1 second")` | **not supported on Azure Databricks** |
| Real-time | `.trigger(realTime="5 minutes")` | long-running batch with per-record processing and sub-second latency. The value is the batch/checkpoint duration, **not** the latency |

### Q: Advantages?
- **AvailableNow** on a schedule is cheapest because the cluster stops between runs.
- The **default** trigger gives the lowest micro-batch latency.
- A **processingTime** interval reduces storage-listing API calls.

### Q: Disadvantages/limitations?
- The default trigger makes many cloud-storage API calls, which costs money.
- Serverless notebooks and jobs support **only availableNow and once**. Anything else fails with `INFINITE_STREAMING_TRIGGER_NOT_SUPPORTED`.
- Asynchronous progress tracking is incompatible with availableNow/once.

### Q: When to use / when NOT to use?
- Use availableNow for SLAs of hours or daily.
- Use processingTime for seconds-to-minutes SLAs on classic job compute.
- Use real-time mode for sub-second operational work such as fraud detection.
- Don't use availableNow/once/continuous for low-latency operational streams.

### Q: Current adoption / what replaced what?
- `once` was replaced by `availableNow`.
- OSS continuous processing was replaced by real-time mode.
- For always-on serverless streaming, use a serverless Lakeflow pipeline in **continuous mode**, or a continuous job with availableNow.

### Q: How does availableNow compare to once?
Both process the backlog and stop. Once processes it as one single batch. AvailableNow splits it into rate-limited batches, so you get stable memory use and no giant first batch.

### Q: Exam trap: "Jobs 'continuous' schedule = continuous trigger"?
No. The Jobs continuous schedule means auto-restart with one active run, and it is recommended for always-on streams. It is unrelated to `trigger(continuous=...)`.

## §5 Watermarks

### Q: What is a watermark?
It is an event-time lateness threshold:
- Watermark = **max event time seen − delay**. It is computed at the end of a batch and applied in the next one.
- Records inside the threshold are **guaranteed** to be processed.
- Records later than the threshold **may** be dropped, but that is not guaranteed.
- State whose window end is older than the watermark is evicted.

### Q: How is it used?
```python
events.withWatermark("event_time", "10 minutes") \
      .groupBy(F.window("event_time", "5 minutes"), "device_id").count()
```
- Define the watermark **before** the stateful operator, on the **same column** the window uses.
- Reference the column by name (`"event_time"` or `F.col(...)`).
- SQL equivalent: `FROM t WATERMARK event_time DELAY OF INTERVAL 10 MINUTES` (DBR 12.0+).

### Q: Advantages?
It bounds state size and memory, and it enables append-mode aggregations and outer stream-stream joins.

### Q: Disadvantages/limitations?
- Late data beyond the threshold can be silently dropped.
- Longer delays mean more state and more output latency.
- There is one global watermark per query, not one per key.

### Q: How do multiple inputs behave?
Each input tracks its own watermark. The global watermark is the **min** of them by default (`spark.sql.streaming.multipleWatermarkPolicy=min`). Setting it to `max` lowers latency but **drops data from the slower stream**. A stalled input holds back the output of the whole query.

### Q: When to use / when NOT to use?
- Use watermarks on every event-time aggregation, dedup, and stream-stream join.
- In **complete** mode the watermark doesn't drop state, so it doesn't help there.

### Q: Exam trap: "Watermark on ingest_time, window on event_time"?
State is never cleaned up. The watermark and the window/dedup/join columns must match.

### Q: Exam trap: initial Delta snapshot drops records as "late"?
The snapshot is processed in file-modification order, which can push the watermark ahead of older event times. Set `withEventTimeOrder=true` (DBR 11.3+).

## §6 Windowed aggregations

### Q: What window types exist?
| Type | Function | Property |
|---|---|---|
| Tumbling | `F.window("ts", "1 hour")` | fixed size, no overlap, each row in exactly 1 window |
| Sliding | `F.window("ts", "6 hours", "1 hour")` | fixed size, overlapping. `slideDuration ≤ windowDuration`, and a row lands in several windows |
| Session | `F.session_window("ts", "30 minutes")` | dynamic size. The window closes after a gap with no events, and each new event extends it |

### Q: How is it used?
```python
(activity.withWatermark("ts", "1 hour")
   .groupBy("user_id", F.session_window("ts", "30 minutes"))
   .agg(F.sum("page_views").alias("pv")))
```
The window column is a struct `{start, end}`.

### Q: Advantages?
Event-time correctness for out-of-order data, and incremental state.

### Q: Disadvantages/limitations?
- Sliding windows multiply state by window/slide.
- Session windows keep sessions open until gap plus watermark.
- The time column must be `TimestampType`/`TimestampNTZType`.
- Durations can range from µs to days. Months are not allowed.

### Q: When to use which?
- Tumbling for hourly or daily totals.
- Sliding for rolling metrics ("last 6 h, refreshed hourly").
- Session for user activity bursts.
- Use `current_timestamp()` if you need processing-time windows.

### Q: Exam trap: "Rolling 15-min average updated every 5 min"?
That is a **sliding** window, `window(ts, "15 minutes", "5 minutes")`, not a session window.

## §7 Stateful operators & state store (dedup, transformWithState, RocksDB)

### Q: What are stateful operators?
Operators that keep intermediate data across batches: streaming aggregations, `distinct`, `dropDuplicates`, `dropDuplicatesWithinWatermark`, stream-stream joins, and custom ones (`transformWithState`, legacy `mapGroupsWithState`/`flatMapGroupsWithState`/`applyInPandasWithState`).

### Q: How is dedup used?
```python
# duplicates share the same event time -> include it in the keys so the watermark can clean up
df.withWatermark("ts", "1 hour").dropDuplicates(["event_id", "ts"])
# duplicates have different event/arrival times (producer retries)
df.withWatermark("ts", "10 hours").dropDuplicatesWithinWatermark(["event_id"])   # DBR 13.3 LTS+
```

### Q: How does dropDuplicates compare to dropDuplicatesWithinWatermark?
- `dropDuplicates` without a watermark keeps every key forever.
- With a watermark it only cleans up if the event-time column is part of the keys. That breaks dedup when duplicates carry different timestamps.
- `dropDuplicatesWithinWatermark` requires a watermark, dedups on the key alone, and guarantees removal of duplicates inside the threshold. Set the delay larger than the max gap between duplicates.

### Q: What is transformWithState?
It is the new arbitrary-stateful API, **DBR 16.2+**. You write a `StatefulProcessor` with:
- state variables: Value, List or Map state
- per-variable **TTL**
- processing-time and event-time **timers**
- initial state
- **state schema evolution**

It is available in Scala and Python (row-based `transformWithState`, and `transformWithStateInPandas`). It requires RocksDB.

### Q: Current adoption / what replaced what?
- transformWithState replaces `mapGroupsWithState`/`flatMapGroupsWithState`.
- Databricks still says to prefer the built-in operators (agg/dedup/join) when they fit.
- Use transformWithState for things like update-mode joins, joins after watermark expiry, top-K, or sessionization with custom expiry.

### Q: What is the RocksDB state store?
A state store provider that keeps active state in native memory and on local disk instead of the JVM heap, which avoids GC pauses with large state. It is the **default in DBR 17.3 LTS+**, along with changelog checkpointing. On older runtimes:
```python
spark.conf.set("spark.sql.streaming.stateStore.providerClass",
               "com.databricks.sql.streaming.state.RocksDBStateStoreProvider")
spark.conf.set("spark.sql.streaming.stateStore.rocksdb.changelogCheckpointing.enabled", "true")  # DBR 13.3+
```

### Q: Advantages of RocksDB + changelog checkpointing?
- Predictable memory and fewer GC pauses.
- Changelog checkpointing uploads only the changes, not full snapshots, so checkpoints are shorter and latency is lower.
- It is required for async state checkpointing and for transformWithState.

### Q: Limitations?
- You cannot switch the provider on an existing checkpoint.
- Changelog checkpointing *can* be toggled on an existing RocksDB stream, but it needs a restart and DBR 13.3+.
- With async state checkpointing, any checkpoint failure fails the query because there are no task retries.

### Q: Other stateful tuning recommendations?
- Use compute-optimized workers.
- Set shuffle partitions to **1–2× cluster cores** before the first run.
- Set `spark.sql.streaming.noDataMicroBatches.enabled=false` to skip empty batches. The catch: watermark-driven output then waits for new data.
- Enable state rebalancing on resize with `spark.sql.streaming.statefulOperator.stateRebalancing.enabled`.

### Q: Exam trap: "Large stateful stream has long GC pauses. Add driver memory?"
No. Use RocksDB with changelog checkpointing. State lives on the executors, not the driver.

## §8 Stream-static joins

### Q: What is a stream-static join?
A **stateless** join between a streaming DataFrame and a batch DataFrame, typically a fact stream with a slowly-changing dimension.

### Q: How is it used?
```python
spark.readStream.table("c.s.orders") \
     .join(spark.read.table("c.s.customers"), "customer_id", "left")   # stream on the left
```

### Q: Is the static side refreshed?
Yes, for Delta. Each micro-batch joins against the **latest valid version** of the static Delta table at the time that batch is processed. Dimension updates apply to *subsequent* batches only.

### Q: Advantages?
No watermark and no join state, so latency is low and the query is simple.

### Q: Disadvantages/limitations?
- Stream rows that were already processed are **not recomputed** when the dimension changes.
- Results are non-deterministic on replay if the dimension changed in between.
- Supported types: inner, left outer (stream on left), left semi. Right or full outer with the stream on the left is not supported.

### Q: When NOT to use?
When facts must always reflect the current dimension values. Use a materialized view, which recomputes joins, or restructure the pipeline.

### Q: How do Lakeflow pipelines compare?
- Triggered pipeline: the static side is the snapshot as of the start of the update.
- Continuous pipeline: the latest version is read on each update.

### Q: Exam trap: "The static Delta table is cached at query start and never refreshed"?
False. Each micro-batch reads the latest version.

## §9 Stream-stream joins

### Q: What is a stream-stream join?
A **stateful** join where both inputs are streams. Spark buffers rows from both sides until a match is possible or impossible. Supported types are inner, left/right/full outer, and left semi.

### Q: How is it used?
```python
imp = impressions.withWatermark("imp_time", "2 hours")
clk = clicks.withWatermark("click_time", "3 hours")
imp.join(clk, F.expr("""clk_ad_id = imp_ad_id AND
                        click_time >= imp_time AND
                        click_time <= imp_time + interval 1 hour"""), "leftOuter")
```

### Q: What is required?
- Output mode must be **append**.
- **Inner** joins: watermarks and a time-range condition are optional, but without them state is unbounded. Databricks recommends watermarks on both sides.
- **Outer** joins: a watermark and an **event-time range condition are mandatory**. Watermark both sides. The range condition must use the watermarked columns.

### Q: Advantages?
True event correlation, for example impression to click or order to payment, with bounded state.

### Q: Disadvantages/limitations?
- Unmatched outer rows (NULL-padded) are emitted **only after the watermark** proves no match can arrive, so output is delayed.
- No update mode.
- Changing the join type or keys requires a new checkpoint.

### Q: When to use transformWithState instead?
When you need update mode, joins after watermark expiry, many-to-many with custom expiry, or dynamic retention.

### Q: Exam trap: "Left outer stream-stream join shows no NULL rows after 5 min with a 1-hour watermark. Bug?"
Not a bug. Unmatched rows wait for the watermark plus the range condition to pass.

## §10 foreachBatch and idempotent writes

### Q: What is foreachBatch?
A sink that calls your function `(batch_df, batch_id)` once per micro-batch, so you can use any batch API: MERGE, multiple tables, JDBC, operations unsupported on streams.

### Q: How is it used (idempotent MERGE upsert)?
```python
APP_ID = "orders_silver_v1"                 # stable. Change it if the checkpoint is reset
def upsert(micro_df, batch_id):
    if micro_df.isEmpty(): return
    latest = (micro_df.withColumn("rn", F.row_number().over(
                Window.partitionBy("order_id").orderBy(F.desc("updated_at"))))
              .filter("rn = 1").drop("rn"))             # one source row per key
    latest.createOrReplaceTempView("updates")
    micro_df.sparkSession.sql("""
      MERGE INTO c.s.orders_silver t USING updates s ON t.order_id = s.order_id
      WHEN MATCHED AND s.updated_at > t.updated_at THEN UPDATE SET *
      WHEN NOT MATCHED THEN INSERT *""")
    (micro_df.write.option("txnAppId", APP_ID).option("txnVersion", batch_id)
       .mode("append").saveAsTable("c.s.orders_audit"))  # idempotent append

stream.writeStream.foreachBatch(upsert).outputMode("update") \
      .option("checkpointLocation", chk).start()
```

### Q: Advantages?
- Update-like upserts into Delta.
- One read, many sinks.
- Reuses existing batch connectors.

### Q: Disadvantages/limitations?
- **At-least-once**: a failed batch is replayed with the same `batch_id`, so each write must be idempotent.
- Multiple sinks run **serially**, which adds latency. Databricks recommends separate streams per sink.
- You must handle empty batches. For example, an `OPTIMIZE` on the source with nothing to compact produces an empty batch.
- With upstream stateful operators you must consume the whole batch DataFrame.
- Not compatible with continuous or real-time mode.
- MERGE re-reads its input, which inflates input-rate metrics. Cache or uncache the batch DataFrame to avoid this.

### Q: How do txnAppId/txnVersion work?
They are DataFrameWriter options on Delta writes. Delta records `(txnAppId, txnVersion)` and skips a write whose version it has already committed for that app ID. Bind `txnVersion` to `batch_id`. If you start a **new checkpoint**, batch IDs restart at 0, so you **must change `txnAppId`**. Otherwise new batches are silently skipped.

### Q: How do you make MERGE idempotent?
- Dedupe the micro-batch on the merge key. Multiple source rows matching one target row is a MERGE error.
- Use deterministic, newer-wins conditions.
- Use `micro_df.sparkSession` for SQL.

### Q: Exam trap: "Catch exceptions inside foreachBatch and continue"?
Databricks says to let errors propagate and let the orchestrator (Jobs) retry the whole batch. Swallowing errors risks data loss or partial writes.

## §11 Delta table as a streaming source (reader options)

### Q: What is it?
`spark.readStream.table(...)` incrementally reads newly committed Delta versions. By default it starts from the latest version, including the full current snapshot.

### Q: Which options matter?
| Option | Meaning | Default / gate |
|---|---|---|
| `maxFilesPerTrigger` | max new files per batch | **1000** |
| `maxBytesPerTrigger` | **soft** max bytes per batch | none |
| both | the first limit reached wins | |
| `skipChangeCommits` | ignore commits that update/delete existing rows. Appends only | **DBR 12.2 LTS+**, replaces `ignoreChanges` |
| `ignoreChanges` | legacy (≤ 11.3). Re-emits rewritten files, so **duplicates** | legacy |
| `ignoreDeletes` | legacy. Ignores **full partition drops only** | legacy |
| `startingVersion`/`startingTimestamp` | start point. Mutually exclusive, new checkpoints only | |
| `withEventTimeOrder` | event-time-ordered initial snapshot | DBR 11.3+ |
| `readChangeFeed` | stream CDF rows (insert/update_pre/post/delete) | CDF must be enabled |
| `failOnDataLoss` | `false` skips versions already cleaned from the log | true |
| Kafka `maxOffsetsPerTrigger` | Kafka rate limit | |

### Q: What happens when the source gets UPDATE/DELETE/MERGE/OVERWRITE?
By default the stream **fails**. You have four options:
- `skipChangeCommits`: simple, but changes are not propagated.
- **CDF**: propagates every change type. Databricks prefers it.
- Full refresh: new checkpoint plus rebuilding downstream.
- Materialized view.

### Q: Limitations?
- A source schema change fails the query. A restart usually fixes it.
- The stream must run within the source retention windows (7 days for VACUUMed files, 30 days for the log), or it fails with `DELTA_FILE_NOT_FOUND_DETAILED`.
- Never set `spark.sql.files.ignoreMissingFiles=true` as a workaround.

### Q: Exam trap: "GDPR deletes by user_email on a date-partitioned source break the stream. Use ignoreDeletes?"
No. ignoreDeletes only covers whole-partition drops. Use **skipChangeCommits**. If downstream must reflect the deletes, use CDF.

### Q: Exam trap: "availableNow ignores maxFilesPerTrigger"?
False. AvailableNow honours rate limits. Once processes everything in one batch.

## §12 Streaming monitoring

### Q: What tools exist?
- `StreamingQuery` handle: `lastProgress`, `recentProgress`, `status`, `id`/`runId`, `exception()`, `awaitTermination()`, `stop()`.
- `spark.streams.active`.
- `StreamingQueryListener`.
- Spark UI **Streaming** tab and the notebook progress dashboard (its Raw Data tab shows the JSON).

### Q: How is it used?
```python
q = df.writeStream.queryName("orders_silver").option("checkpointLocation", chk).toTable("t")
q.lastProgress["numInputRows"]; q.status["isDataAvailable"]

from pyspark.sql.streaming import StreamingQueryListener
class Health(StreamingQueryListener):
    def onQueryStarted(self, e): pass                       # keep non-blocking
    def onQueryProgress(self, e):                           # end of every micro-batch
        p = e.progress
        if p.processedRowsPerSecond < p.inputRowsPerSecond: print("falling behind")
    def onQueryIdle(self, e): pass                          # waiting for data
    def onQueryTerminated(self, e): pass
spark.streams.addListener(Health())
```

### Q: Which metrics matter?
- `numInputRows`, `inputRowsPerSecond`, `processedRowsPerSecond`. If processed is below input for a sustained period, the query is falling behind.
- `durationMs` (`addBatch`, `latestOffset`, `triggerExecution`).
- `eventTime.watermark`.
- `stateOperators[].numRowsTotal`/`memoryUsedBytes`.
- Source backlog: `numFilesOutstanding`, `numBytesOutstanding`.
- `observedMetrics` (from `df.observe`).

### Q: Limitations?
- Listener callbacks run on the driver listener thread for all queries, so heavy work there delays reporting. Buffer the data and write it from another thread.
- In Python and Scala, listeners need DBR 11.3+.
- On UC dedicated access, touching UC objects needs DBR 15.1+. Scala on standard access needs 16.1+.
- `onQueryProgress` fires only at the end of a batch. A very long batch emits neither progress nor idle events, but the query is still healthy.

### Q: How does lastProgress compare to a listener?
`lastProgress` is a pull for one query, used ad hoc. A listener is a push for every query in the session, used for alerting and exporting.

### Q: Exam trap: "Push per-batch metrics to an external monitoring tool"?
Use `StreamingQueryListener.onQueryProgress`. Polling `lastProgress` in a loop is not the answer.

## §13 Adaptive Query Execution (AQE)

### Q: What is AQE?
Runtime re-optimization at every shuffle or broadcast exchange, using actual statistics. It is **on by default** (`spark.databricks.optimizer.adaptive.enabled`; OSS name `spark.sql.adaptive.enabled`).

### Q: What does it do (4 features)?
1. Switches sort-merge join to **broadcast hash join** at runtime when one side is below `spark.databricks.adaptive.autoBroadcastJoinThreshold` (**30MB**). The static planner uses `spark.sql.autoBroadcastJoinThreshold` (10MB).
2. **Coalesces post-shuffle partitions** (`advisoryPartitionSizeInBytes` 64MB, `minPartitionSize` 1MB. Don't set `minPartitionNum`).
3. **Splits skewed partitions** in SMJ and shuffle hash joins. A partition counts as skewed if it is > 5× the median **and** > 256MB.
4. Propagates **empty relations**.

### Q: Advantages?
It fixes bad estimates (stale or missing stats, skew) without code changes and removes the need for many hints.

### Q: Disadvantages/limitations?
- It applies only to queries with an exchange or subquery, and **not to streaming queries**.
- It doesn't reorder joins. That needs stats and the CBO: `ANALYZE TABLE ... COMPUTE STATISTICS`, or predictive optimization.
- It never fixes skew in broadcast joins.
- It can't broadcast the left side of a LEFT OUTER join.
- A runtime broadcast happens only after both sides have been shuffled.

### Q: How do I see what AQE did?
- `AdaptiveSparkPlan isFinalPlan=true`.
- Coalescing shows as `CustomShuffleReader … Coalesced`.
- Skew handling shows as `SortMergeJoin … isSkew=true`.
- A changed join node means the strategy switched.
- `df.explain()` shows the initial and current plans. **SQL `EXPLAIN` shows only the initial plan** because it doesn't run the query.

### Q: Exam trap: "Disable AQE to make broadcast decisions predictable"?
No. Keep AQE on. Add an explicit broadcast hint where you know the size.

## §14 Shuffle partitions

### Q: What is `spark.sql.shuffle.partitions`?
The number of partitions after a shuffle (joins, aggregations). The default is **200**. Setting it to `auto` enables auto-optimized shuffle, which sizes the count from the plan and the input.

### Q: How is it used?
`spark.conf.set("spark.sql.shuffle.partitions", "auto")` for batch. Set an explicit value **before the first run** of a stateful stream, at 1–2× cluster cores.

### Q: Advantages / disadvantages of tuning?
- Too few partitions means big tasks and spill.
- Too many means scheduling overhead and tiny files.
- In batch, AQE coalescing reduces the pain of setting it too high.

### Q: How does batch compare to streaming?
Batch can change it freely. For a stateful stream it is frozen in the checkpoint.

### Q: Exam trap: "Stage spills heavily. Best first config change?"
Use auto-optimized shuffle (`auto`) or more partitions. Adding a broadcast hint for a large table is wrong.

## §15 Broadcast joins & join hints

### Q: What is a broadcast hash join?
The small side is shipped to every executor, so the large side is never shuffled.

### Q: How is it used?
```python
from pyspark.sql.functions import broadcast
fact.join(broadcast(dim), "k")
# SQL: SELECT /*+ BROADCAST(d) */ ...   aliases BROADCASTJOIN, MAPJOIN
```
Other join hints are `MERGE` (aliases SHUFFLE_MERGE, MERGEJOIN), `SHUFFLE_HASH` and `SHUFFLE_REPLICATE_NL`. If the two sides are hinted differently, the priority is **BROADCAST > MERGE > SHUFFLE_HASH > SHUFFLE_REPLICATE_NL**. Partition hints are `COALESCE`, `REPARTITION`, `REPARTITION_BY_RANGE` and `REBALANCE`. REBALANCE needs AQE and splits skewed output partitions.

### Q: Advantages?
No shuffle of the big side, and no join skew on the big side.

### Q: Disadvantages/limitations?
- The hint **overrides the threshold**, so broadcasting something too large can cause driver or executor OOM.
- The left side of a LEFT OUTER join can't be broadcast.

### Q: Do I still need hints with AQE?
Yes, when you know the sizes. A planned broadcast avoids shuffling both sides first. AQE respects hints.

### Q: How does a broadcast join compare to sort-merge?
Broadcast is best when one side is small. Sort-merge suits two large sides and is the one that gets AQE skew splitting. Photon compute tends to pick hash joins.

### Q: Exam trap: "Dimension of 25MB, but the plan shows SortMergeJoin at compile time"?
The static threshold is 10MB. Add a `broadcast()` hint, or raise `spark.sql.autoBroadcastJoinThreshold`. AQE might switch at runtime because 25MB is under 30MB, but only after the shuffle.

## §16 Data skew

### Q: What is skew?
A few partitions or keys hold most of the data. One or a few tasks then run far longer than the rest while the other cores sit idle.

### Q: How do I detect it?
In the Spark UI stage page → Summary Metrics, compare **Max** with the **75th percentile** task duration. If Max is at least 50% above the 75th percentile, suspect skew. On SQL warehouses and serverless, use the query profile.

### Q: What fixes exist (in order)?
1. **AQE skew join.** Check that it is an SMJ or SHJ, that the partition exceeds both thresholds, and that the join type allows splitting that side.
2. Lower `skewedPartitionFactor` / `skewedPartitionThresholdInBytes`.
3. **Salting.** Add a random suffix to the hot keys on the big side and replicate the small side across the suffixes, or use a two-stage aggregation.
4. **Liquid clustering** for skew in the stored table layout.
5. **REBALANCE** hint for skewed writes.

The legacy `SKEW` hint still exists, but Databricks says AQE is better.

### Q: Which side can AQE split?
| Join | Left | Right |
|---|---|---|
| INNER/CROSS | yes | yes |
| LEFT OUTER/SEMI/ANTI | yes | **no** |
| RIGHT OUTER | **no** | yes |
| FULL OUTER | **no** | **no** |

### Q: Exam trap: "Skewed right side of a LEFT OUTER join, AQE on, still one straggler"?
AQE can't split the right side of a left outer join. **Salt** the key, or restructure the join.

### Q: Exam trap: "Increase spark.sql.shuffle.partitions to fix single-hot-key skew"?
It doesn't help. One key still hashes to one partition.

## §17 Data skipping & file sizes

### Q: What is data skipping?
Delta stores per-file **min, max and null count** for the **first 32 columns** (`delta.dataSkippingNumIndexedCols`) and prunes files at query time.

### Q: How is it tuned?
```sql
ALTER TABLE t SET TBLPROPERTIES ('delta.dataSkippingStatsColumns' = 'event_date,customer_id');
ALTER TABLE t ALTER COLUMN long_json_col AFTER last_indexed_col;  -- long strings out of first 32
ALTER TABLE t CLUSTER BY (customer_id);                           -- liquid clustering
OPTIMIZE t;                                                       -- compaction / clustering
```
DBR 14.3+ lets you change the stats columns and recompute existing stats.

### Q: Advantages?
Much less I/O for selective filters, with no index maintenance.

### Q: Disadvantages/limitations?
- Stats cost something at write time, especially on long strings.
- Stats are useless if the data in each file isn't clustered on the filter column.

### Q: How does liquid clustering compare to partitioning and Z-order?
- **Liquid clustering** is Databricks' recommendation for new tables. You can change keys without rewriting data, and it handles high cardinality and skew well.
- **Partitioning** only makes sense for tables over about 1 TB with partitions of at least 1 GB. Otherwise you get small files.
- **Z-order** (`OPTIMIZE … ZORDER BY`) is the legacy approach and can't be combined with liquid clustering.

### Q: What controls file size?
- `OPTIMIZE` for compaction.
- **Auto compaction**: runs after a successful write, synchronously, on the writing cluster.
- **Optimized writes**: bin-packs before writing. Best for partitioned tables.
- `delta.targetFileSize`. On UC managed tables with DBR 11.3+, only OPTIMIZE respects it.
- Predictive optimization runs OPTIMIZE, VACUUM and ANALYZE automatically on UC managed tables.

### Q: Exam trap: "Frequent filter column is column #40; queries scan everything"?
It has no stats. Move the column into the first 32, raise `dataSkippingNumIndexedCols`, or list it in `dataSkippingStatsColumns`.

### Q: Exam trap: "Streaming with 1-second triggers on a low-volume source makes tiny files"?
Lengthen the trigger interval or use availableNow, and enable auto compaction.

## §18 Caching

### Q: What caches exist?
| | **Disk cache** (formerly "Delta cache"/DBIO) | **Spark cache** (`cache`/`persist`/`CACHE TABLE`) |
|---|---|---|
| Where | local SSD on workers | executor memory (by storage level) |
| What | Parquet files, including Delta | any DataFrame/RDD/subquery, any format |
| Trigger | automatic on first read | manual |
| Staleness | **auto-invalidated** when files change | stale until unpersist/REFRESH |
| Enable | on by default on SSD/cache-accelerated worker types; `spark.databricks.io.cache.enabled` | always |

SQL warehouses also have a **query result cache**: local plus remote, 24 h, invalidated when the table is updated. `SET use_cached_result=false` is only for benchmarking.

### Q: How is it used?
- Disk cache: pick a storage-optimized or SSD worker type.
- Spark cache: `df.persist(); …; df.unpersist()`.

### Q: Advantages / disadvantages?
- The disk cache is transparent, consistent and uses no heap. It uses at most half the local SSD.
- The Spark cache can hold computed intermediates, but it competes for memory, goes stale, and is lost when a worker is decommissioned.

### Q: When to use / not?
- Use the disk cache for repeated reads of Delta or Parquet. Databricks says to avoid the Spark cache for that.
- Use the Spark cache for an expensive intermediate reused several times in one job, for example the batch DataFrame in a foreachBatch that feeds several writes.

### Q: Current adoption / what replaced what?
- "Delta cache" was renamed to disk cache.
- `CACHE SELECT` is **ignored** in DBR 14.2+ and on SQL warehouses.
- Serverless `df.cache()` behaves differently from classic.

### Q: Exam trap: "Analysts re-query the same Delta tables; add df.cache() in each notebook"?
Wrong. Use the disk cache through SSD worker types, or a SQL warehouse with its result cache.

## §19 Photon

### Q: What is Photon?
Databricks' native **C++ vectorized** execution engine. It processes columnar batches with SIMD and has no JVM GC. Catalyst still plans the query, and Photon executes the operators it supports.

### Q: How is it enabled?
- Always on for **SQL warehouses, serverless compute and serverless pipelines**.
- On classic all-purpose and job compute (DBR 9.1 LTS+), it is on by default through the **"Use Photon Acceleration"** checkbox.
- Through the Clusters or Jobs API you must set `runtime_engine: "PHOTON"`. The Pipelines API uses `photon: true`.

### Q: What does it accelerate?
- SQL and DataFrame scans, filters, joins (hash joins) and aggregations.
- Columnar shuffle.
- Delta/Parquet writes, including MERGE, UPDATE, DELETE, INSERT and CTAS. Wide tables benefit especially.
- **Stateless** streaming: Delta, Parquet, CSV, JSON, Kafka and Kinesis sources, writing to Delta or Parquet sinks.
- Features that require Photon: predictive I/O, and dynamic file pruning in MERGE/UPDATE/DELETE.

### Q: What does it NOT accelerate?
**UDFs** (Python, Scala, pandas), **RDD APIs**, **Dataset typed APIs**, and **stateful streaming**. It also gives no benefit for queries under about 2 seconds. When Photon hits unsupported work, it **transparently falls back** to Spark for the rest of that operation, and results stay correct.

### Q: Disadvantages?
Photon instances use a **different (higher) DBU rate**, so check that it is cheaper overall per job and not just faster.

### Q: How do I verify Photon use?
- Spark UI SQL DAG: Photon operators are **orange** and Spark operators blue.
- Query profile: shows the % of task time in Photon. Photon operators appear purple.

### Q: Exam trap: "Enabled Photon; Python-UDF-heavy job barely improved. Why?"
UDFs aren't supported, so those stages fall back to Spark. Rewrite the UDFs with built-in functions.

## §20 Compute types & settings

### Q: What compute types exist and when do I use each?
| Type | Use | Notes |
|---|---|---|
| **All-purpose** (classic) | interactive development | highest DBU rate. Set auto-termination. Never for production streams |
| **Job compute** | scheduled production jobs | DBU rate much lower than all-purpose. Ephemeral and isolated. Multitask jobs can share a job cluster |
| **Serverless** (notebooks/jobs) | most workloads, no infrastructure to manage | streaming is **availableNow only** |
| **SQL warehouse** (serverless/pro/classic) | SQL, BI, dashboards | Photon on. **Max clusters = concurrency**, size = per-query power |
| **Lakeflow pipeline compute** | declarative ETL and streaming | enhanced autoscaling |

### Q: How does autoscaling behave, and what are its limits?
- Optimized autoscaling (Premium) goes from min to max in at most 2 steps. It scales down after 40 s of under-use on job compute and 150 s on all-purpose.
- It has limitations **scaling down Structured Streaming**. Don't enable it for streaming jobs. Use Lakeflow enhanced autoscaling instead, which is the default on new pipelines and always on for serverless pipelines.
- Never combine it with `spark.dynamicAllocation.enabled`.
- It is not available for spark-submit.

### Q: What are pools?
Idle, ready VMs that reduce cluster start and autoscale time. Idle pool instances cost **no DBUs** but you still pay the VM cost. Use an on-demand pool for the driver.

### Q: What are compute policies?
Admin rules that restrict or fix compute settings: node types, max workers, auto-termination, required tags, runtime, T-shirt sizes. They are the governance and cost-control answer.

### Q: What about spot instances (Azure Spot VMs)?
- Workers can be spot. The **driver is always on-demand** (`first_on_demand` ≥ 1).
- `availability` is `SPOT_AZURE`, `ON_DEMAND_AZURE` or `SPOT_WITH_FALLBACK_AZURE`.
- `spot_bid_max_price = -1` means the lowest price.
- Enable decommissioning (`spark.decommission.enabled`, `spark.storage.decommission.*`) to migrate shuffle and RDD blocks on eviction.
- Pros: cheaper. Cons: evictions slow jobs down. Not for tight SLAs.

### Q: Exam trap: "Cheapest compute for a nightly production notebook"?
Job compute or serverless jobs, not all-purpose.

### Q: Exam trap: "BI users queue at 9 am on a SQL warehouse"?
Raise **max clusters** to add concurrency. A bigger warehouse size doesn't fix queuing.

## §21 Spark UI & Query Profile diagnosis

### Q: What is the diagnosis workflow?
Jobs timeline → longest job → longest stage (Input/Output/Shuffle read/write, task count) → skew and spill → I/O-bound → other causes.

### Q: How do I read the symptoms?
| Symptom | Means | Fix |
|---|---|---|
| Max task ≥ 1.5× p75 | skew | AQE skew, salting, clustering, REBALANCE |
| Spill (memory/disk) shown in stage details | execution memory exhausted in shuffle/join/sort/agg | shuffle partitions `auto`/more, bigger-memory nodes, fewer larger workers for heavy shuffles, fewer/narrower columns, **smaller streaming batches** (maxFiles/BytesPerTrigger) |
| stage with 1 task | no parallelism (e.g. non-splittable gzip, `coalesce(1)`, window without partitionBy) | repartition, splittable input |
| big Input, slow | I/O bound | skipping, clustering, disk cache |
| slow with little I/O | small files, slow UDFs, Cartesian/exploding join | compaction, built-in functions, fix the join |
| gaps between jobs | driver-side work (Python, collect, listing) | move work to executors |
| executors lost / exit 137 | OOM (driver: collect/toPandas; executor: skew) | limit collects, fix skew |

SQL DAG node times are **cumulative executor time**, not wall clock.

### Q: What is the query profile?
The execution view for **SQL warehouses and serverless**, where there is no Spark UI. It shows the operator tree with rows, time, memory, spill and pruning (files/bytes read vs pruned), the % of time in Photon, and performance insights such as DATA_SPILL.

### Q: How does the Spark UI compare to the query profile?
The Spark UI is for classic all-purpose and job compute. The query profile is for SQL warehouses and serverless.

### Q: Exam trap: "Max task 20 min, median 30 s, no spill. Add workers?"
More workers won't help, because one straggler task still bounds the stage. The cause is skew, so fix the skew.
