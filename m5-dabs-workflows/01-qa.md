## 1. Declarative Automation Bundles (DABs)

### Q: What is it?
It is an infrastructure-as-code tool built into the Databricks CLI. One project folder holds source (notebooks, .py, wheels) **plus** YAML (or Python) definitions of Databricks resources: jobs, Lakeflow pipelines, dashboards, schemas, volumes, apps, experiments, models. The CLI validates, deploys, and runs that folder against a **target** workspace.

### Q: Current naming / what replaced what?
**Declarative Automation Bundles** is the new name for **Databricks Asset Bundles**. The rename is non-breaking: the command is still `databricks bundle`, and `databricks.yml` is unchanged. Related renames: Workflows → **Lakeflow Jobs**, DLT → **Lakeflow Spark Declarative Pipelines**, Repos → **Git folders**. Bundles are Databricks' recommended CI/CD tool. They replace hand-rolled REST/CLI deploy scripts and the older dbx tool.

### Q: How is it used?
```bash
databricks bundle init default-python      # scaffold
databricks bundle validate                 # check YAML + resolve vars
databricks bundle deploy -t dev            # create/update resources
databricks bundle run -t dev my_job        # run by RESOURCE KEY
databricks bundle destroy -t dev           # tear down
```

### Q: Advantages?
- Code **and** job/pipeline config live together in Git, so they are reviewed and versioned together.
- The same definition deploys to dev, staging, and prod with per-target overrides.
- Built-in dev isolation: user-scoped paths, name prefix, paused schedules.
- It builds artifacts such as wheels.
- It runs as a service principal in CI.
- Templates help standardize projects.

### Q: Disadvantages / limitations?
- A YAML learning curve.
- State lives in the workspace, so renaming bundle, target, or workspace orphans resources.
- Resources edited in the UI drift until the next deploy overwrites them. Prod-mode resources can't be edited in the UI.
- Some resource types are limited when deployer != `run_as` (only jobs and pipelines).

### Q: When to use / when NOT?
- **Use** for any multi-environment, team, or CI/CD project.
- **Not needed** for a one-off notebook or ad hoc exploration.
- If you have **no CI/CD tool at all** and only need code versioned, a production Git folder is the lighter alternative.

### Q: How does it compare to Git folders, Terraform, and the REST API?
| | Bundles | Git folders | Terraform provider | REST API/CLI scripts |
|---|---|---|---|---|
| Versions code | yes | yes | no (refs code) | no |
| Versions job/pipeline config | **yes** | **no** | yes | DIY |
| Multi-env promotion | targets | manual pull per folder | workspaces/vars | DIY |
| Best for | data/AI project CI/CD | dev collaboration, code-only deploy | workspace/infra provisioning (UC, clusters policies, networking) | edge automation |

### Q: Exam trap: "The company is moving to Declarative Automation Bundles. What must change in existing databricks.yml files?"
**Nothing.** The rename is cosmetic. Any answer that requires migrating YAML or switching CLI commands is wrong.

## 2. `databricks.yml` structure

### Q: What is it?
It is the single required root config file of a bundle. Other YAML files are merged in with `include`.

### Q: How is it used?
```yaml
bundle:
  name: sales_etl                 # required; part of bundle identity
include:
  - resources/*.yml               # globs relative to databricks.yml
variables:
  catalog: { default: dev_catalog }
workspace:
  host: https://adb-111.11.azuredatabricks.net
artifacts:
  default: { type: whl, build: uv build --wheel, path: . }
resources:
  jobs:
    sales_job:                    # RESOURCE KEY (bundle run / ${resources.jobs.sales_job.id})
      name: sales-job             # display name
      tasks:
        - task_key: ingest
          notebook_task: { notebook_path: ./src/ingest.ipynb }
targets:
  dev:  { mode: development, default: true }
  prod: { mode: production, workspace: { host: https://adb-222.22.azuredatabricks.net } }
```

### Q: What are the top-level mappings?
| Key | Holds |
|---|---|
| `bundle` | `name` (required), `git`, `cluster_id`, `deployment.lock` |
| `include` | other config files |
| `variables` | custom variables |
| `workspace` | `host`, `root_path`, `file_path`, `artifact_path`, `profile`, `sync_mode` |
| `artifacts` | builds (`type: whl/jar/tgz`, `build`, `path`, `files`, `dynamic_version`) |
| `resources` | jobs, pipelines, dashboards, schemas, volumes, clusters, apps... |
| `targets` | per-environment overrides |
| `run_as` | identity for runs |
| `permissions` | top-level ACL (`CAN_VIEW`, `CAN_RUN`, `CAN_MANAGE`) |
| `sync` | include/exclude/paths of synced files |
| `presets` | deployment presets |

### Q: How are relative paths resolved?
Relative to the **YAML file that declares them**, not relative to `databricks.yml`. A job in `resources/job.yml` therefore points to `../src/nb.ipynb`.

### Q: What does `workspace.sync_mode` do?
- `overwrite` (default): files are uploaded to `file_path`.
- `in-place`: source-linked, so resources reference workspace source directly. Only for deploys **from the workspace**, and the default for dev deploys from the workspace.
- `immutable` (Private Preview): a read-only snapshot, so files can't change during a run.

### Q: Advantages / limitations of splitting into `include` files?
- **Advantage:** small per-resource files make clean PR diffs.
- **Limitation:** path-relativity mistakes are the number-one deploy error.

### Q: Exam trap: the resource key vs `name`?
`databricks bundle run` takes the **resource key** (`sales_job`), not the display `name` (`sales-job`). In dev mode the display name becomes `[dev alice] sales-job`, but the key is unchanged.

### Q: Exam trap: can `workspace.host` be `${var.host}`?
**No.** Custom variables can't be used for workspace auth fields (`host`, `profile`, ...). Set `host` literally per target.

## 3. Targets

### Q: What is a target?
A named deployment environment under `targets:` (dev, staging, prod). Its settings override or merge with the top-level ones.

### Q: What can a target set?
`default`, `mode`, `workspace` (`host`, `root_path`), `run_as`, `variables`, `resources` (merged with top-level; `permissions` lists combine), `presets`, `permissions`, `git` (`branch`), `cluster_id`, `artifacts`, `sync`.

### Q: How is a target selected?
In order: `-t <name>`, then the `DATABRICKS_BUNDLE_TARGET` env var, then the target with `default: true`.

### Q: Advantages?
- One bundle covers every environment, which is Databricks' recommendation: one bundle per team/domain covering dev/stg/prod, **not** one bundle per environment.

### Q: Disadvantages?
- Heavy per-target resource overrides make the effective config hard to read. Use `bundle validate -t prod --output json` to see the merged result.

### Q: When to create separate bundles instead?
When products, ownership or permission boundaries, lifecycles, or independent rollback differ. Model inter-bundle dependencies in CI/CD, not by merging bundles.

### Q: Exam trap: two teams' bundles deploy to the same prod workspace with the same `bundle.name`, both deployed by the same CI service principal. What happens?
They **interfere**, because the identity (deployer + bundle name + target) is identical. Give them distinct bundle names or root_paths.

## 4. Deployment modes (development vs production) and presets

### Q: What are deployment modes?
`targets.<t>.mode: development | production` is an optional bundle of default behaviors for pre-prod and prod.

### Q: What does `mode: development` do?
- Prefixes every resource (except files and notebooks) with `[dev ${workspace.current_user.short_name}]` and adds a `dev` tag to jobs and pipelines.
- **Pauses all schedules and triggers.** Unpause per job with `schedule.pause_status: UNPAUSED` or `continuous.pause_status: UNPAUSED`.
- **Enables concurrent runs** on all jobs. Opt out per job with `max_concurrent_runs: 1`.
- Sets Lakeflow pipelines to `development: true`.
- **Allows `--cluster-id` / `cluster_id`** to override all cluster definitions with one interactive cluster.
- **Disables the deployment lock.** Re-enable with `bundle.deployment.lock.enabled: true`.

### Q: What does `mode: production` do?
- Validates that pipelines have `development: false`.
- Validates that the current Git branch equals `git.branch` if one is set. Override with `--force`.
- Recommends a `run_as` SP. **Without an SP** it also validates that `artifact_path`, `file_path`, `root_path`, and `state_path` aren't user-specific, and that `run_as` and `permissions` are set.
- **Forbids `--cluster-id` / `cluster_id` overrides.**
- Resources can't be edited in the UI.

### Q: What are presets and how do they compare to modes?
Presets are fine-grained knobs under `targets.<t>.presets`:

| Preset | Effect |
|---|---|
| `name_prefix` | resource name prefix |
| `tags` | tags on taggable resources (not `schema`) |
| `trigger_pause_status` | `PAUSED` or `UNPAUSED` for all triggers. **Forced PAUSED in development mode** |
| `jobs_max_concurrent_runs` | default for all jobs |
| `pipelines_development` | true/false |
| `artifacts_dynamic_version` | auto-version wheels |
| `source_linked_deployment` | **deprecated**, use `workspace.sync_mode` |

**Precedence:** individual resource setting > preset > mode.
```yaml
targets:
  prod:
    mode: production
    presets: { name_prefix: 'prod_', tags: { cost_center: fin } }
```

### Q: Advantages / disadvantages of modes?
- **Advantage:** safe defaults in one line.
- **Disadvantage:** dev-mode "surprises", such as a schedule that never fires or runs that overlap.

### Q: When NOT to use `mode: development`?
For a shared staging or integration target where schedules must actually run and names must be stable. Use no mode, or `production` with presets.

### Q: Exam trap: "After `bundle deploy -t dev` the nightly schedule never ran." Why?
Dev mode **paused** it, and that is by design. The fix is `pause_status: UNPAUSED` on that job. A `trigger_pause_status: UNPAUSED` preset doesn't work, because dev mode forces PAUSED.

### Q: Exam trap: a preset says `jobs_max_concurrent_runs: 20` and the job says `max_concurrent_runs: 5`. Effective value?
**5.** The resource setting beats the preset.

## 5. Variables and substitutions

### Q: What is a custom variable?
A deploy-time placeholder declared under `variables:` and referenced as `${var.<name>}`.
```yaml
variables:
  catalog:
    description: UC catalog
    default: dev_catalog
  wh_id:
    lookup: { warehouse: 'Shared Serverless' }   # name -> ID at deploy
  etl_cluster:
    type: complex                                # ONLY valid type value
    default: { spark_version: 15.4.x-scala2.12, node_type_id: Standard_DS3_v2, num_workers: 2 }
```

### Q: Which object types support `lookup`?
`alert`, `cluster`, `cluster_policy`, `dashboard`, `instance_pool`, `job`, `metastore`, `notification_destination`, `pipeline`, `query`, `service_principal`, `warehouse`. It is an **error** if 0 or more than 1 object has that name.

### Q: How are variable values set, and in what precedence?
First match wins:
1. `--var="k=v"`
2. Env var `BUNDLE_VAR_k`
3. `.databricks/bundle/<target>/variable-overrides.json`
4. `targets.<t>.variables.k`
5. `default`

With no default and no value supplied, validate/deploy **fails**.

### Q: What are substitutions?
Built-in `${...}` references: `${bundle.name}`, `${bundle.target}` (**not** the deprecated `${bundle.environment}`), `${workspace.host}`, `${workspace.current_user.userName}`, `${workspace.current_user.short_name}`, `${workspace.root_path}`, `${workspace.file_path}`, `${resources.jobs.<key>.id}`, `${resources.pipelines.<key>.name}`.

### Q: How do `${}` and `{{}}` compare?
| | `${var.x}` / `${bundle.target}` | `{{job.run_id}}` / `{{tasks.t.values.k}}` |
|---|---|---|
| Resolved | **deploy time** by the CLI | **run time** by the Jobs service |
| Changes require | redeploy | nothing; it varies per run |

### Q: Advantages / limitations?
- **Advantages:** environment-specific config without duplicating YAML, and `lookup` avoids hard-coded IDs.
- **Limitations:** values are baked in at deploy, `type` only accepts `complex`, and vars can't be used for auth fields.

### Q: When to use variables vs job parameters vs `base_parameters`?
- Changes **per environment**: bundle variable.
- Changes **per run**: job parameter, which can take `default: ${var.x}`.
- Per task, and the job has no job parameters: `base_parameters`.

### Q: Exam trap: `databricks bundle run my_job --var="catalog=prod"` still processes `dev_catalog`. Why?
Variables are resolved at **deploy**, so `run` executes the already-deployed definition. Make `catalog` a job parameter and use `--params catalog=prod`.

### Q: Exam trap: `type: string` on a variable?
Invalid. Only `complex` is allowed, and a complex variable with a scalar default fails validation.

## 6. Bundle identity, root_path, deployment state

### Q: What defines a bundle's identity?
`root_path`, which defaults to `/Workspace/Users/${workspace.current_user.userName}/.bundle/${bundle.name}/${bundle.target}`. So identity = **deployer + bundle name + target** (in a workspace).

### Q: How does deploy decide create/update/delete?
A **state file** in the workspace tracks resource **IDs**, not names:
- In config and not deployed: create.
- Deployed: update.
- **Removed from config: deleted on the next deploy.**
- Changing the bundle name, target, or workspace means old resources are **forgotten**, so they are orphaned and stay running.

### Q: How do you adopt an existing UI-created job?
`databricks bundle generate job --existing-job-id <id>` writes the YAML, then `databricks bundle deployment bind <resource_key> <job_id>` links it.

### Q: Where should prod deploy?
A folder with ACL-restricted write access owned by the deploying SP, set via an explicit `root_path` on the prod target. **Not `/Workspace/Shared`**, because every user can write there.

### Q: Exam trap: a developer deletes a job's YAML block "to stop deploying it" and redeploys. Result?
The job is **deleted** from the workspace.

### Q: Exam trap: renaming `bundle.name` and redeploying?
New copies of every resource are created, and the old ones are orphaned, not removed.

## 7. run_as and permissions

### Q: What is `run_as`?
The identity that deployed jobs and pipelines **run as**, separate from the identity that **deploys**. It can be top-level or per target.
```yaml
targets:
  prod:
    run_as:
      service_principal_name: 9f0c1a2b-....   # SP APPLICATION ID (GUID)
```

### Q: Which fields are allowed and what are the rules?
| Field | Rule |
|---|---|
| `user_name` | Non-admins can set only **their own** email |
| `service_principal_name` | **Application ID**, and you need the `servicePrincipal/user` role on it |
| `group_name` | **Only** inside a job or pipeline resource's own `run_as`. **Not** top-level or target |

### Q: Limitations?
- Deployer != run_as: **only jobs and pipelines** are supported.
- `run_as` + a model serving endpoint in the bundle gives an error.

### Q: Advantages of an SP run identity?
Runs survive people leaving or role changes, follow least privilege, and get a stable owner.

### Q: How are permissions declared?
- Top-level `permissions:` levels are `CAN_VIEW`, `CAN_RUN`, `CAN_MANAGE`.
- Per resource you can use the resource's own levels, for example jobs: `CAN_VIEW`, `CAN_MANAGE_RUN`, `CAN_MANAGE`, `IS_OWNER`.
- Top-level and target-level resource permissions **combine**.

### Q: Exam trap: `service_principal_name: etl-prod-sp` (display name)?
Wrong. It must be the application ID GUID.

## 8. Bundle CLI

### Q: Which commands and flags matter?
| Command | Purpose / key flags |
|---|---|
| `bundle init [template]` | `default-python`, `default-sql`, `dbt-sql`, `mlops-stacks`, or a custom template path/URL |
| `bundle validate` | `-t`, `--var`, `--output json` (shows resolved values) |
| `bundle plan` | preview changes |
| `bundle deploy` | `-t`, `--var`, `--force` (skip git-branch check), `--force-lock`, `--auto-approve`, `--fail-on-active-runs`, `-c/--cluster-id` (dev only) |
| `bundle run [KEY]` | `--params k=v` (job params), `-- --k=v` (job/notebook params), `--only a,+b,c+`, `--restart`, `--no-wait`; pipelines: `--full-refresh-all`, `--full-refresh t`, `--refresh t`, `--refresh-all`, `--validate-only`; `-- <cmd>` runs a script with bundle auth |
| `bundle destroy` | **permanent**; `--auto-approve`, `--force-lock`; protect with `lifecycle.prevent_destroy: true` |
| `bundle summary` | identity plus resource deep links |
| `bundle generate job|pipeline|dashboard` | YAML from an existing resource |
| `bundle deployment bind` | link a key to an existing ID |
| `bundle schema` | JSON schema |

### Q: How is `--only` used?
`databricks bundle run my_job --only +task_b+` runs task_b plus everything upstream (`+` prefix) and downstream (`+` suffix). This starts a **new** run.

### Q: Typical sequences?
```bash
databricks bundle validate && databricks bundle deploy && databricks bundle run sales_job   # dev loop
databricks bundle validate -t prod && databricks bundle deploy -t prod --auto-approve       # CI
```

### Q: Exam trap: you edit the notebook locally and run `bundle run`. Is the old code executed?
Yes. With the default `overwrite` sync mode, `run` executes the last **deployed** files. Run `deploy` first.

### Q: Exam trap: `--params` on a job that has only task-level `base_parameters`?
**Error.** Job params require job-level `parameters`. Conversely, task params on a job that has job params also fail.

## 9. Authentication and CI/CD pipelines

### Q: Which auth methods exist and when is each used?
| Method | Use | Config |
|---|---|---|
| OAuth **U2M** | humans, local dev | `databricks auth login --host <url>` (browser; saves a profile) |
| OAuth **M2M** (Databricks SP secret) | automation | `DATABRICKS_HOST`, `DATABRICKS_CLIENT_ID`, `DATABRICKS_CLIENT_SECRET` |
| Microsoft Entra SP (secret) | Azure automation | `DATABRICKS_HOST`, `ARM_TENANT_ID`, `ARM_CLIENT_ID`, `ARM_CLIENT_SECRET` |
| Azure CLI | ADO `AzureCLI@2` (`useGlobalConfig: true`) | `DATABRICKS_HOST` |
| **Workload identity federation (OIDC)** | GitHub Actions, ADO, GitLab; **recommended** | federation policy on the SP, so there are no secrets |
| Managed identity | self-hosted Azure agents | `ARM_USE_MSI=true`, `ARM_CLIENT_ID` |
| PAT | legacy | avoid |

### Q: How does GitHub Actions with WIF look?
```yaml
permissions: { id-token: write, contents: read }   # id-token REQUIRED for OIDC
jobs:
  deploy:
    environment: prod                     # matches policy subject ...:environment:prod
    runs-on: ubuntu-latest
    env:
      DATABRICKS_AUTH_TYPE: github-oidc
      DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST }}
      DATABRICKS_CLIENT_ID: ${{ vars.DATABRICKS_CLIENT_ID }}  # SP app ID, not a secret
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main
      - run: databricks bundle deploy -t prod
```

### Q: How does Azure DevOps look?
- Use an **Azure Resource Manager service connection**, preferably with workload identity federation.
- Install the CLI via `curl -fsSL https://raw.githubusercontent.com/databricks/setup-cli/main/install.sh | sh`.
- Run bundle commands inside `AzureCLI@2`, or export `ARM_*` with `addSpnToEnvironment` for client-secret auth.
- The SP must be added to the workspace with permissions.

### Q: What is the recommended pipeline?
PR → `bundle validate` + unit tests → `deploy -t staging` + integration run → merge to `main` → `deploy -t prod` as an SP, with `run_as` an SP.

### Q: Advantages / disadvantages of WIF?
- **Advantages:** no secret to store or rotate, and scoped by repo, branch, or environment.
- **Disadvantages:** the policy subject must match the token `sub` **exactly**. GitHub changed the `sub` format for repos created after 15 Jul 2026 (numeric IDs).

### Q: Exam trap: "most secure way for a pipeline to authenticate, no stored credentials"?
Workload identity federation. A PAT and an M2M client secret are both stored secrets.

### Q: Exam trap: U2M in a nightly CI pipeline?
Wrong. It needs an interactive browser login.

## 10. Git folders (formerly Repos)

### Q: What is it?
A visual Git client and API in the workspace: clone, branch, commit/push, pull, merge/rebase, conflict resolution, diff.

### Q: How is it used in dev?
Each developer clones into `/Workspace/Users/<email>/` and works on **their own branch**, then opens a PR. Switching the branch of a **shared** Git folder switches it for everyone using it.

### Q: How is it used for prod without bundles?
- An admin creates a **production Git folder** outside user folders.
- Users get **Can Run**, and only SPs/admins can edit.
- Automation keeps it current: CI calls the Repos API (`repos.update(id, branch="main")`), or a scheduled job does.

### Q: Advantages?
Native Git UX in the notebook UI, and zero extra tooling.

### Q: Limitations?
- Only **code** is versioned. Job/pipeline config, schedules, and compute are not.
- Sparse checkout can't be disabled once enabled.
- Sparse checkout doesn't work for ADO repos over 4 GB.

### Q: How does it compare to bundles?
Git folders give you version control for code. Bundles give you version control **and deployment** of code plus resource config. They're complementary: you can author and deploy bundles from inside a Git folder (needs workspace files and serverless).

### Q: Exam trap: "jobs must be reproducible across workspaces including schedule and cluster settings, using Git folders only". Enough?
No. You need bundles, because Git folders don't version job config. Also, `git_source` / `source: GIT` inside bundles is **not recommended**.

## 11. Lakeflow Jobs

### Q: What is it?
The Databricks orchestrator, formerly Workflows. A job is a DAG of **tasks** plus compute, triggers, parameters, notifications, and permissions. The UI is **Jobs & Pipelines**.

### Q: Minimum job?
A unique name, ≥1 task, and compute (serverless, job cluster, or all-purpose). A schedule is optional, since you can run it manually.

### Q: Advantages?
- Native DAG with conditional/loop tasks.
- Many trigger types.
- Repair runs.
- Serverless.
- System tables for monitoring, and 60-day run history.

### Q: Disadvantages?
- Cross-job dependencies are limited to Run Job tasks or job-completion triggers (Beta).
- Run history is kept only 60 days, so export it if you need longer.

### Q: How does it compare to Azure Data Factory / Airflow calling Databricks?
- Jobs is native: task values, repair, serverless, and table/file triggers.
- External orchestrators suit cross-platform pipelines but lose those features. They typically call `run-now` and can use a production Git folder.

### Q: Exam trap: run history retention?
**60 days** for jobs and pipelines.

## 12. Task types

### Q: Which task types exist and how are they parameterized?
| Task | YAML key | Key fields | Params |
|---|---|---|---|
| Notebook | `notebook_task` | `notebook_path`, `base_parameters`, `warehouse_id` | key-value → widgets |
| Python script | `spark_python_task` | `python_file`, `parameters` | JSON array → argv |
| Python wheel | `python_wheel_task` | `package_name`, `entry_point`, `parameters` or `named_parameters` | positional or keyword |
| SQL | `sql_task` | `warehouse_id` + `query`/`file`/`dashboard`/`alert` | key-value → `:param` |
| Pipeline | `pipeline_task` | `pipeline_id`, `full_refresh` | |
| dbt | `dbt_task` | `commands`, `project_directory`, `warehouse_id` | |
| Run Job | `run_job_task` | `job_id`, `job_parameters` | key-value |
| If/else | `condition_task` | `op`, `left`, `right` | |
| For each | `for_each_task` | `inputs`, `task`, `concurrency` | |
| JAR / Spark submit | `spark_jar_task` / `spark_submit_task` | | JSON array |
| Dashboard | `dashboard_task` | `dashboard_id`, `warehouse_id` | |

### Q: How is a wheel task used?
```yaml
- task_key: score
  python_wheel_task: { package_name: sales, entry_point: main, named_parameters: { date: '{{job.start_time.iso_date}}' } }
  libraries: [ { whl: ../dist/*.whl } ]           # classic compute
  # serverless instead: environment_key: default   (REQUIRED for wheel/script/dbt on serverless)
```

### Q: When wheel vs notebook?
- **Wheel:** packaged, unit-tested, versioned library code. Build it via bundle `artifacts`.
- **Notebook:** exploratory or presentation-heavy steps.

### Q: How does Run Job compare to a single big job?
- Run Job reuses another job, with its own permissions, cluster, and history.
- A cost: it counts toward the workspace concurrent Run Job limit.

### Q: Exam trap: a pipeline task in a job with `max_concurrent_runs: 5`?
The job is capped to **1** concurrent run, because a pipeline runs one update at a time.

## 13. Dependencies and `run_if`

### Q: What is it?
`depends_on` defines DAG edges. `run_if` decides whether a task runs given its upstream outcomes.
```yaml
- task_key: cleanup
  depends_on: [ { task_key: transform } ]
  run_if: ALL_DONE
```

### Q: What are the six conditions?
| `run_if` | Runs when | If unmet → |
|---|---|---|
| `ALL_SUCCESS` (**default**) | all deps succeeded | `Upstream failed` |
| `AT_LEAST_ONE_SUCCESS` | ≥1 succeeded | `Upstream failed` |
| `NONE_FAILED` | none failed **and** ≥1 ran | `Upstream failed` |
| `ALL_DONE` | all finished, any outcome | always runs |
| `AT_LEAST_ONE_FAILED` | ≥1 failed | `Excluded` |
| `ALL_FAILED` | all failed | `Excluded` |

### Q: What evaluation rules matter?
- Upstream **Excluded** counts as **success**. **Upstream failed** and **Upstream canceled** count as **failed**.
- If all deps are Excluded, the task is Excluded, and this cascades down a chain.
- Canceling propagates downstream, but failure-handling tasks still run.
- A disabled parent: `ALL_DONE` still runs, while `ALL_SUCCESS` and `ALL_FAILED` don't.

### Q: How is job status computed?
From **leaf** tasks:
- **Succeeded**: all tasks succeeded.
- **Succeeded with failures**: some tasks failed but every leaf succeeded. This counts as **success** for notifications.
- **Failed**: ≥1 leaf failed.

### Q: When to use each?
- `ALL_DONE`: cleanup or teardown, always.
- `AT_LEAST_ONE_FAILED`: alert, rollback, or compensation.
- `AT_LEAST_ONE_SUCCESS`: proceed if any source landed.
- `NONE_FAILED`: after branches where some may be Excluded.

### Q: Exam trap: the job has `transform → cleanup (ALL_DONE)`, `transform` fails, cleanup succeeds. Job status and failure email?
"Succeeded with failures", and **no on_failure email**. Fix it with a task-level notification on `transform`, or an `AT_LEAST_ONE_FAILED` leaf that raises.

### Q: Exam trap: the alert task has `AT_LEAST_ONE_FAILED` and everything succeeded. Is the alert task "failed"?
No. It is **Excluded** (skipped), which counts as success.

## 14. If/else and For each tasks

### Q: What is the If/else task?
A `condition_task` that compares two operands. Downstream tasks pick a branch with `outcome`.
```yaml
- task_key: has_rows
  depends_on: [ { task_key: ingest } ]
  condition_task: { op: GREATER_THAN, left: '{{tasks.ingest.values.row_count}}', right: '0' }
- task_key: transform
  depends_on: [ { task_key: has_rows, outcome: 'true' } ]
```
- Ops in YAML: `EQUAL_TO`, `NOT_EQUAL`, `GREATER_THAN`, `GREATER_THAN_OR_EQUAL`, `LESS_THAN`, `LESS_THAN_OR_EQUAL`. The UI shows `== != > >= < <=`.

### Q: Limitations of If/else?
- Needs no cluster, but has **no retries and no notifications**.
- `outcome` is valid only on a dependency that points at a condition task.
- The branch not taken is **Excluded**.

### Q: What is For each?
It runs a **nested task** once per element of `inputs`, with optional `concurrency`.
```yaml
- task_key: per_table
  for_each_task:
    inputs: '{{tasks.list_tables.values.tables}}'    # or '["a","b"]' or {{tasks.sql_t.output.rows}}
    concurrency: 4
    task:
      task_key: per_table_iter
      notebook_task: { notebook_path: ../src/load.ipynb, base_parameters: { table: '{{input}}' } }
```
- Use `{{input.<field>}}` for object or SQL-row elements.

### Q: Limitations of For each?
- SQL output used as `inputs` is capped at 1,000 rows / 48 KB and kept 7 days.
- A pipeline task inside For each runs **1 iteration at a time**.
- Aggregated task values are an array of at most about 48 KB.

### Q: How does For each compare to `dbutils.notebook.run` in a loop?
For each is declarative, shows per-iteration status, and supports repair and concurrency control. Use the notebook loop only when the logic is too dynamic for Jobs.

### Q: Exam trap: reading values set inside For each iterations downstream?
Reference the **nested** task key (`{{tasks.per_table_iter.values.k}}`). You get a JSON array ordered by iteration, with `null` for iterations that didn't set it.

## 15. Task values

### Q: What are they?
Small JSON-serializable values (≤48 KiB) passed between tasks of the **same run** through `dbutils.jobs.taskValues`.

### Q: How are they used?
```python
dbutils.jobs.taskValues.set(key="row_count", value=df.count())   # in task "ingest"
# downstream config (preferred):  '{{tasks.ingest.values.row_count}}'
n = dbutils.jobs.taskValues.get(taskKey="ingest", key="row_count", debugValue=10)  # code (discouraged)
```

### Q: Advantages?
They pass data-dependent control values (counts, lists, flags) into If/else, For each, SQL, and other tasks, with no temp tables.

### Q: Limitations?
- `set`/`get` work only in **Python notebooks**. Any task can **reference** values via `{{tasks.<t>.values.<k>}}`.
- The 48 KiB limit means they are not for datasets.
- `get` hard-codes the upstream task name. `default=` masks typos.
- `debugValue` is used only for **interactive** runs outside a job.

### Q: How do they compare to `dbutils.notebook.exit`?
- `exit` returns one string to a `dbutils.notebook.run` caller.
- Task values flow between **job tasks**.

### Q: Exam trap: a SQL task needs the row count computed by an upstream Python notebook. How?
Use a SQL task parameter set to `{{tasks.ingest.values.row_count}}` and read it as `:row_count`. SQL can't call `taskValues.get`.

## 16. Job parameters, task parameters, dynamic value references

### Q: What are job parameters?
Job-level key/default pairs that can be overridden per run (Run now with different parameters, API `job_parameters`, `bundle run --params`, or the repair dialog).
```yaml
parameters:
  - { name: catalog,  default: '${var.catalog}' }
  - { name: run_date, default: '{{job.start_time.iso_date}}' }
```

### Q: What are task parameters?
Task-level key-value pairs (notebook `base_parameters`, SQL, wheel `named_parameters`, Run Job) or JSON arrays (Python script, wheel positional, JAR, Spark submit, For each).

### Q: How do they interact?
- Job params are **pushed down automatically** to key-value tasks, and the **job param wins** on a key clash.
- JSON-array tasks don't get pushdown, so reference `{{job.parameters.<name>}}`.
- **Bundles reject a job with both job-level `parameters` and task `base_parameters`.**
- Code reads them with `dbutils.widgets.get("k")` (strings) or SQL `:k`.

### Q: What are dynamic value references?
Run-time `{{...}}` tokens usable in parameter or config fields (**not** inside code):

| Ref | Value |
|---|---|
| `{{job.id}}`, `{{job.name}}`, `{{job.run_id}}`, `{{job.repair_count}}` | job/run metadata |
| `{{job.start_time.iso_date|iso_datetime|year|month|day|hour|is_weekday|timestamp_ms}}` | UTC start |
| `{{job.trigger.type}}` | `periodic`, `one_time`, `run_job_task`, `file_arrival`, `continuous`, `table`, `model` |
| `{{job.trigger.file_arrival.location}}`, `{{job.trigger.table_update.updated_tables}}` | trigger context |
| `{{job.parameters.<n>}}` | job param |
| `{{task.name}}`, `{{task.run_id}}`, `{{task.execution_count}}` | current task (count includes retries and repairs) |
| `{{tasks.<t>.values.<k>}}`, `.result_state`, `.error_code`, `.output.rows`, `.output.first_row.<col>` | upstream task |
| `{{workspace.id}}`, `{{workspace.url}}` | workspace |
| `{{(job.start_time - 1.day).iso_date}}` | date arithmetic (Beta) |

### Q: Limitations?
- A syntax error or unknown namespace is **silently kept as a literal string**. An invalid key in a **known** namespace (for example `{{job.notebook_url}}`) raises an error.
- No expressions except date arithmetic.
- **Deprecated:** `{{job_id}}`, `{{run_id}}`, `{{start_date}}`, `{{parent_run_id}}`, `{{task_key}}`, `{{task_retry_count}}`. Use `job.id`, `task.run_id`, `job.start_time.*`, `job.run_id`, `task.name`, `task.execution_count`.

### Q: Exam trap: is a job parameter default a security control?
No. Anyone with **CAN MANAGE RUN** can override it. Restrict permissions instead.

### Q: Exam trap: a Python script task doesn't see job parameter `catalog`. Why?
Script tasks take JSON-array params with no pushdown. Add `"--catalog", "{{job.parameters.catalog}}"` to `parameters`.

## 17. Retries, timeouts, notifications, health rules

### Q: What are the retry and timeout settings?
Task-level:
- `max_retries` (`-1` means unlimited)
- `min_retry_interval_millis` (default 0)
- `retry_on_timeout` (**default false**)
- `timeout_seconds` (0 = none; jobs also have a job-level `timeout_seconds`)
- `disable_auto_optimization`: serverless auto-optimization can retry **beyond** your policy, so set it to true for at-most-once tasks.

### Q: How are notifications configured?
```yaml
email_notifications:
  on_start: [...]; on_success: [...]; on_failure: [oncall@contoso.com]
  on_duration_warning_threshold_exceeded: [...]; on_streaming_backlog_exceeded: [...]
webhook_notifications: { on_failure: [ { id: <system-destination-id> } ] }   # Slack/Teams/PagerDuty/webhook, admin-created
notification_settings: { no_alert_for_skipped_runs: true, no_alert_for_canceled_runs: true }
# task-level: notification_settings.alert_on_last_attempt: true
```
- Max **3 system destinations per event type**.
- Editing notifications needs **CAN MANAGE / IS OWNER**.

### Q: What are health rules?
```yaml
health: { rules: [ { metric: RUN_DURATION_SECONDS, op: GREATER_THAN, value: 3600 } ] }
```
- Other metrics: `STREAMING_BACKLOG_BYTES`, `_RECORDS`, `_SECONDS`, `_FILES`. Backlog uses a 10-minute average and alerts resend every 30 minutes.
- Backlog alerts are not supported on pipeline tasks and break with `awaitTermination()`.

### Q: How does a health rule compare to a timeout?
- A health rule **warns only**: the run continues.
- `timeout_seconds` **kills** the run.

### Q: Limitations?
- **Job-level notifications aren't sent when failed tasks are retried.** Use task-level ones.
- "Succeeded with failures" triggers `on_success`, not `on_failure`.
- Continuous jobs don't support retry policies.

### Q: Exam trap: a task times out and doesn't retry despite `max_retries: 3`. Why?
`retry_on_timeout` defaults to **false**.

## 18. Repair runs

### Q: What is a repair run?
Rerunning only the **unsuccessful (failed or canceled) tasks plus their dependent tasks** inside the **same** job run. Successful tasks are not rerun.

### Q: How is it used?
- UI: failed run, then **Repair run**, optionally edit parameters, then Repair.
- CLI: `databricks jobs repair-run <RUN_ID> --rerun-all-failed-tasks` (or `--json '{"rerun_tasks":["t3"]}' --rerun-dependent-tasks`).
- The run must not be in progress.

### Q: Advantages?
It saves time and compute, keeps history in one run, and lets you fix code or config first: the repair uses the **current** job and task settings.

### Q: Limitations?
- Only for **multi-task** jobs (≥2 tasks). A single-task job uses **Run now**.
- Tasks restart from the beginning and are not made idempotent, so a half-done append can **duplicate rows**.
- A shared job cluster gets **a new cluster `<key>_v1`**.
- Duration covers the original run plus all repairs.
- A disabled task reruns only if listed explicitly in `rerun_tasks`.

### Q: Parameters during repair?
Override or add values in the dialog. A later repair can clear them to revert. `{{job.repair_count}}` increments.

### Q: How does repair compare to retries, Run now, and `bundle run --only`?
| | Scope | Same run? |
|---|---|---|
| Retries | one task, automatic, transient errors | yes |
| Repair | failed + downstream, manual or API | yes |
| Run now | whole job | no (new run) |
| `bundle run --only t+` | chosen subset | no (new run) |

### Q: Exam trap: A → B → C plus A → D. B fails, C is upstream-failed, D succeeded. Which tasks run in the repair?
**B and C only.** A and D succeeded.

## 19. Triggers (schedule, file arrival, table update)

### Q: Which triggers exist?
| Trigger | YAML | Facts |
|---|---|---|
| Scheduled | `schedule: {quartz_cron_expression, timezone_id, pause_status}` | **Quartz, seconds first**: `0 30 2 * * ?` = 02:30 daily; one of DoM/DoW is `?` |
| Periodic | `trigger: {periodic: {interval, unit: HOURS|DAYS|WEEKS}}` | interval since the last run |
| File arrival | `trigger: {file_arrival: {url, min_time_between_triggers_seconds, wait_after_last_change_seconds}}` | **UC volume or external location** (root/subpath, recursive); checks about every minute |
| Table update | `trigger: {table_update: {table_names, condition: ANY_UPDATED|ALL_UPDATED, wait_after_last_change_seconds, min_time_between_triggers_seconds}}` | UC Delta/Iceberg managed, external Delta, MV, ST, views; ≤25 tables |
| Continuous | `continuous: {...}` | section 20 |
| Model update / Job completion | Beta | |
| None | omit | manual or API |

### Q: What do the two timing options mean?
- `min_time_between_triggers_seconds` is a **cooldown**: at most one run per interval.
- `wait_after_last_change_seconds` **debounces**: each new file or update resets the timer. Use it to wait for a whole batch.

### Q: Advantages of event triggers over a cron schedule?
They run when data is ready, with no always-on cluster and no polling cost beyond cloud listing. Pair file arrival with **Auto Loader** for exactly-once processing.

### Q: File arrival limitations?
- Only **new** files trigger: an overwrite with the same name doesn't.
- No wildcards.
- The path can't contain external tables or managed locations.
- **Without file events:** ≤10,000 files at the path and ≤50 jobs per workspace. Enable **file events** on the external location to scale.

### Q: Table update limitations?
- **>10 tables requires file events.**
- The job's **run-as** principal needs `SELECT` (+ `USE CATALOG/SCHEMA`), or the trigger silently fails to evaluate.
- Views count each source table.

### Q: Exam trap: "run when both `orders` and `customers` have new commits"?
Table update trigger with `condition: ALL_UPDATED`. `ANY_UPDATED` is the default and fires on either table.

### Q: Exam trap: cron `30 2 * * *` in a job schedule?
Invalid. Quartz needs seconds first and a `?`.

## 20. Continuous jobs

### Q: What is it?
A trigger mode that keeps **exactly one** run always active. A new run starts less than 60 s after the previous run ends or fails.
```yaml
continuous: { pause_status: UNPAUSED, task_retry_mode: ON_FAILURE }   # NEVER | ON_FAILURE (YAML default NEVER)
```

### Q: When to use?
Always-on Structured Streaming. It **replaces** the legacy pattern of "unlimited retries + max 1 concurrent run".

### Q: Advantages?
Auto-restart with **exponential backoff** on consecutive failures (unlimited retries, backoff resets when the job is healthy), and no scheduling logic to maintain.

### Q: Limitations?
- One running instance only.
- **No task dependencies, no retry policies** (use `task_retry_mode`), and no schedule at the same time.
- **Run now** is replaced by **Restart run**, which is also how the job picks up new configuration.
- On serverless, only bounded triggers (`AvailableNow`) work. `ProcessingTime`/`Continuous` triggers aren't supported. For low latency, run a continuous pipeline.

### Q: How do you stop or start it?
Pause or Resume. **Run now** on a paused continuous job starts a single run.

### Q: Exam trap: you changed the notebook path of a running continuous job. When does it take effect?
After **Restart run**, or a run-now API call with the job ID.

## 21. Concurrency and queueing

### Q: What is `max_concurrent_runs`?
The maximum number of simultaneous active runs of a job. **Default 1.** Runs beyond it are **skipped**.

### Q: What is queueing?
`queue: { enabled: true }` queues runs blocked by job, workspace, or Run Job concurrency limits for **up to 48 h** instead of skipping them. It is **on by default for UI-created jobs since April 2024**.

### Q: When to raise concurrency?
For overlapping frequent schedules, or parallel runs with different parameters, **if** the tasks don't write to the same targets non-idempotently.

### Q: Overrides to remember?
- Dev mode enables concurrent runs.
- A pipeline task caps the job to 1.
- Continuous jobs are always 1.
- The `jobs_max_concurrent_runs` preset loses to an explicit job value.

### Q: Exam trap: an hourly job's run overlaps the next and the next one disappears with status "Skipped". Fix without allowing overlap?
Enable **queueing** (keeping `max_concurrent_runs: 1`).

## 22. Job compute

### Q: What are the options?
| Option | YAML | Use / notes |
|---|---|---|
| **Serverless** | omit cluster (notebook); `environments` + `environment_key` | Default choice with fast start. `environment_key` **required** for Python script, wheel, and dbt. `performance_target: STANDARD|PERFORMANCE_OPTIMIZED` |
| **Job cluster** | task `new_cluster` | Isolated per task, jobs-compute pricing, terminates after the task |
| **Shared job cluster** | job `job_clusters[].job_cluster_key` + task `job_cluster_key` | One cluster reused by several tasks in a run, so startup happens once. **No libraries on the shared cluster**; declare them per task |
| **All-purpose** | `existing_cluster_id` | Dev/debug only, all-purpose pricing |
| **SQL warehouse** | `warehouse_id` (SQL/dbt/dashboard/SQL notebook) | Serverless or pro, not classic, for notebooks |

```yaml
environments:
  - environment_key: default
    spec: { environment_version: '2', dependencies: [ ../dist/*.whl ] }
```

### Q: Shared job cluster advantages / disadvantages?
- **Advantages:** cheaper and faster than one cluster per task.
- **Disadvantages:** tasks contend for resources, it can't mix runtimes, and a repair spins up `_v1`.

### Q: Run-as for jobs?
Defaults to the creator/owner. Set an SP (or a group at resource level). Job ACLs: `CAN_VIEW`, `CAN_MANAGE_RUN`, `CAN_MANAGE`, `IS_OWNER`.

### Q: Exam trap: a prod job uses `existing_cluster_id` of an interactive cluster. What's wrong?
Cost (all-purpose DBUs), no isolation, and failures when the cluster is restarted or edited. Use a job cluster or serverless. Also, prod mode forbids the `--cluster-id` override.

### Q: Exam trap: a serverless Python wheel task fails validation. Missing?
`environment_key` pointing at a job `environments` entry.

## 23. Widgets, `%run`, `dbutils.notebook.run`

### Q: What are widgets?
Notebook input parameters, and also how notebook tasks receive job and task params.
```python
dbutils.widgets.text("catalog", "dev_catalog", "Catalog")     # name, default, label
dbutils.widgets.dropdown("env", "dev", ["dev", "prod"])       # also combobox, multiselect
cat = dbutils.widgets.get("catalog")                          # always str
dbutils.widgets.remove("env"); dbutils.widgets.removeAll()
```
- A widget default hides a missing job parameter. That is handy for interactive use but masks misconfiguration.

### Q: What is `%run`?
`%run ./helpers` executes another notebook **inline in the same context**, so its functions and variables become available.
- It must be **alone in its cell**, with a literal path.
- It returns nothing.
- It can't import `.py` files.

### Q: What is `dbutils.notebook.run`?
`dbutils.notebook.run(path, timeout_seconds, {"k": "v"})` starts an **ephemeral job** on the current cluster in a separate context.
- `arguments` set the child's widgets (strings, ASCII only).
- It returns the child's `dbutils.notebook.exit("...")` string (≤5 MB).
- It throws `WorkflowException` on failure, so it can be retried or run in threads.
- A timeout of `0` means none, and runs must finish within 30 days.

### Q: How do they compare?
| | `%run` | `dbutils.notebook.run` |
|---|---|---|
| Context | shared | isolated |
| Return | none | string |
| Dynamic path / loop / try-except | no | yes |
| Recommended alternative | **workspace files + `import`** | **Lakeflow Jobs** (For each, If/else) |

### Q: When to use each?
- `%run`: shared config or helpers when you can't use workspace files.
- `dbutils.notebook.run`: metadata-driven or conditional orchestration that Jobs can't express.

### Q: Exam trap: the caller needs a DataFrame back from the child notebook?
`exit` returns only a string. Return a temp view name, a table path, or JSON.

## 24. Decision table: "if the scenario says X, pick Y"

| Scenario | Pick |
|---|---|
| Same resources to dev/test/prod, different catalogs | One bundle + `targets` + `variables` |
| Change value per run without redeploy | Job parameter (`default: ${var.x}`) |
| Need an ID by name | `variables.x.lookup` |
| Devs share a dev workspace safely | `mode: development` |
| Prod runs as non-human | `run_as.service_principal_name: <app-id>` |
| Prod deploy only from `main` | `mode: production` + `git.branch: main` |
| CI auth with no stored secret | Workload identity federation |
| Local interactive auth | `databricks auth login` (U2M) |
| Adopt an existing UI job | `bundle generate` + `bundle deployment bind` |
| Preview a deploy | `bundle plan` / `validate --output json` |
| Pass a value task → task | `taskValues.set` + `{{tasks.t.values.k}}` |
| Branch on a value | `condition_task` + `outcome` |
| Loop over a list | `for_each_task` |
| Always-run cleanup | `run_if: ALL_DONE` |
| Alert only on failure | `run_if: AT_LEAST_ONE_FAILED` |
| Re-execute only failed part | Repair run |
| Transient errors | `max_retries` + `min_retry_interval_millis` |
| Kill a runaway task / warn when slow | `timeout_seconds` / `health` rule |
| Start when files land | File arrival trigger (UC volume/ext location) |
| Start when tables change | Table update trigger |
| 24/7 streaming | Continuous job |
| Don't drop overlapping runs | `queue.enabled: true` |
| Many tasks, one classic cluster | Shared job cluster |
| Least ops | Serverless (+ `environment_key` for wheel/script/dbt) |
| Reuse helpers | Workspace files + `import` (or `%run`) |
| Code-only deploy, no CI tool | Production Git folder + Repos API |
