## §1 Secret scopes: Azure Key Vault-backed vs Databricks-backed

### Q: What is a secret scope?
A named collection of secrets in **one workspace**. Permissions (ACLs) apply to the **whole scope**, never to a single secret. Two backends:

| | Azure Key Vault-backed | Databricks-backed |
|---|---|---|
| Where values live | Your Azure Key Vault | Encrypted DB managed by Azure Databricks |
| Write secrets from Databricks? | **No. Read-only interface.** Create/rotate/delete in Azure (portal, `az keyvault secret set`, Key Vault REST) | Yes: CLI `put-secret`, SDK, Secrets API |
| Create the scope with | UI `https://<workspace-url>#secrets/createScope` (case-sensitive: capital **S**), or CLI/API | CLI `databricks secrets create-scope <name>` or Secrets API (**no UI page**) |
| Rotation | Rotate in Key Vault, nothing changes in Databricks | Re-`put-secret` |
| Best for | Central enterprise secret management, shared with other Azure services, Key Vault auditing | Databricks-only secrets, quick setup |

### Q: How do I create a Key Vault-backed scope?
1. Key Vault prerequisites (current docs):
   - Permission model **Vault access policy**. Key Vault-backed scopes **don't support Azure RBAC**, and new vaults default to RBAC, so switch it first.
   - You need **Key Vault Contributor, Contributor or Owner** on the vault, even if Databricks already has access.
   - Networking: allow selected networks plus **"Allow trusted Microsoft services to bypass this firewall"**, or allow all networks.
2. Go to `https://<workspace-url>#secrets/createScope`. Enter the scope name, **Manage Principal** (`Creator` needs **Premium**, otherwise `All workspace users`), the **DNS Name** (`https://<kv>.vault.azure.net/`) and the **Resource ID** (`/subscriptions/…/providers/Microsoft.KeyVault/vaults/<kv>`). Both values are on the vault's **Properties** blade.
3. Creating the scope adds an access policy granting **Get** and **List** on secrets to the AzureDatabricks application.
4. Verify with `databricks secrets list-scopes`.

CLI alternative: `databricks secrets create-scope <name> --scope-backend-type AZURE_KEYVAULT --json '{... "backend_azure_keyvault": {"resource_id": "...", "dns_name": "..."}}'`. The Secrets API expects a **Microsoft Entra ID token** (not a PAT) for this call. Bundles can also declare `resources.secret_scopes` with `backend_type: AZURE_KEYVAULT` + `keyvault_metadata`.

### Q: How do I read and list secrets?
```python
pwd  = dbutils.secrets.get(scope="kv-sales", key="sql-password")   # str, redacted in output
raw  = dbutils.secrets.getBytes("kv-sales", "cert")                # bytes
dbutils.secrets.list("kv-sales")      # [SecretMetadata(key='sql-password'), ...]  metadata only, never values
dbutils.secrets.listScopes()
```
```sql
SELECT secret('kv-sales', 'sql-password');          -- SQL function; output shows [REDACTED]
CREATE CONNECTION sqlsrv TYPE sqlserver OPTIONS (host 'x', port '1433',
  user secret('kv-sales','sql-user'), password secret('kv-sales','sql-password'));
```
CLI: `databricks secrets list-secrets <scope>` (metadata), `databricks secrets get-secret <scope> <key>` (returns **base64**: pipe through `jq -r .value | base64 --decode`). Values returned by the API/CLI are **not redacted**.

### Q: How does redaction work, and where does it fail?
Values read with `dbutils.secrets.get()` or a Spark-config secret reference are replaced with `[REDACTED]` when displayed. It only matches the **literal** value:
- `print(pwd)` shows `[REDACTED]`.
- `print(" ".join(pwd))` or `pwd[::-1]` leaks it. Redaction does not stop deliberate transformation. Control **who can run code** (notebook/compute ACLs) and **who can READ the scope**.
- Secrets are **not redacted** in the Spark driver's `stdout`/`stderr`. By default only CAN MANAGE on the compute can view driver logs.
- SQL: DQL that calls `secret()` is redacted. DML that would store a raw secret is blocked unless it is wrapped in e.g. `sha2()` / `aes_encrypt()`.

### Q: What are the secret ACL levels?
| Ability | READ | WRITE | MANAGE |
|---|---|---|---|
| Read secrets, list keys | ✓ | ✓ | ✓ |
| Write/delete secrets | | ✓ | ✓ |
| Change ACLs | | | ✓ |

```bash
databricks secrets put-acl kv-sales data-engineers READ     # principal: user email, SP applicationId, or group name
databricks secrets list-acls kv-sales
databricks secrets delete-acl kv-sales data-engineers
```
- Granting scope ACLs requires **Premium**. `put-acl` **overwrites** the principal's existing level.
- The scope creator gets MANAGE by default. Workspace admins have MANAGE on all scopes.
- For a Key Vault-backed scope, scope READ grants **every secret in that vault**. To separate access, use **separate vaults/scopes**.
- WRITE on a Key Vault-backed scope still can't write from Databricks. The backend is read-only.

### Q: How do I reference a secret in Spark config or an environment variable?
```ini
# Compute > Advanced > Spark config  (one secret per property)
spark.password {{secrets/kv-sales/sql-password}}
fs.azure.account.oauth2.client.secret.<acct>.dfs.core.windows.net {{secrets/kv-sales/sp-secret}}
# Compute > Advanced > Environment variables
SQL_PWD={{secrets/kv-sales/sql-password}}
```
- Read it with `spark.conf.get("spark.password")` or `${spark.password}` in SQL. Env vars are also visible to cluster-scoped init scripts as `$SQL_PWD`.
- The **compute owner needs READ** on the scope, and only the owner can add or edit the reference.
- A rotated secret is fetched again **only after a compute restart**.
- Anyone with CAN ATTACH TO can read env vars, and (without table ACLs) Spark conf. Don't use this for secrets that some users of the compute must not see.

### Q: What replaced or supplements workspace scopes?
**Secrets in Unity Catalog** (`catalog.schema.secret`) are securables available in every workspace on the metastore, with per-secret UC privileges. They can be Databricks-managed, or **Key Vault-backed (Beta)**. They are readable with `dbutils.secrets` on DBR 17.3 LTS+ / serverless env v4+, and usable in UC Python/Scala UDFs (callers need only `EXECUTE`). They don't work in Spark conf, env vars, or Databricks Connect. Exam questions (written for March 2026) almost certainly mean **workspace secret scopes**.

### Q: Exam trap: "Rotate the SQL password in Key Vault. What must change in Databricks?"
Nothing for code that calls `dbutils.secrets.get()`: it reads the new value on the next call. **But** a `{{secrets/...}}` Spark-config or env-var reference needs a **compute restart**.

### Q: Exam trap: "Use the Databricks CLI `put-secret` to add a key to the Key Vault-backed scope."
It fails: the scope is read-only. Add the secret in **Azure Key Vault**. It then appears in the scope automatically.

## §2 Identities for data and resource access (short recap; detail in M3 §7, §14)

### Q: Managed identity vs service principal: what is each used for?
| Need | Use |
|---|---|
| UC access to ADLS (external locations, managed storage) | **Access Connector for Azure Databricks** (system- or user-assigned **managed identity**) wrapped in a **storage credential**. No secret to rotate, and it works behind a storage firewall (trusted access) |
| Databricks → other Azure services (Event Hubs, Key Vault, Service Bus) via SDK | UC **service credential** (Access Connector MI), privilege `ACCESS` |
| Jobs/CI identity, "run as" non-human | Databricks **service principal** (Entra ID-managed or Databricks-managed), OAuth M2M |
| ADF → Databricks | ADF's **system/user-assigned managed identity**, with **Contributor** role on the workspace resource (§12) |
| Legacy ADLS via Spark conf OAuth | Entra SP client ID + secret from a scope (§1). Legacy pattern; prefer UC credentials |

### Q: Exam trap: "No secrets to rotate, storage firewall on." Which identity?
A managed identity via the Access Connector, not an SP client secret in a scope.

## §3 Azure Monitor: diagnostic logs → Log Analytics, KQL, alerts

### Q: What are Azure Databricks diagnostic logs?
**Audit (control-plane) events** — who did what — streamed by an Azure **diagnostic setting** on the `Microsoft.Databricks/workspaces` resource. They are **not** Spark metrics, executor logs or query performance data.
- **Requires the Premium plan.**
- Configure them as **Owner/Contributor** on the workspace resource: portal → workspace → **Monitoring → Diagnostic settings → Add diagnostic setting**, or `az monitor diagnostic-settings create`, `New-AzDiagnosticSetting`, ARM/Bicep, or REST.
- Destinations (one or more): **Send to Log Analytics workspace**, **Archive to a storage account**, **Stream to an event hub**, partner solution.
- Latency: typically **within 15 minutes**, not guaranteed.
- **Account-level events are not included.** Only the `system.access.audit` system table has them.

### Q: Which log categories exist (the ones to recognize)?
`accounts`, `clusters`, `clusterLibraries`, `dbfs`, `deltaPipelines`, `featureStore`, `genie`, `gitCredentials`, `globalInitScripts`, `instancePools`, `jobs`, `notebook`, `repos`, `secrets`, `sqlPermissions`, `ssh`, `unityCatalog`, `workspace`, `databrickssql`, `webTerminal`, `modelRegistry`, `mlflowExperiment`, plus newer ones (`Apps`, `Dashboards`, `Ingestion`, `LineageTracking`, `PredictiveOptimization`, `VectorSearch`, `WorkspaceFiles`, `ClusterPolicies`, …).
- Older categories land in dedicated tables: `DatabricksJobs`, `DatabricksClusters`, `DatabricksNotebook`, `DatabricksSecrets`, `DatabricksUnityCatalog`, `DatabricksDeltaPipelines`, `DatabricksSQL`, `DatabricksAccounts`, `DatabricksWorkspace`, …
- Common columns: `TimeGenerated`, `Category`, `OperationName`, **`ActionName`**, `Identity`, **`RequestParams`** (a JSON string), **`Response`** (JSON with `statusCode`, `errorMessage`), `ServiceName`, `SourceIPAddress`, `UserAgent`, `RequestId`, `SessionId`.

### Q: KQL basics I must be able to read?
```kusto
// Failed (or canceled) job runs in the last 24 h
DatabricksJobs
| where TimeGenerated > ago(24h)
| where ActionName == "runFailed"
| extend p = parse_json(RequestParams)
| project TimeGenerated, JobId = tostring(p.jobId), RunId = tostring(p.runId),
          TaskKey = tostring(p.taskKey), State = tostring(p.jobTerminalState), Identity
| order by TimeGenerated desc

// Failure counts per job, 1-hour bins
DatabricksJobs
| where ActionName == "runFailed"
| summarize failures = count() by JobId = tostring(parse_json(RequestParams).jobId), bin(TimeGenerated, 1h)

// Who read secrets
DatabricksSecrets | where ActionName == "getSecret" | project TimeGenerated, Identity, RequestParams

// Cluster create/edit/delete events
DatabricksClusters | where ActionName in ("create", "edit", "permanentDelete") | take 50
```
Operators to know: `where`, `project`, `extend`, `summarize … by`, `bin()`, `ago()`, `parse_json()`/`tostring()`, `join`, `union`, `order by`, `take`/`limit`, `render timechart`.
Jobs actions include `runStart`, `runSucceeded`, `runFailed` (failed **or canceled**), `runNow`, `runTriggered`, `submitRun`, `repairRun`, `create`, `update`, `reset`, `delete`.

### Q: How do I configure an Azure Monitor alert on this?
A **log search alert rule**:
1. **Scope**: the Log Analytics workspace.
2. **Condition**: a KQL query, measured as a row count (or an aggregated value), threshold e.g. `> 0`, with an **evaluation frequency** (e.g. every 5 min) and a **lookback window**. Optionally split by dimension (e.g. `JobId`).
3. **Action group**: email/SMS/push/voice, webhook, Logic App, Azure Function, Automation runbook, ITSM, event hub.
4. **Severity** 0–4, plus alert details.

Activity-log alerts cover Azure resource-level operations, e.g. someone deleting the workspace.

### Q: Azure Monitor vs system tables vs job notifications: which do I pick?
| Requirement | Pick |
|---|---|
| Ops/SOC team already centralizes **all Azure resources** in Log Analytics; KQL alerting; Sentinel/SIEM | **Diagnostic settings → Log Analytics + log alerts** |
| Account-level events, lineage, billing, job run timelines, compute utilization, queryable with SQL | **System tables** (`system.access.audit`, `system.lakeflow.job_run_timeline`, `system.billing.usage`, `system.compute.*`). Databricks' **recommended** audit source |
| Tell the job owner a run failed/was slow, on a per-job basis | **Job notifications** (email, webhook, Teams/Slack, duration/backlog thresholds). See M5 §17 |
| Alert on a SQL condition over data or system tables | **Databricks SQL alert** |
| Spark driver/executor logs | **Compute log delivery** to a volume/ABFSS. Diagnostic settings don't carry them |

### Q: Exam trap: "Diagnostic settings is greyed out / no Databricks categories appear."
The workspace is on the **Standard** tier. Diagnostic logs require **Premium**. Also check that the subscription is registered for `microsoft.insights`.

### Q: Exam trap: "Stream executor memory metrics to Log Analytics via diagnostic settings."
Not possible. Diagnostic logs are audit events only. Use compute metrics, system tables, or a custom log4j/metrics forwarder.

## §4 Set operators: UNION / UNION ALL / unionByName / INTERSECT / EXCEPT

### Q: What are the semantics?
| SQL | Default | PySpark equivalent | Notes |
|---|---|---|---|
| `UNION` | **DISTINCT** | `df1.union(df2).distinct()` | Dedup costs a shuffle |
| `UNION ALL` | keeps duplicates | `df1.union(df2)` (alias `unionAll`) | **By position, not by name** |
| — | — | `df1.unionByName(df2, allowMissingColumns=True)` | Matches **by name**. Missing columns are filled with NULL (Spark 3.1+) |
| `INTERSECT [DISTINCT]` | distinct | `df1.intersect(df2)` | Rows in both |
| `INTERSECT ALL` | keeps multiplicity | `df1.intersectAll(df2)` | min(count1, count2) copies |
| `EXCEPT [DISTINCT]` / `MINUS` | distinct | `df1.subtract(df2)` (or `exceptAll` for ALL) | Rows in 1 not in 2, **deduplicated** |
| `EXCEPT ALL` | each row in 2 removes **one** match | `df1.exceptAll(df2)` | Multiset difference |

- Both sides must have the **same number of columns** (`NUM_COLUMNS_MISMATCH`) and least-common types (`INCOMPATIBLE_COLUMN_TYPE`).
- `INTERSECT` binds tighter than `UNION`/`EXCEPT` when you chain them.
- Set operators treat **NULLs as equal** (unlike `=` in joins).
- Map-type columns aren't supported in set operations.

Example from the docs, with `number1 = 3,1,2,2,3,4` and `number2 = 5,1,1,2`:
- `EXCEPT` → `3,4`
- `EXCEPT ALL` → `3,3,4`
- `INTERSECT ALL` → `1,2`
- `UNION` → `1,2,3,4,5`

### Q: When to use which?
- Append monthly extracts with identical schema: `UNION ALL` / `union` (cheapest).
- Combine sources whose columns are in a different order, or where one side lacks columns: **`unionByName(allowMissingColumns=True)`**.
- Find rows that changed or are missing between two snapshots: `EXCEPT` (both directions for a diff), or `EXCEPT ALL` when duplicates matter.
- Find common keys: `INTERSECT`, or a semi join when you need more columns from one side.

### Q: Exam trap: two DataFrames with the same columns in different order, combined with `union()`.
No error if the types are compatible, but the values land in the **wrong columns** (silent corruption, or an implicit cast). Use `unionByName`.

### Q: Exam trap: "Rows in `today` not in `yesterday`, keeping duplicates that appear twice today but once yesterday."
`EXCEPT ALL` / `exceptAll`. Plain `EXCEPT` / `subtract` deduplicates and returns nothing for that row.

## §5 Joins (incl. semi/anti) and denormalizing

### Q: Which join types exist?
| SQL | PySpark `how=` | Returns |
|---|---|---|
| `[INNER] JOIN` | `"inner"` | Matches only |
| `LEFT [OUTER] JOIN` | `"left"` / `"left_outer"` | All left rows, NULLs where no match |
| `RIGHT [OUTER] JOIN` | `"right"` | All right rows |
| `FULL [OUTER] JOIN` | `"full"` / `"outer"` | All rows from both sides |
| `LEFT SEMI JOIN` | `"left_semi"` / `"semi"` | **Left columns only**, for left rows that have ≥1 match. **No duplication** |
| `LEFT ANTI JOIN` | `"left_anti"` / `"anti"` | Left rows with **no** match |
| `CROSS JOIN` | `crossJoin()` | Cartesian product |

```python
orphans = orders.join(customers, "customer_id", "left_anti")     # FK violations / late-arriving dims
active  = customers.join(orders, "customer_id", "left_semi")     # customers who ordered (no row explosion)
```
```sql
SELECT o.* FROM orders o LEFT ANTI JOIN customers c ON o.customer_id = c.customer_id;
```

### Q: What are the join traps?
- **NULL keys never match** with `=`. Use `<=>` / `eqNullSafe` if NULL should equal NULL.
- **`NOT IN (subquery)` with a NULL in the subquery returns zero rows.** Use `NOT EXISTS` or a `LEFT ANTI JOIN`.
- An inner join to a dimension with **duplicate keys multiplies fact rows**, so revenue doubles. Deduplicate the dimension (§20) or use a semi join for filtering.
- `df1.join(df2, "id")` (column name or list) gives a single `id` column. `df1.join(df2, df1.id == df2.id)` keeps **both**, causing ambiguous-column errors later.
- Performance (broadcast, skew, AQE) is in M4 §15–§16.

### Q: What does "denormalize" mean here, and when?
Join dimensions into the fact to produce a **wide, flat gold table** (or a nested struct/array) so BI/Genie avoids joins at query time.
- Pros: simpler, faster reads.
- Cons: redundancy, wide rows, and updates to dimension attributes must be re-propagated.
```python
gold = (fact_sales
  .join(dim_customer.filter("is_current"), "customer_sk", "left")
  .join(broadcast(dim_product), "product_sk", "left")
  .select("order_id", "order_date", "amount", "customer_name", "segment", "product_name", "category"))
```
Nested denormalization (one row per order with its line items): `groupBy("order_id").agg(collect_list(struct("sku", "qty", "price")).alias("lines"))`. Reverse it with `explode` / `inline`.

### Q: Exam trap: "List customers who placed at least one order. Each customer must appear once and only customer columns are needed."
`LEFT SEMI JOIN`. An inner join plus `distinct()` works but costs more. An inner join alone duplicates customers.

## §6 PIVOT / UNPIVOT (SQL and PySpark)

### Q: How does SQL PIVOT work?
```sql
SELECT * FROM (SELECT year, quarter, sales FROM sales)        -- project ONLY the needed columns first
PIVOT (sum(sales) AS total, avg(sales) AS avg
       FOR quarter IN (1 AS q1, 2 AS q2, 3 AS q3, 4 AS q4));
-- columns: year, q1_total, q1_avg, q2_total, ...
```
- **Implicit GROUP BY = every column not used in the aggregate or the FOR column.** Forgetting to project away `region` yields one row per (year, region) instead of per year. This is the #1 PIVOT trap.
- `IN` values must be **literals** (`NON_LITERAL_PIVOT_VALUES`).
- Multiple FOR columns: `FOR (quarter, region) IN ((1,'east') AS q1_east, …)`.
- Each cell is `agg(...) FILTER (WHERE quarter = 1)`. That's also how you write a pivot without PIVOT.

### Q: How does SQL UNPIVOT work?
```sql
SELECT * FROM quarterly_sales
UNPIVOT INCLUDE NULLS (sales FOR quarter IN (q1 AS `Jan-Mar`, q2 AS `Apr-Jun`, q3, q4));
-- result: all other columns + quarter (STRING) + sales (least common type of q1..q4)
-- multi-value: UNPIVOT ((name, email) FOR rank IN ((name1, email1) AS primary, (name2, email2) AS secondary))
```
- **Default is `EXCLUDE NULLS`**: rows whose value is NULL are dropped. Use `INCLUDE NULLS` to keep them.
- Value columns must share a least-common type (`UNPIVOT_VALUE_DATA_TYPE_MISMATCH`). Cast first if needed.
- Requires DBR 12.2 LTS+.

### Q: PySpark equivalents?
```python
wide = df.groupBy("year").pivot("quarter", [1, 2, 3, 4]).agg(F.sum("sales"))   # pass values!
long = wide.unpivot(ids=["year"], values=["1", "2", "3", "4"],
                    variableColumnName="quarter", valueColumnName="sales")      # melt() is an alias (Spark 3.4+)
```
- `pivot("col")` **without a values list** triggers an extra job to compute the distinct values, and the output columns change whenever the data changes. Pass the list for performance and a stable schema.
- `unpivot`/`melt` **keeps NULLs** (unlike SQL's default `EXCLUDE NULLS`). Add `.dropna(subset=["sales"])` to match the SQL default.
- `values=None` unpivots all non-id columns.

### Q: When NOT to pivot?
When the set of values is unbounded or high-cardinality (thousands of columns), or keeps changing. Keep the data long and pivot in the BI tool.

## §7 Filtering, grouping, aggregating

### Q: Which constructs should I know cold?
```sql
SELECT region, product, sum(amount) AS rev,
       count_if(amount < 0) AS refunds,
       sum(amount) FILTER (WHERE channel = 'web') AS web_rev,
       approx_count_distinct(customer_id) AS approx_custs
FROM sales
WHERE order_date >= '2026-01-01'              -- row filter BEFORE grouping
GROUP BY ROLLUP (region, product)             -- (region,product), (region), ()
HAVING sum(amount) > 1000;                    -- filter AFTER grouping

SELECT * FROM sales
QUALIFY row_number() OVER (PARTITION BY customer_id ORDER BY order_ts DESC) = 1;   -- filter on a window
```
| Clause | Grouping sets produced |
|---|---|
| `GROUP BY ROLLUP(a, b)` | (a,b), (a), () — hierarchical subtotals and a grand total |
| `GROUP BY CUBE(a, b)` | (a,b), (a), (b), () — all 2ⁿ combinations |
| `GROUP BY GROUPING SETS ((a,b), (a), ())` | exactly the listed ones |
| `GROUP BY ALL` | all non-aggregate select columns |

- Subtotal rows have NULL in the rolled-up column. Use `grouping(col)` / `grouping_id()` to tell a subtotal NULL from a data NULL.
- PySpark: `df.rollup("a", "b")`, `df.cube("a", "b")`, `groupBy().agg(F.sum(...), F.countDistinct(...), F.approx_count_distinct(...))`.
- `WHERE` can't reference aggregates, so use `HAVING`. `HAVING` can't reference window functions, so use `QUALIFY`.

### Q: Exam trap: "Subtotal per region and a grand total, but not per product alone."
`ROLLUP(region, product)`. `CUBE` would also add per-product subtotals.

## §8 Version control: Git folders, branching, PRs, conflicts

### Q: What can Git folders do (beyond M5 §10)?
Clone, create/switch branches, commit & push, pull, **merge**, **rebase**, **reset (hard)**, sparse checkout, diff, and **resolve conflicts in the UI**. There's also a web-terminal Git CLI, and the Repos API for automation.
- **Pull requests are created and reviewed in the Git provider** (GitHub, Azure DevOps, GitLab, Bitbucket). After a push, Databricks shows a "Create a pull request on your git provider" link.
- Only **code/files** are versioned: notebooks (source or `.ipynb`), `.py`, `.sql`, YAML. Not job configuration (that's bundles) and not notebook outputs by default.

### Q: Which branching strategy?
- **Each developer uses their own Git folder** (under `/Workspace/Users/<me>/`) and their **own feature branch**. Switching the branch in a shared Git folder switches it for everyone.
- Use **feature branches off `main`** (or off `develop` in GitFlow), merged by **PR + review + CI** (unit tests and `bundle validate`/deploy to dev). Protect `main` with branch policies: required reviewers and a passing build.
- Release to environments with bundles' **targets** (`dev`/`staging`/`prod`), or a **production Git folder** updated by CI via the Repos API, not by humans.
- Merge vs rebase: for Git beginners Databricks recommends **merge**, since it doesn't rewrite history and needs no force push. Rebase gives linear history but rewrites commits.

### Q: How do I resolve a merge conflict in a Git folder?
A conflict occurs during **pull, merge or rebase** when the same lines changed on both sides. The Git folders UI lists the conflicting files and offers:
1. **Manually edit** the file: keep the lines you want and delete the `<<<<<<< ======= >>>>>>>` markers, then **Mark As Resolved**.
2. **Keep all current changes** or **Take all incoming changes**: accept one side entirely.
3. **Abort**: undo the whole operation and try again.

When all files are resolved, click **Continue Merge** / **Continue Rebase**. A merge with no conflict pushes automatically.

**Pulling incoming changes clears the notebook state** (variables, attached session state).

### Q: Exam trap: "Two developers share one Git folder and one keeps 'losing' the branch."
Shared Git folder. Give each developer their own Git folder and branch.

### Q: Exam trap: "Resolve the conflict by accepting the teammate's version of the whole file."
**Take all incoming changes**, then Continue Merge. Not Abort, which discards the merge, and not a hard reset, which discards local commits.

## §9 Testing strategy and deploying (CLI vs REST)

### Q: What are the test layers?
| Layer | Scope | Where it runs | Data |
|---|---|---|---|
| **Unit** | One pure function, e.g. `def add_vat(df) -> DataFrame` in `src/` | Locally or in CI with `pytest` + **Databricks Connect** (or local PySpark), or in a notebook via `pytest.main()`. Run on **every PR** and block merges on failure | Small in-memory fake DataFrames |
| **Integration** | Components together: reads/writes to real UC tables, joins, MERGE, pipeline + table | A **dev/staging workspace** after `bundle deploy -t staging`, run as a job | Non-prod catalog, representative data including bad records |
| **End-to-end** | Whole flow from source to gold, including orchestration, triggers, permissions | Staging, triggered by CI after deploy (`bundle run`) | Production-like volume and shape |
| **UAT** | Business users confirm outputs (dashboards, Genie answers, reports) meet requirements | Pre-prod/staging, **humans** | Prod-like, masked as needed |

Rules:
- Never unit-test against production tables.
- Keep logic in importable modules (workspace files / `src/`), not in notebook cells. That's what makes it unit-testable.
- For pipelines, test on small datasets that include error records, using a development update.
- Promotion gate: "tests pass on `main` and in staging" → deploy to prod.

### Q: Unit test example (pytest + Databricks Connect)?
```python
# src/transforms.py
from pyspark.sql import DataFrame, functions as F
def dedup_latest(df: DataFrame, key: str, ts: str) -> DataFrame:
    from pyspark.sql.window import Window
    w = Window.partitionBy(key).orderBy(F.col(ts).desc())
    return df.withColumn("_rn", F.row_number().over(w)).filter("_rn = 1").drop("_rn")
```

### Q: How do I deploy a bundle: CLI vs REST APIs?
- **CLI (the standard):** `databricks bundle validate|deploy|run -t <target>`, from a dev machine or CI (GitHub Actions / Azure DevOps). Authenticate as a **service principal** (OAuth M2M, or Entra workload identity federation). Details in M5 §8–§9. You can also deploy from the workspace UI (bundle editor **Deploy** button).
- **REST APIs:** there is no single public "deploy bundle" endpoint. `bundle deploy` itself is a client that calls the workspace REST APIs. A REST-only pipeline (no CLI on the agent) does the same steps itself:
  1. Upload code: `POST /api/2.0/workspace/import`, or update a production Git folder with `PATCH /api/2.0/repos/{repo_id}` `{"branch": "main"}`.
  2. Create or update resources: `POST /api/2.2/jobs/create` / `jobs/reset` (pipelines via `/api/2.0/pipelines`).
  3. Trigger and poll: `POST /api/2.2/jobs/run-now`, `GET /api/2.2/jobs/runs/get`.
  - Auth: an OAuth token for an SP (`Authorization: Bearer`).
  - Cost: you lose bundle state tracking, drift handling and targets. Prefer the CLI, and use REST for edge automation or when the CLI can't be installed.

### Q: Exam trap: "Run unit tests on each PR without a running cluster in CI."
`pytest` with **Databricks Connect to serverless**, or a local PySpark install in CI for pure-transform tests. You don't need to deploy a job just to run unit tests.

## §10 AI/BI Genie (Genie spaces, now "Genie Agents")

### Q: What is it?
A natural-language chat interface over **up to 50 UC tables, views or metric views**, curated by an analyst. Genie writes and runs SQL on a **pro or serverless SQL warehouse** (serverless recommended).
- **Data access is always evaluated with the end user's own UC permissions**, so row filters and column masks apply. The author's warehouse credentials are embedded **for compute only**.
- Docs renamed "Genie spaces" to **Genie Agents**. The exam likely says "Genie space".

### Q: Requirements to create one?
- The Databricks SQL entitlement.
- **CAN USE** on a pro or serverless warehouse.
- **SELECT** on the data.
- At least **CAN EDIT** on the space. The creator gets CAN MANAGE.
- Users need at least CAN VIEW/RUN on the space plus SELECT on the data, and EXECUTE on any SQL functions.
- Partner-powered AI features must be enabled.

### Q: Which instruction types exist, and when do I use each?
| Instruction type | What | Use for |
|---|---|---|
| **Text (general) instructions** | One plain-text block. It counts as **1** instruction | Global rules: fiscal year starts in July, "revenue excludes refunds", default date range, terminology |
| **Example SQL queries** | A question title plus the SQL. Static or **parameterized** (`:param`, typed String/Date/Decimal/Integer…). Optional usage guidance | **Recommended main lever.** Organization-specific logic, complex joins |
| **SQL functions** | UC scalar or table-valued functions attached to the space. Genie can't see or modify their body | Complex or sensitive logic that shouldn't be exposed or rewritten |
| **Trusted assets** | **Parameterized example queries + SQL functions.** When Genie uses one verbatim, the answer is marked **Trusted** (verified) | High-stakes recurring questions |
| **Knowledge store** | Space-local table/column descriptions, **synonyms**, hidden columns, **join relationships**, **SQL expressions** (measures, filters, dimensions), prompt matching (value sampling) | Business terms like `active_customer` or `gross_margin`, and joins without FKs. **Doesn't change UC metadata** |
| **Benchmarks** | Test questions with gold SQL | **Evaluation only.** Genie doesn't learn from them |

Limits: **100 instructions** per space (each example query, each function, and the text block count 1 each), and **200 knowledge-store snippets**.

### Q: How do table/column comments drive discovery?
Genie uses **UC table names, descriptions, column names/comments, and PK/FK constraints** (informational, §20) to pick tables and write joins:
```sql
COMMENT ON TABLE gold.sales.orders IS 'One row per order line; amounts in EUR incl. VAT';
ALTER TABLE gold.sales.orders ALTER COLUMN net_amt COMMENT 'Amount excl. VAT, EUR';
ALTER TABLE gold.sales.orders ADD CONSTRAINT fk_cust FOREIGN KEY (customer_id) REFERENCES gold.sales.customers;
```
AI-generated comments (Catalog Explorer) are fine, but review them. Best practice:
- Keep the space focused (≈5 tables or fewer).
- Pre-join into views or **metric views**.
- Hide confusing columns.
- Keep instructions short and non-conflicting. Too many reduces quality.

### Q: Exam trap: "Genie keeps computing revenue including refunds. Fix it so every question uses the right definition."
Add a **SQL expression (measure)** in the knowledge store, or a text instruction or example query, defining revenue. Don't rename the UC column. Benchmarks won't fix it, because they only evaluate.

### Q: Exam trap: "Users see 'trusted' on some answers but not others."
Only answers produced from a **parameterized example query or UC SQL function** used verbatim are trusted.

## §11 Azure Event Hubs streaming ingestion

### Q: How does Databricks read Event Hubs?
Through the Event Hubs **Kafka-compatible endpoint** with the built-in **Structured Streaming Kafka connector** (`format("kafka")` / `read_kafka`).
- The old `azure-event-hubs-spark` connector **isn't in the Databricks Runtime**, and **Lakeflow pipelines can't use third-party JVM libraries**, so in pipelines Kafka is the only way.
- The Kafka endpoint needs the Event Hubs **Standard, Premium or Dedicated** tier (**not Basic**).

| Kafka concept | Event Hubs concept |
|---|---|
| Cluster / bootstrap server | **Namespace** `<ns>.servicebus.windows.net:9093` |
| Topic | **Event hub** |
| Partition / offset | Partition / offset |
| Consumer group | Kafka consumer groups are **auto-created**, distinct from Event Hubs consumer groups (no need for `$Default`). Standard: 1,000 Kafka groups per namespace |

### Q: Code (SAS connection string, SASL PLAIN)?
```python
ns, hub = "evhns-iot", "telemetry"
conn = dbutils.secrets.get("kv-iot", "eh-listen-conn")   # "Endpoint=sb://evhns-iot.servicebus.windows.net/;SharedAccessKeyName=listen;SharedAccessKey=..."
opts = {
  "kafka.bootstrap.servers": f"{ns}.servicebus.windows.net:9093",
  "subscribe": hub,                                     # the event hub name; EntityPath is NOT needed
  "kafka.security.protocol": "SASL_SSL",
  "kafka.sasl.mechanism": "PLAIN",
  "kafka.sasl.jaas.config":
     f'kafkashaded.org.apache.kafka.common.security.plain.PlainLoginModule required username="$ConnectionString" password="{conn}";',
  "startingOffsets": "earliest",                        # default is "latest" for streams
  "maxOffsetsPerTrigger": "50000",
  "failOnDataLoss": "false",
}
raw = spark.readStream.format("kafka").options(**opts).load()
# columns: key, value (BINARY), topic, partition, offset, timestamp, timestampType
events = (raw.select(F.from_json(F.col("value").cast("string"), schema).alias("e"),
                     "partition", "offset", F.col("timestamp").alias("enqueued_ts"))
             .select("e.*", "partition", "offset", "enqueued_ts"))
(events.writeStream.option("checkpointLocation", "/Volumes/iot/raw/chk/telemetry")
       .trigger(availableNow=True).toTable("iot.bronze.telemetry"))
```
- Username is the literal string **`$ConnectionString`**. In a Python f-string or Scala `s""`, make sure `$` isn't interpolated (escape it as `\$` in Scala).
- **Use the `kafkashaded.` class prefix.** Unshaded `org.apache.kafka...` fails with `RESTRICTED_STREAMING_OPTION_PERMISSION_ENFORCED`.
- Kafka client options need the **`kafka.` prefix**. Spark source options (`subscribe`, `startingOffsets`, `maxOffsetsPerTrigger`, `failOnDataLoss`) don't.
- Use a **listen-only** shared access policy, not `RootManageSharedAccessKey`.

### Q: Entra ID / OAuth instead of SAS?
- **UC service credential** (DBR 16.1+, recommended on standard/serverless): `"databricks.serviceCredential": "<cred>"`. Don't set any `kafka.sasl.*` or `kafka.security.protocol` options with it.
- **SP client ID + secret** via `OAUTHBEARER`:
  - `kafka.security.protocol=SASL_SSL`, `kafka.sasl.mechanism=OAUTHBEARER`
  - JAAS `kafkashaded…OAuthBearerLoginModule required clientId=".." clientSecret=".." scope="https://<ns>.servicebus.windows.net/.default"`
  - `kafka.sasl.oauthbearer.token.endpoint.url=https://login.microsoft.com/<tenant>/oauth2/v2.0/token`
  - `kafka.sasl.login.callback.handler.class=kafkashaded…OAuthBearerLoginCallbackHandler`
  - Supported on dedicated compute (DBR 12.2+), standard (DBR 14.3+), and non-UC pipelines. **Not on UC pipelines.**
- Certificate-based Entra auth is not supported.

### Q: Offsets and consumer groups: how do they behave?
- **Spark tracks offsets in the checkpoint**, not in a Kafka consumer group. `startingOffsets` (`latest` default / `earliest` / per-partition JSON) is read **only when the query starts with a new checkpoint**. After that, the checkpoint wins.
- To reprocess from the beginning: new checkpoint location + `startingOffsets=earliest`, within the Event Hubs retention window (Standard max 7 days, Premium/Dedicated 90).
- If the stream is down longer than retention, offsets expire. `failOnDataLoss=true` (the default) fails the query, while `false` skips and continues.
- Spark generates a unique consumer `group.id` per query by default. Don't share `kafka.group.id` between queries.
- Throughput: partitions bound read parallelism. `maxOffsetsPerTrigger` caps the batch size, and `minPartitions` can split partitions into more Spark tasks.

### Q: In a Lakeflow pipeline?
Same Kafka options inside `@dp.table` returning `spark.readStream.format("kafka")…`, or SQL `CREATE OR REFRESH STREAMING TABLE t AS SELECT * FROM STREAM read_kafka(bootstrapServers => '<ns>.servicebus.windows.net:9093', subscribe => 'telemetry', ...)`.
- Read the key with `dbutils.secrets.get` (or `secret()` in SQL), with names passed through pipeline configuration (`spark.conf.get`).
- No checkpoint to manage.
- Set `pipelines.reset.allowed=false` on the bronze table: a full refresh would otherwise wipe data that Event Hubs no longer retains.

### Q: Exam trap: "Install the `azure-eventhubs-spark` Maven library on the pipeline."
Not allowed: pipelines don't accept third-party JVM libraries, and the library isn't in the runtime. Use the Kafka endpoint.

### Q: Exam trap: "Stream connects but returns no rows."
`startingOffsets` defaults to `latest`, so no new events have arrived yet. Or the topic name (event hub) is wrong.

### Q: Which ADF activities run Databricks work?

|---|---|---|

Return a value with `dbutils.notebook.exit("...")`, read in ADF as `@activity('nb').output.runOutput` (**≤ 2 MB**; JSON properties via `.runOutput.prop`) |

### Q: When ADF vs Lakeflow Connect vs notebooks/Auto Loader vs Lakeflow Jobs?
| Scenario | Pick |
|---|---|

| Files landing in ADLS, custom parsing, schema evolution | **Auto Loader** in a notebook/job or a pipeline (M1 §1) |
| Streaming from Event Hubs/Kafka | Structured Streaming / pipeline with the **Kafka connector** (§11) |
| Enterprise orchestration **across many Azure services** (Copy from 90+ connectors, on-prem via **self-hosted integration runtime**, Functions, Logic Apps, SQL stored procs) with Databricks as one step; existing ADF estate | **Azure Data Factory** calling a Databricks Job/Notebook activity |
| Orchestration where every task is in Databricks (notebooks, pipelines, SQL, dbt), with repair runs, file-arrival/table triggers | **Lakeflow Jobs** (M5 §11+) |
| Query an external database in place without copying | **Lakehouse Federation** (§22) |

### Q: Exam trap: "ADF must trigger an existing multi-task Databricks job on serverless and pass a run date."
**Databricks Job activity** with `jobParameters`. A Notebook activity runs a single notebook on a cluster defined in the linked service.

### Q: Exam trap: "ADF linked service with managed identity returns 403."
The data factory's MI lacks the **Contributor** role on the Databricks workspace resource. The fix is Azure RBAC, not a PAT or secret scope.

## §13 Compute: pools

### Q: What do pools do, and how are they sized?
A set of **idle, ready VMs** that clusters attached to the pool draw from. They give **faster cluster start and autoscale**. **No DBUs** are charged for idle instances, but the **VM (instance provider) cost applies**.

| Setting | Meaning |
|---|---|
| **Min idle instances** | Always kept idle and never terminated. They're replenished when clusters consume them |
| **Max capacity** | Cap on **idle + in-use** instances. Exceeding it on autoscale gives `INSTANCE_POOL_MAX_CAPACITY_FAILURE`. Set it only for quota, team isolation (pool A 50 / pool B 50), or cost |
| **Idle instance auto termination** | Minutes an instance **above min idle** may stay idle before being released |
| Instance type | **Fixed at creation, can't be edited.** Driver and workers can use the same or different pools (`driver_instance_pool_id`, `instance_pool_id`) |
| Preloaded runtime | Even faster start when the cluster uses that DBR version |
| **All Spot** | **All** nodes, including the driver, are spot, and evicted instances aren't replaced with on-demand. Use an **on-demand pool for the driver** |
| Tags | Pool tags propagate to VMs and DBU usage |

- Creating a pool needs the **Allow pool creation** entitlement (admins by default).
- Pool ACLs are **NO PERMISSIONS / CAN ATTACH TO / CAN MANAGE**.
- Cluster policies can pin `instance_pool_id`, forcing pool use.
- For pools to help, cluster **min workers ≤ pool min idle**, and **max workers ≤ pool max capacity**, or creation fails.

### Q: When NOT to use pools?
Databricks recommends **serverless** over pools where the workload supports it. Pools don't apply to serverless or SQL warehouses. Avoid large min-idle settings for spiky, rare jobs, because you pay VM cost 24/7.

### Q: Exam trap: "Cut job cluster startup from ~5 min, accept some idle VM cost, classic compute required."
A **pool with min idle > 0** (and a preloaded runtime). Not autoscaling, not Photon.

## §14 Compute: libraries and init scripts

### Q: What scopes and sources exist?
| Scope | How | Persistence / who sees it |
|---|---|---|
| **Compute-scoped** | Compute → Libraries → Install new: **PyPI/Maven/CRAN**, **workspace files**, **UC volumes**, cloud storage (ABFSS), local upload. A **`requirements.txt`** is supported (DBR 15.0+) | All notebooks/jobs on that compute. Reinstalled on every start. Needs **CAN MANAGE** on the compute |
| **Notebook-scoped (Python)** | `%pip install pkg==1.2`, `%pip install /Volumes/c/s/v/my.whl`, `%pip install -r /Workspace/.../requirements.txt` | **This notebook session only.** Doesn't affect other notebooks. Must be reinstalled each session. Put it at the **top** of the notebook. `%pip` doesn't auto-restart the Python process, so after upgrading a package (or installing from `requirements.txt`) call `dbutils.library.restartPython()`, which loses Python state |
| **Job task libraries** | `libraries:` on the task (whl, jar, pypi, maven), or serverless **environments** (`dependencies:`) | That task's compute |
| **Serverless notebooks/jobs** | **Environment** side panel / base environment YAML. Compute-scoped libraries don't exist there | — |

- **DBFS-root libraries are deprecated** (disabled by default on DBR 15.1+). **Workspace libraries (legacy)** are deprecated. Workspace *files* are fine.
- Recommendation: **UC volumes on standard access mode** (grant `READ VOLUME` + `USE CATALOG`/`USE SCHEMA`). On standard access mode, **JARs, Maven coordinates and init scripts must be on the metastore allowlist** (`MANAGE ALLOWLIST` privilege).
- **JARs can't be notebook-scoped.**
- Python import precedence (high to low): CWD in a Git folder → Git folder root → notebook-scoped `%pip` → compute-scoped → DBR built-ins → CWD outside Git folders → `sys.path` appends.

### Q: Init scripts?
Shell scripts that run on **every node at startup, before the Spark driver/executor JVM starts**. Use them for OS packages, certificates and agents.
- **Cluster-scoped** (recommended): stored in **workspace files**, **UC volumes**, or ABFSS.
- **Global**: run on every cluster in the workspace, admin only. Use them sparingly.
- **DBFS-stored init scripts are end-of-life.**
- An init script failure **fails the cluster start**.
- Databricks **doesn't recommend installing Python libraries via init scripts**. Use library mechanisms instead.
- They don't apply to serverless.

### Q: Exam trap: "One notebook needs pandas 2.x while others on the shared cluster need the default."
Notebook-scoped `%pip install` in that notebook. A compute-scoped install would change it for everyone.

## §15 Compute: permissions, access modes, runtime/ML, termination, node types

### Q: Compute permission levels?
| Ability | CAN ATTACH TO | CAN RESTART | CAN MANAGE |
|---|---|---|---|
| Attach notebook, view Spark UI and metrics | ✓ | ✓ | ✓ |
| Start / restart / **terminate** | | ✓ | ✓ |
| Edit config, **attach libraries**, resize, change permissions, view driver logs (default) | | | ✓ |

- There's also NO PERMISSIONS, and **CAN VIEW (Beta)**: Spark UI and metrics only, no attach.
- Any user with **CAN RUN on a notebook** that is already attached can use that compute implicitly.
- JDBC/ODBC clients need CAN ATTACH TO, plus CAN RESTART to autostart a terminated cluster.
- SQL warehouses use **CAN USE / CAN MONITOR / CAN MANAGE** (and IS OWNER). Different object, different levels.
- Creating compute needs **unrestricted cluster creation** or access to a **compute policy** (e.g. Personal Compute).

### Q: Access modes?
| Mode (old name) | Who | Languages | Use |
|---|---|---|---|
| **Standard** (shared) | Many users concurrently, isolated by **Lakeguard** | Python, SQL, Scala (DBR 13.3+). **No R**, no RDD APIs | **Default and recommended** for most ETL, SQL and collaboration |
| **Dedicated** (single user) | One user **or one group** (group = Public Preview, DBR 15.4+) | Python, SQL, Scala, **R** | **ML runtime, GPUs, RDD APIs, R**, privileged machine access. Fine-grained access control (row filters/masks, ST/MV reads) needs DBR 15.4+ and serverless enabled |
| No isolation shared (legacy) | Anyone, no isolation | — | Not UC. Don't use |

- **Auto** access mode (UI default) picks **Standard** unless you choose an ML runtime, a GPU instance, or DBR < 14.3, in which case it picks **Dedicated**.
- Only admins can assign dedicated compute to **another user**.

### Q: Runtime, ML and Photon?
- Pick the **latest LTS** DBR.
- The **Machine learning** checkbox selects **Databricks Runtime ML**: TensorFlow, PyTorch, XGBoost, MLflow and friends preinstalled. It **automatically sets Dedicated access mode**. Choose it only for GPU, distributed ML or AutoML work. Its large library set can conflict with your own dependencies.
- **Photon** helps SQL/DataFrame workloads, not RDDs/UDF-heavy Python. Details in M4 §19.

### Q: Termination and node types?
- **Auto-termination** (all-purpose): **10–10,000 minutes** of inactivity. `0` or unchecked turns it off.
  - Inactive means all commands, Spark jobs, Structured Streaming, JDBC calls and web-terminal activity have finished.
  - Idle time still bills DBUs and VMs until termination.
- **Job compute** terminates when the job ends.
- Terminated compute is **deleted 30 days after termination** unless it is **pinned**.
- A job scheduled on a terminated all-purpose cluster **autostarts** it.
- Restart long-running clusters regularly to pick up image patches.
- **Node types**: general purpose (D-series) for most ETL, memory-optimized (E-series) for large joins/caching/shuffle, compute-optimized (F-series) for CPU-bound work, storage-optimized (L-series, local NVMe) for disk cache-heavy work, GPU (NC/ND) for DL.
  - Driver type defaults to the worker type. Enlarge it only for big `collect()`/`toPandas()` or many attached notebooks.
  - **Single node** compute (0 workers, Spark local mode) suits small data and pandas-style ML.
- Autoscaling, spot and policies: M4 §20.

### Q: Exam trap: "A data scientist needs R on UC data with row filters."
**Dedicated** access mode on DBR 15.4+ (serverless enabled for FGAC). Standard doesn't support R.

### Q: Exam trap: "The user can restart the cluster but can't install a library."
Expected. Installing libraries needs **CAN MANAGE**. CAN RESTART only covers start, restart and terminate.

## §16 Data modeling: granularity and temporal (history) tables

### Q: How do I choose table granularity?
State the **grain** explicitly: "one row per order line per day", "one row per sensor reading".
- Store the **lowest grain that requirements need** in silver/fact tables, because you can always aggregate up.
- Build **pre-aggregated gold** (daily/monthly, per store) for dashboards. A materialized view is a good fit (M1 §8).
- Mixing grains in one table (order headers and lines) causes double counting.
- **Column granularity**:
  - Keep atomic values (separate `street`, `city`, `postcode` instead of one address string when you filter by city).
  - Keep the **full timestamp** and derive `order_date`. A generated column (`GENERATED ALWAYS AS (CAST(order_ts AS DATE))`) gives a cheap date filter and a clustering key.
  - Store amounts at transaction level, not only rounded totals.

### Q: Which history mechanism: SCD2 vs time travel vs CDF?
| Need | Mechanism | Why / limits |
|---|---|---|
| Business "as-of" queries over years ("customer's segment on 2024-03-01"), auditable attribute history | **SCD Type 2 temporal table**: `valid_from`, `valid_to`, `is_current` (AUTO CDC `STORED AS SCD TYPE 2` gives `__START_AT`/`__END_AT`; M1 §11, or a MERGE pattern) | Permanent, queryable with plain SQL, survives VACUUM |
| Undo a bad write, reproduce last week's ML training set, debug | **Delta time travel** (`VERSION AS OF` / `TIMESTAMP AS OF`; M2 §11) | Limited by `delta.logRetentionDuration` (30 days default) and **VACUUM** (`deletedFileRetentionDuration` 7 days). **Not a history-retention strategy** |
| Propagate row-level inserts/updates/deletes downstream incrementally | **Change Data Feed** (`delta.enableChangeDataFeed`; `_change_type`, `_commit_version`, `_commit_timestamp`; M2 §14) | Feeds SCD2/silver→gold. Subject to the same retention/VACUUM. A **source** for history, not the history itself |
| Only current state | **SCD Type 1** (overwrite) | No history |

### Q: Exam trap: "Auditors need 7 years of attribute changes. Use time travel with `logRetentionDuration = 2555 days`."
Wrong design. Every old file is retained, VACUUM stops being useful, and storage and log replay costs grow. Build an **SCD2 history table** (fed by CDF or CDC).

## §17 File/table format choice; managed vs external recap

### Q: Which format when?
| Format | Choose when | Avoid because |
|---|---|---|
| **Delta** (default) | Any UC table you write: ACID, MERGE/UPDATE/DELETE, time travel, CDF, liquid clustering, deletion vectors, constraints, streaming source/sink, predictive optimization | — |
| **Delta + Iceberg reads (UniForm)** | One copy of data must be **read by Iceberg engines** (Snowflake, Trino, Athena) via the UC Iceberg REST catalog. Set `delta.enableIcebergCompatV2=true` + `delta.universalFormat.enabledFormats='iceberg'`, which needs column mapping | IcebergCompatV2 **can't coexist with deletion vectors** (purge with `REORG … UPGRADE UNIFORM`). IcebergCompatV3 (DBR 18+) adds DV support. External engines read only |
| **Managed Iceberg** (`CREATE TABLE … USING ICEBERG`, DBR 16.4+, serverless for metadata) | External Iceberg engines must **write** too, or the org standard is Iceberg | Fewer Databricks-only features than Delta |
| **Parquet** (plain, external) | Interchange/export files for a system that only reads Parquet | No ACID, no MERGE, no time travel. Small-file and consistency issues |
| **CSV / JSON** | **Landing/bronze inputs** from source systems, human-readable exports | No schema or types, slow to scan, no predicate pushdown. Never as the curated table format |
| Avro / ORC / XML | Accept as sources (Auto Loader handles them) | Convert to Delta in bronze |

### Q: Managed vs external recap?
**Managed is the default and recommended.** UC owns the lifecycle: `DROP` deletes the data (recoverable for 7 days with `UNDROP`), and predictive optimization and automatic liquid clustering apply.
Use **external** when the data must live at a specific path that other tools also read or write, or the data must survive a DROP. Details in M3 §6.

## §18 Column data types

### Q: Which type choices are exam material?
| Data | Use | Don't |
|---|---|---|
| Money, quantities needing exact arithmetic | **`DECIMAL(p, s)`** (max precision 38; e.g. `DECIMAL(18,2)`). Bare `DECIMAL` = `DECIMAL(10,0)`, which drops cents | `DOUBLE`/`FLOAT`: binary floating point gives rounding drift (`0.1 + 0.2 ≠ 0.3`) and sums that don't reconcile |
| Measurements, scientific values, ML features | `DOUBLE` | — |
| An instant in time (event times from many zones) | **`TIMESTAMP`** (= with local time zone): stored as a UTC instant, displayed in the session time zone (`spark.sql.session.timeZone`) | — |
| A wall-clock value that must not shift by zone (store opening time, "local business date-time" from the source) | **`TIMESTAMP_NTZ`**: no zone conversion ever | It adds the `timestampNtz` table feature (protocol upgrade), so older readers break |
| Dates | `DATE` | Strings like `'20260131'`: no validation, bad pruning |
| Identifiers | `BIGINT` (or `STRING` for codes with leading zeros, e.g. postcodes) | `INT` for fast-growing keys (overflows at 2.1B) |
| Flags | `BOOLEAN` | 'Y'/'N' strings |
| Semi-structured JSON with evolving shape | **`VARIANT`** (DBR 15.3+), or `STRUCT` when the shape is stable | Raw `STRING` JSON parsed with `from_json` on every query |
| Text | `STRING` (`VARCHAR(n)`/`CHAR(n)` enforce length on Delta, rarely needed) | — |

### Q: How do type checks and safe casts work?
- **Schema enforcement** on write rejects mismatched types. Evolution: M2 §16.
- **`try_cast(x AS INT)`**, `try_to_timestamp`, `try_divide`, `try_to_number` return **NULL instead of an error** under ANSI mode (on by default in Databricks SQL).
- Quarantine pattern: `WHERE try_cast(amount AS DECIMAL(18,2)) IS NULL AND amount IS NOT NULL` finds bad rows.
- Type widening (e.g. INT→BIGINT, `delta.enableTypeWidening`) is covered in M2.

### Q: Exam trap: "Monthly revenue in the report is off by fractions of a cent versus the ERP."
`DOUBLE` used for amounts. Change to `DECIMAL(18,2)` (or the source's scale).

## §19 Data profiling

### Q: Which profiling tools exist?
| Tool | What you get | When |
|---|---|---|
| Notebook result → **Data Profile** tab (`display(df)` → `+` → Data Profile) | Per-column counts, nulls/missing %, distinct, min/max/mean/stddev, histograms, top values | Quick interactive look |
| **`dbutils.data.summarize(df, precise=False)`** | Same profile, programmatic. Approximate by default (`precise=True` for exact) | Notebook automation |

### Q: Exam trap: "Track null rate and distribution drift of a production table daily and alert on change."
**Data profiling (data quality monitoring) with a time series profile** + an alert on the drift metrics table. Not ad-hoc `summary()`.

## §20 Data quality without pipelines: constraints, nulls, duplicates

### Q: Which constraints does Delta enforce?
| Constraint | Syntax | Enforced? |
|---|---|---|
| `NOT NULL` | In `CREATE TABLE` (`id BIGINT NOT NULL`) or `ALTER TABLE t ALTER COLUMN c SET NOT NULL` / `DROP NOT NULL` | **Yes**. Existing rows are verified first |
| `CHECK` | `ALTER TABLE t ADD CONSTRAINT valid_amt CHECK (amount >= 0 AND currency IN ('EUR','USD'))`; `ALTER TABLE t DROP CONSTRAINT valid_amt` | **Yes**. `ADD CONSTRAINT` **fails if any existing row violates it** |
| `PRIMARY KEY` / `FOREIGN KEY` / `UNIQUE` (Preview) | `CONSTRAINT pk PRIMARY KEY (id)` (PK columns must be NOT NULL) | **No, informational only.** Used by the optimizer (with `RELY`), BI tools, Genie |

- A violating write **fails the whole transaction** (no partial write, no row dropping). That's the difference from pipeline expectations (M1 §9), which can warn, drop or fail.
- CHECK expressions must be deterministic, and can't use **UDFs, aggregate functions, window functions, or functions returning multiple rows**. So a CHECK can't enforce uniqueness or cross-row cardinality. Use MERGE logic or a dedup step plus a test query.
- Adding a constraint upgrades the writer protocol (≥3). View constraints in `SHOW TBLPROPERTIES` (`delta.constraints.<name>`) or `DESCRIBE DETAIL`.
- Removing CHECK constraints completely, with a protocol downgrade: `ALTER TABLE … DROP FEATURE checkConstraints` (DBR 15.4+).

### Q: Range, cardinality and type checks without pipelines?
- **Range**: `CHECK (qty BETWEEN 1 AND 10000)`.
- **Nullability**: `NOT NULL`.
- **Domain**: `CHECK (status IN (...))`.
- **Type**: column types, schema enforcement, `try_cast` quarantine.
- **Cardinality/uniqueness**: assertion queries in a job task, e.g. `SELECT id FROM t GROUP BY id HAVING count(*) > 1` → `assert` empty, with an If/else task or SQL alert on the result.

### Q: Handling missing/null values?
```python
df.na.drop(how="any", subset=["order_id", "amount"])          # dropna(how='any'|'all', thresh=n, subset=[..])
df.na.fill({"channel": "unknown", "discount": 0})               # fillna; type-matched per column
df.withColumn("ship_dt", F.coalesce("ship_dt", "order_dt"))     # first non-null
df.filter(F.col("email").isNull())                              # never  == None
```
SQL: `coalesce(a, b, 'n/a')`, `nvl(a, b)`, `ifnull`, `nullif(x, 0)` (avoids divide-by-zero), `count_if(c IS NULL)`, `c <=> d` (null-safe equality).
Choose **drop vs default vs impute vs quarantine** per business rule. Don't fill with 0 where 0 has meaning.

### Q: Duplicates?
```python
df.dropDuplicates()                          # full-row duplicates (= distinct())
df.dropDuplicates(["order_id"])              # one row per key, but WHICH row is arbitrary
from pyspark.sql.window import Window
w = Window.partitionBy("order_id").orderBy(F.col("updated_at").desc(), F.col("ingest_ts").desc())
latest = df.withColumn("rn", F.row_number().over(w)).filter("rn = 1").drop("rn")   # deterministic: keep newest
```
```sql
SELECT * FROM bronze.orders
QUALIFY row_number() OVER (PARTITION BY order_id ORDER BY updated_at DESC) = 1;
-- idempotent load that never inserts dupes:
MERGE INTO silver.orders t USING (dedup_source) s ON t.order_id = s.order_id
WHEN MATCHED AND s.updated_at > t.updated_at THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;
```
- `row_number` gives exactly one row per key. `rank`/`dense_rank` keep **ties**, so duplicates survive.
- `dropDuplicates` treats NULL keys as equal.
- Streaming dedup: `dropDuplicatesWithinWatermark` (M4 §7).

### Q: Exam trap: "`ALTER TABLE ... ADD CONSTRAINT chk CHECK (amount > 0)` fails."
Existing rows violate it. Fix or quarantine those rows first, then add the constraint.

### Q: Exam trap: "Keep the most recent record per customer; `dropDuplicates(['customer_id'])` after `orderBy(desc)`."
Not guaranteed: `dropDuplicates` doesn't honor a prior sort. Use `row_number()` over a window.

## §21 Error handling in notebooks, pipelines and jobs

### Q: Notebook-level patterns?
```python
import json, time
def run_with_retry(path, timeout_s, args, max_retries=2):
    for attempt in range(max_retries + 1):
        try:
            return dbutils.notebook.run(path, timeout_s, args)     # raises on child failure or timeout
        except Exception as e:
            if attempt == max_retries:
                raise                                              # re-raise => task FAILS => job retry/alerts fire
            time.sleep(30 * (attempt + 1))

try:
    out = json.loads(run_with_retry("./load_orders", 1800, {"run_date": run_date}))
    if out["rows"] == 0:
        dbutils.jobs.taskValues.set("status", "empty")             # downstream If/else can branch on it
except Exception as e:
    log_error(table="ops.etl_errors", step="load_orders", err=str(e))   # your own audit table
    raise
```
- **`dbutils.notebook.exit(value)` ends the notebook as SUCCEEDED** with a string value. **It does not fail the task.** To fail, **raise** an exception (or let one propagate).
  - The value is returned to `dbutils.notebook.run` (≤ 5 MB) or to ADF `runOutput` (≤ 2 MB).
  - It doesn't stop a background streaming query: call `query.stop()` first.
- `dbutils.notebook.run(path, timeout_seconds, args)`: `0` = no timeout, it throws on timeout or failure, `args` are strings that set widgets, and the child runs in a separate context. Details and the `%run` comparison are in M5 §23.
- Catch **specific** errors where you can (`AnalysisException` for missing tables, Py4J errors). Swallowing all exceptions hides failures from Jobs and alerts.
- Data-level errors: `try_cast`/`try_divide`, the Auto Loader `_rescued_data` column, `badRecordsPath` / `mode=PERMISSIVE` + `columnNameOfCorruptRecord` for malformed CSV/JSON, quarantine tables.
- Idempotency is what makes retries safe: MERGE/replaceWhere instead of blind append, plus streaming checkpoints. A retried append duplicates rows.

### Q: Job and pipeline level (cross-ref M5 §13, §17, §18)?
- Task **retries** (`max_retries`, `min_retry_interval_millis`, `retry_on_timeout`) and **timeouts** (`timeout_seconds`).
- **Run-if** conditions (`ALL_SUCCESS`, `AT_LEAST_ONE_FAILED`, `ALL_DONE`, …) for cleanup or alert tasks.
- **Notifications**, and **repair run** (re-run only failed and dependent tasks).
- Continuous jobs retry with exponential backoff.
- Pipelines (production run behavior): automatic retries and cluster restarts. Expectations `FAIL UPDATE` aborts the update atomically.

### Q: Exam trap: "Notebook catches the exception and calls `dbutils.notebook.exit('FAILED')`. Why didn't the job's failure email fire?"
`exit` marks the task **Succeeded**. Re-raise the exception (or `raise Exception(...)`) after logging.

## §22 Lakehouse Federation: connections and foreign catalogs (short recap)

### Q: What is it and how is it set up?
Query external databases **in place** (read-only) through UC governance. No data is copied, and filters/aggregates are pushed down where possible.
```sql
CREATE CONNECTION sqlsrv_erp TYPE sqlserver               -- also: mysql, postgresql, redshift, snowflake, sqldw, databricks, ...
OPTIONS (host 'erp.database.windows.net', port '1433',
         user secret('kv-erp', 'user'), password secret('kv-erp', 'pwd'));   -- use secret(), never literals

CREATE FOREIGN CATALOG erp USING CONNECTION sqlsrv_erp OPTIONS (database 'ERPDB');

GRANT USE CATALOG, USE SCHEMA, SELECT ON CATALOG erp TO `analysts`;
SELECT * FROM erp.dbo.customers WHERE country = 'NL';
```
- Privileges:
  - `CREATE CONNECTION` on the metastore (or metastore admin) to create the connection.
  - `CREATE CATALOG` on the metastore **plus** connection ownership or **`CREATE FOREIGN CATALOG`** on the connection to create the catalog.
  - `USE CONNECTION` lets others use the connection.
- Requires DBR 13.3 LTS+ or a pro/serverless SQL warehouse.
- Auth types depend on the source. SQL Server supports username/password, **OAuth**, and **OAuth M2M**.
- `CREATE CONNECTION` is for federation and HTTP connections. **Lakeflow Connect** ingestion connections are created in Catalog Explorer, the Connections API or the CLI.
- Federation vs ingestion: federation for ad-hoc/low-volume access and POCs. **Ingest** (Lakeflow Connect, ADF) for heavy, repeated analytics, history, and to offload the source.
- HMS / Glue federation (catalog federation): M3 §20.

### Q: Exam trap: "Analysts must join SQL Server customers with lakehouse orders today, no pipelines, governed by UC."
Connection + foreign catalog (Lakehouse Federation).
