## §0 Lakeflow Spark Declarative Pipelines (formerly DLT): names

### Q: What is it?
A declarative ETL framework. You declare **streaming tables, materialized views, views and flows** in SQL or Python. The pipeline infers the DAG from table references, then handles orchestration, checkpoints, retries, schema/state management, data quality and lineage. Its open-source core is **Apache Spark Declarative Pipelines (SDP)**, in Spark 4.1+. The docs use "Lakeflow pipelines", "Lakeflow Spark Declarative Pipelines" and "Spark Declarative Pipelines on Lakeflow" for the same product.

### Q: What replaced what? (the exam may use either name)
| Legacy (DLT) | Current |
|---|---|
| Delta Live Tables | Lakeflow (Spark) Declarative Pipelines |
| `import dlt` | `from pyspark import pipelines as dp` (`dlt` still works) |
| `@dlt.table` (streaming DF → ST, batch DF → MV) | `@dp.table` (ST) / `@dp.materialized_view` (MV). `@dp.table` given a batch DF still makes an MV, but `@dp.materialized_view` is recommended |
| `@dlt.view` | `@dp.temporary_view` |
| `dlt.apply_changes()` | `dp.create_auto_cdc_flow()` (same signature) |
| `dlt.apply_changes_from_snapshot()` | `dp.create_auto_cdc_from_snapshot_flow()` |
| `APPLY CHANGES INTO` | `CREATE FLOW f AS AUTO CDC INTO` (`APPLY CHANGES` still available) |
| `CREATE LIVE TABLE` / `CREATE STREAMING LIVE TABLE` | `CREATE MATERIALIZED VIEW` / `CREATE STREAMING TABLE` |
| `LIVE.tbl` references | Unqualified names resolve to the pipeline's default catalog/schema. `LIVE.` is silently ignored in default publishing mode and is legacy-only |
| `@dlt.table(temporary=True)` | `@dp.table(private=True)` |
| Workflows | Lakeflow Jobs |
| Development / Production mode toggle | "Update run behavior", chosen by how the update is triggered (§13) |

### Q: Which features are Databricks-only (not in Apache SDP)?
`create_auto_cdc_flow`, `create_auto_cdc_from_snapshot_flow`, expectations (`dp.expect*`), the event log, and continuous mode.

### Q: Exam trap: `SELECT * FROM LIVE.bronze` in a new pipeline. Error?
No. `LIVE.` is silently ignored in the default publishing mode and the name resolves to the default schema. It only means something in legacy-publishing-mode pipelines.

## §1 Auto Loader (`cloudFiles`)

### Q: What is it?
A Structured Streaming source (`format("cloudFiles")`). It incrementally discovers and ingests new files from ADLS/S3/GCS/UC volumes, with **exactly-once** processing tracked in the checkpoint. It is **streaming only**, so you read it with `spark.readStream`. It does **not** guarantee file order in any discovery mode.

### Q: How is it used?
```python
# Job/notebook: you own schemaLocation + checkpoint
(spark.readStream.format("cloudFiles")
   .option("cloudFiles.format", "json")
   .option("cloudFiles.schemaLocation", "/Volumes/c/s/v/_schemas/orders")
   .option("cloudFiles.inferColumnTypes", "true")
   .option("cloudFiles.schemaHints", "amount DECIMAL(18,2)")
   .load("abfss://landing@acct.dfs.core.windows.net/orders/")
   .select("*", "_metadata.file_path")
 .writeStream
   .option("checkpointLocation", "/Volumes/c/s/v/_chk/orders")
   .trigger(availableNow=True)
   .toTable("main.bronze.orders"))

# Inside a pipeline: no schemaLocation, no checkpoint, no writeStream
@dp.table
def bronze_orders():
    return (spark.readStream.format("cloudFiles")
            .option("cloudFiles.format", "json")
            .load("abfss://landing@acct.dfs.core.windows.net/orders/"))
```

### Q: Which options and defaults must I know?
| Option | Default | Note |
|---|---|---|
| `cloudFiles.format` | required | json, csv, xml, parquet, avro, orc, text, binaryFile |
| `cloudFiles.schemaLocation` | — | **Required outside pipelines** for inference/evolution (can be the checkpoint dir). **Managed automatically in pipelines** |
| `cloudFiles.inferColumnTypes` | **false** | JSON/CSV/XML columns (including nested fields) are inferred as **STRING** |
| `cloudFiles.schemaHints` | — | DDL string. Used **only if you don't supply a schema**. Works with `inferColumnTypes` on or off. Can add columns that aren't present yet |
| `cloudFiles.schemaEvolutionMode` | `addNewColumns` without a schema / **`none` with a schema** | §2 |
| `cloudFiles.includeExistingFiles` | true | Evaluated **only on the stream's first start** |
| `cloudFiles.maxFilesPerTrigger` | 1000 | Soft limit. With `maxBytesPerTrigger`, whichever limit is hit first applies |
| `cloudFiles.allowOverwrites` | false | Reprocess files modified after discovery |
| `cloudFiles.partitionColumns` | inferred from `k=v` dirs | New partition levels are ignored unless listed |
| `cloudFiles.useManagedFileEvents` | false (DBR 18.1+: `if_available`) | §3 |
| `cloudFiles.useNotifications` | false | Classic notifications, §3 |

Schema inference samples the **first 50 GB or 1000 files**, whichever limit is hit first. Parquet/Avro use their encoded types. If one Parquet column has different types across files, Auto Loader picks the widest.

### Q: What are the advantages?
- Scales to millions of files per hour (with notifications/file events).
- Exactly-once processing.
- Schema inference, evolution and rescue.
- Lower cost than COPY INTO at scale because it splits work into micro-batches.
- Works in Jobs, notebooks, pipelines, and via SQL `read_files` in streaming tables.

### Q: What are the disadvantages and limitations?
- Streaming only.
- Harder to reprocess a chosen subset of files (COPY INTO is easier for that).
- No ordering guarantee.
- `addNewColumns` intentionally **fails** the stream once per schema change, so you need retries.
- On serverless notebooks/jobs, only the `availableNow` and `once` triggers are allowed.

### Q: When should I use it, and when not?
- **Use it** for continuous or large-volume file landing, evolving schemas, or bronze ingestion in pipelines.
- **Don't use it** for a one-time load of a few files with simple SQL (COPY INTO or `read_files` CTAS is simpler).
- **Don't use it** for SaaS or database sources (use Lakeflow Connect).
- **Don't use it** for message buses (use the Kafka/Event Hubs source).

### Q: How does it compare to COPY INTO?
| | Auto Loader | COPY INTO |
|---|---|---|
| Scale | Millions of files | Thousands of files |
| Mode | Streaming (`availableNow` = batch-like) | Batch SQL command |
| Schema evolution | Rich: modes, rescue, hints | `mergeSchema` only |
| Reprocess a subset | Hard | Easy (`FILES=`, `PATTERN=`, `force`) |
| State | Checkpoint | Load history in the Delta table |

### Q: Exam trap: JSON ingested with Auto Loader, every column is STRING. Bug?
No, that's the default (`inferColumnTypes=false`). Fix it with `cloudFiles.inferColumnTypes=true` and/or `cloudFiles.schemaHints`. `read_files` defaults to `inferColumnTypes=true`, the opposite.

### Q: Exam trap: you set `includeExistingFiles=false` on a stream that has already run. What happens?
Nothing. The option only applies on the first start. You need a new checkpoint.

## §2 Auto Loader schema evolution & `_rescued_data`

### Q: What does each `cloudFiles.schemaEvolutionMode` do when a new column appears?
| Mode | Fails? | Schema updated? | New data goes to |
|---|---|---|---|
| `addNewColumns` (**default without a schema**) | **Yes, once**. The new column is merged into the schema at `schemaLocation` first, then it throws `UnknownFieldException`. A restart resumes with the new schema | Yes (appended at end). Existing column **types never change** | New column |
| `addNewColumnsWithTypeWidening` (Preview, DBR 16.4+) | Yes, once | Yes, and widens types (int→long, float→double) | Unsupported type changes → rescued column |
| `rescue` | **No** | **No** | `_rescued_data` |
| `failOnNewColumns` | **Yes, and stays failed** until you update the provided schema or remove the offending file | No | — |
| `none` (**default with a schema**) | No | No | **Dropped**, unless `rescuedDataColumn` is set |

### Q: How is it used?
```python
.option("cloudFiles.schemaEvolutionMode", "rescue")
.option("rescuedDataColumn", "_rescued_data")   # needed only if you pass .schema(...)
```
SQL: `read_files(..., schemaEvolutionMode => 'rescue')`.

### Q: What is `_rescued_data`?
A column added automatically **when the schema is inferred**. It holds a JSON blob of the data that didn't fit, plus the **source file path**. Data lands there when the column is **missing from the schema**, has a **type mismatch**, or has a **case mismatch** (unless `readerCaseSensitive=false`). Empty-struct records go there too.

With a rescued column configured:
- `DROPMALFORMED` doesn't drop rows for type mismatches, and `FAILFAST` doesn't throw for them. Only truly corrupt records are dropped or failed.
- `badRecordsPath` holds only malformed records.

### Q: What are the advantages and disadvantages of each mode?
- **`addNewColumns`**: no data loss and the schema stays current. Downside: one failure per change, and it needs Job retries.
- **`rescue`**: never stops and the downstream schema is stable. Downside: someone has to parse `_rescued_data` later.
- **`failOnNewColumns`**: strict contract. Downside: manual intervention.
- **`none`**: stable and never fails. Downside: **silent data loss**.

### Q: When should I use which mode?
- "Never stop **and** don't change the schema" → `rescue`.
- "Auto-add columns" → `addNewColumns` plus a Job/pipeline with retries.
- "Schema is a contract, halt on drift" → `failOnNewColumns`.
- "Known fixed schema, ignore extras" → `none`.

### Q: How do schema hints compare to a full schema?
- **Hints** override or add specific columns and **keep evolution available**. `addNewColumns` works with hints.
- **A full `.schema()`** disables inference, sets the default mode to `none`, and **forbids `addNewColumns`**.
- For Parquet, a hint tells the reader which type to use (it isn't a cast). A mismatch goes to the rescued column.

### Q: Exam trap: you pass an explicit schema and a new column appears. Where does it go?
Nowhere. The default mode with a schema is `none`, so the column is dropped. Set `rescuedDataColumn` (or use `rescue`) to keep it.

### Q: Exam trap: the stream fails with `UnknownFieldException` under `addNewColumns`. What's the fix?
Just restart; the schema is already updated. In production, use a Lakeflow Job with retries. Don't switch to `none` "to fix it".

## §3 Auto Loader file discovery modes

### Q: What are the modes?
| Mode | Option | Setup | Scale | Cost |
|---|---|---|---|---|
| **File events** (recommended) | `cloudFiles.useManagedFileEvents=true` | One time: enable file events on the **UC external location**. Databricks manages Event Grid + Storage Queue, one per location | Millions of files/hr | Lowest |
| Classic file notification | `cloudFiles.useNotifications=true` | Per-stream subscription and queue, plus credential options (`cloudFiles.queueName`, service credential, …) | Millions of files/hr | Medium |
| Directory listing (default) | none | Just read access | Degrades with directory size (LIST every trigger) | Highest (LIST API calls) |

### Q: What are the advantages and limitations of each?
- **File events**
  - Advantages: no per-stream queues, no notification limits, no tuning of `fetchParallelism`, automatic cleanup.
  - Limitations: the first run does a full listing to sync. Run the stream **at least every 7 days** or it falls back to listing.
- **Classic notifications**
  - Limitations: lots of cloud config, and per-stream resource limits.
- **Directory listing**
  - Advantage: zero setup.
  - Limitation: slow and costly on huge directories.
- **Any mode**: you can switch modes across restarts and keep exactly-once.

### Q: When should I use which?
- **File events** by default.
- **Classic notifications** when file events can't be enabled on the shared external location.
- **Directory listing** for small directories, one-off backfills, or when security policy blocks events.

### Q: Exam trap: the ingestion source is an Azure **premium** storage account and you want notification mode. What happens?
It isn't supported, because premium accounts have no queue storage. Use directory listing (or move to standard storage).

### Q: Exam trap: listing is slow on a huge directory. Should you increase `maxFilesPerTrigger`?
No. That's a rate limit, not a discovery fix. Switch to file events or notifications.

## §4 `read_files()` (SQL table-valued function)

### Q: What is it?
A SQL TVF (DBSQL / DBR 13.3+) that reads files at a path and returns a table. It auto-detects the format, infers a unified schema, and supports `schemaHints`, the rescued data column and `_metadata`. Inside a **streaming table with `STREAM`** it **uses Auto Loader**.

### Q: How is it used?
```sql
-- ad hoc / CTAS (batch)
SELECT *, _metadata.file_path
FROM read_files('abfss://c@acct.dfs.core.windows.net/p', format => 'csv', header => true, schemaHints => 'id INT');

-- incremental (Auto Loader) — STREAM required
CREATE OR REFRESH STREAMING TABLE bronze_events
AS SELECT * FROM STREAM read_files('/Volumes/main/raw/events/',
     format => 'json', schemaEvolutionMode => 'rescue', includeExistingFiles => false);
```

### Q: How do its defaults differ from Auto Loader's?
| | `read_files` | `cloudFiles` |
|---|---|---|
| `inferColumnTypes` | **true** | false |
| `useStrictGlobber` | **true** | false |
| Rescued column | On by default (removed with `schemaEvolutionMode => 'none'`) | On when inferring |
| `schemaLocation` | **Not required** in a streaming table | Required outside pipelines |

### Q: What are the advantages?
- Pure SQL; no Python or checkpoint management.
- Same engine as Auto Loader when streaming.
- Works in DBSQL standalone streaming tables and in pipelines.

### Q: What are the disadvantages and limitations?
- Named-parameter syntax only (`opt => value`), and options containing dots need backticks.
- A batch `read_files` reads **all files** to infer the schema, unless you add `LIMIT`.
- `_metadata` is **not** included in `SELECT *`.
- Needs UC `READ FILES` on the external location, or `READ VOLUME` on the volume.

### Q: When should I use it, and when not?
- **Use it** when SQL teams need incremental ingestion (streaming table + `STREAM read_files`) or for exploration and CTAS.
- **Don't** put it in a materialized view for ongoing ingestion. That gives batch re-read semantics; you want exactly-once in a streaming table.

### Q: Exam trap: `CREATE STREAMING TABLE t AS SELECT * FROM read_files(...)` errors. Why?
`STREAM` is missing. It must be `FROM STREAM read_files(...)`.

### Q: Exam trap: on serverless SQL warehouses, should you set `maxFilesPerTrigger`?
No. Leave both `maxFilesPerTrigger` and `maxBytesPerTrigger` unset so dynamic admission control can work.

## §5 `COPY INTO`

### Q: What is it?
A SQL command that loads files from a location into an **existing Delta table**. It is **retryable and idempotent**: files already loaded are skipped on later runs.

### Q: How is it used?
```sql
CREATE TABLE IF NOT EXISTS main.bronze.bookings;     -- schemaless placeholder OK (DBR 11.3+)
COPY INTO main.bronze.bookings
FROM 'abfss://landing@acct.dfs.core.windows.net/bookings/'
FILEFORMAT = JSON
PATTERN = '2026-*/*.json'                              -- or FILES = ('a.json','b.json')
FORMAT_OPTIONS ('inferSchema'='true', 'mergeSchema'='true')   -- reader: infer/merge across files
COPY_OPTIONS  ('mergeSchema'='true');                  -- evolve TARGET schema
-- transform on load:
-- FROM (SELECT to_date(dt) dt, qty::double FROM 'abfss://...')
```

### Q: What are the advantages?
- Simple SQL and idempotent by default.
- Easy targeted reloads with `FILES`/`PATTERN` and `force`.
- Runs in DBSQL, notebooks and Jobs.
- Can run concurrently on **distinct** file sets.

### Q: What are the disadvantages and limitations?
- Doesn't scale to millions of files (slower discovery per run).
- Weaker schema evolution (no rescue modes).
- Batch only.
- Overlapping concurrent runs cause transaction conflicts.
- A schemaless placeholder table can't take `INSERT`/`MERGE` until `COPY INTO` has loaded data.
- Respects the workspace deletion-vector setting, so readers on DBR ≤ 11.3 can break.

### Q: When should I use it, and when not?
| Scenario | Pick |
|---|---|
| Thousands of files, SQL users, scheduled loads | COPY INTO |
| Reload a specific subset of re-uploaded files | COPY INTO (`force`). It can run **alongside** an Auto Loader stream |
| Millions of files / frequent schema change / very large directories | Auto Loader |
| Most scalable SQL option | Streaming table + `read_files` (Databricks recommends this for SQL users) |

### Q: Exam trap: a file was modified after loading and COPY INTO is re-run. What happens?
It is **still skipped**, because idempotency ignores modifications. Use `COPY_OPTIONS ('force'='true')`, which disables idempotency.

### Q: Exam trap: which `mergeSchema` evolves the target?
The one in **`COPY_OPTIONS`**. `FORMAT_OPTIONS mergeSchema` only merges schemas across the source files.

## §6 Lakeflow Connect (managed connectors)

### Q: What is it?
Databricks' ingestion family. Its **managed connectors** are UC-governed **ingestion pipelines** that run on serverless compute plus Lakeflow pipelines. They handle source auth, incremental reads/CDC, retries, schema evolution and API maintenance for SaaS sources (Salesforce, Workday, ServiceNow, Google Analytics, SharePoint) and databases (SQL Server, MySQL, PostgreSQL, Oracle). Other types: query-based connectors (no CDC on the source), streaming connectors, community connectors, and Zerobus Ingest (direct-write API).

### Q: How is it used?
Through the UI (**Add data** / **Jobs & Pipelines → Ingestion pipeline**), APIs, SDK/CLI or Declarative Automation Bundles. You don't write transformation code.
- **SaaS**: UC **connection** → ingestion pipeline → destination streaming tables.
- **Database**: connection → **ingestion gateway** (continuously reads the change log into **staging storage**, a UC volume) → ingestion pipeline (applies to tables, SCD1/SCD2).
- Users need **`USE CONNECTION`** on the UC connection. Non-admins must use an existing connection.

### Q: What are the advantages?
Least code and maintenance, incremental by default, built-in CDC and SCD2, UC governance, serverless.

### Q: What are the disadvantages and limitations?
- Limited source list, and connectors have varying release states.
- No write-back to the source.
- Not every feature everywhere (e.g., Salesforce: data-type changes aren't auto-evolved; max 250 tables per pipeline).
- Region availability varies.
- Database CDC requires change tracking/CDC enabled on the source.

### Q: When should I use it, and when not?
- **Use it** when a supported SaaS/DB source needs ongoing incremental copies with minimal maintenance.
- **Don't** use it for files in object storage (Auto Loader).
- **Don't** use it for ad hoc queries without copying (Lakehouse Federation).
- **Don't** use it for live sharing with no duplication (Delta Sharing).
- **Don't** use it for unsupported sources (pipelines + Spark APIs, or Structured Streaming).

### Q: How does it compare to Lakehouse Federation and Auto Loader?
- **Managed connectors** copy data incrementally into Delta.
- **Federation** queries the external system in place: good for ad hoc work and POCs, no copy.
- **Auto Loader** is a cloud-object-storage file source, not a fully managed pipeline.
- Databricks guidance: start at the most-managed layer (connector), and drop to pipelines, then Structured Streaming, only if needed.

### Q: Exam trap: which components does a SQL Server connector add that a Salesforce one doesn't?
The **ingestion gateway** and **staging storage**.

## §7 Streaming tables (ST)

### Q: What is it?
A UC managed Delta table with one or more **flows** that **incrementally** process an **append-only** streaming source. Each input record is processed **once**.

### Q: How is it used?
```sql
CREATE OR REFRESH STREAMING TABLE silver_orders
AS SELECT * FROM STREAM bronze_orders;          -- or STREAM(bronze_orders)
```
```python
@dp.table
def silver_orders():
    return spark.readStream.table("bronze_orders")

dp.create_streaming_table("orders_all")          # empty target for flows / AUTO CDC
@dp.append_flow(target="orders_all")
def eu(): return spark.readStream.table("orders_eu")
@dp.append_flow(target="orders_all")
def us(): return spark.readStream.table("orders_us")
```
SQL flows into one ST: `CREATE FLOW f AS INSERT INTO st BY NAME SELECT * FROM STREAM src`. One-time backfill: `INSERT INTO ONCE` / `once=True`, which re-runs only on full refresh.

Standalone (DBSQL, no pipeline): `CREATE STREAMING TABLE ...`, `REFRESH STREAMING TABLE t [FULL]`. This always runs in triggered mode and is backed by a serverless pipeline.

### Q: What are the advantages?
- Low latency, and cost scales with new data rather than history.
- Exactly-once processing.
- Ideal for ingestion (Auto Loader, Kafka) and as AUTO CDC targets.
- Multiple flows can write to one ST.

### Q: What are the disadvantages and limitations?
- A query change only affects **new** rows; reprocessing history needs a full refresh.
- Stream-static joins do **not** recompute when the dimension changes.
- The source must be append-only: updates or deletes in the source **fail** the stream unless you use `skipChangeCommits`, which is Python-only (`spark.readStream.option("skipChangeCommits","true").table(...)`).
- Stateful operations need watermarks.
- No CLONE.
- Non-admins need `REFRESH` on the ST to view its pipeline.

### Q: When should I use it, and when not?
- **Use it** for bronze/silver append ingestion, high volume, low latency, CDC targets.
- **Don't use it** for aggregates or joins that must stay correct as upstream rows change. Use an MV.

### Q: Exam trap: an ST reading a silver table that gets `UPDATE`/`DELETE` commits starts failing. What are the fixes?
`skipChangeCommits` (ignores those commits), or make the downstream object an MV. Reading from an AUTO CDC target? Read its change data feed.

## §8 Materialized views (MV)

### Q: What is it?
A precomputed, persisted query result with **batch semantics**. On each refresh the result equals the defining query over the current sources. It refreshes incrementally when the cost model says that's cheaper, and otherwise recomputes fully.

### Q: How is it used?
```sql
CREATE OR REFRESH MATERIALIZED VIEW gold_daily_revenue
AS SELECT date(order_ts) d, sum(amount) revenue FROM silver_orders GROUP BY 1;
```
```python
@dp.materialized_view
def gold_daily_revenue():
    return spark.read.table("silver_orders").groupBy(...).agg(...)
```
Standalone: `REFRESH MATERIALIZED VIEW m [FULL]`.

### Q: What are the advantages?
- Always correct at refresh time, including late, out-of-order, updated and deleted upstream data.
- Joins recompute when dimensions change.
- Often incremental.

### Q: What are the disadvantages and limitations?
- **Incremental refresh works only on serverless pipelines.** On classic compute it's always a full recompute.
- A full recompute can be expensive on huge history.
- Sources with row filters or column masks aren't incrementally refreshable.
- Some incremental operations need row tracking on the sources.
- Not suited to sources that don't keep history (Kafka) or that you'll purge.

### Q: When should I use it, and when not?
- **Use it** for gold aggregates, joins, and anything that must reflect upstream changes.
- **Don't use it** for ingestion or exactly-once processing (Auto Loader, Kafka), or when a full recompute would be prohibitive. Use an ST there.

### Q: How does it compare to an ST and a view?
| | ST | MV | Temporary view |
|---|---|---|---|
| Semantics | Streaming, append-only, each row once | Batch, always correct | Not persisted; computed when referenced |
| Reflects upstream updates/deletes | No | **Yes** | Yes |
| Read source with | `STREAM` / `readStream` | Batch read | Either |
| Python | `@dp.table` | `@dp.materialized_view` | `@dp.temporary_view` |

### Q: Exam trap: "gold must reflect late corrections and deletes in silver; full recompute OK." ST or MV?
**MV.**

### Q: Exam trap: an MV on a classic-compute pipeline always fully recomputes. Bug?
No. Incremental MV refresh is serverless-only.

## §9 Expectations (data quality)

### Q: What are they?
Named SQL boolean constraints on STs, MVs or temporary views, checked per record, with an action on violation. Metrics go to the event log and the UI **Data quality** tab.

### Q: How are they used?
| Action | SQL | Python single | Python group (dict) | Result |
|---|---|---|---|---|
| **warn (default)** | `CONSTRAINT n EXPECT (cond)` | `@dp.expect("n","cond")` | `@dp.expect_all({...})` | Invalid rows **kept** (written) |
| drop | `... ON VIOLATION DROP ROW` | `@dp.expect_or_drop` | `@dp.expect_all_or_drop` | Dropped before write; count logged |
| fail | `... ON VIOLATION FAIL UPDATE` | `@dp.expect_or_fail` | `@dp.expect_all_or_fail` | Update fails; **atomic rollback**; manual fix |

```sql
CREATE OR REFRESH STREAMING TABLE silver (
  CONSTRAINT valid_id EXPECT (id IS NOT NULL) ON VIOLATION DROP ROW,
  CONSTRAINT valid_amt EXPECT (amount >= 0)
) AS SELECT * FROM STREAM bronze;
```
```python
rules = {"valid_id": "id IS NOT NULL", "valid_amt": "amount >= 0"}
@dp.table
@dp.expect_all_or_drop(rules)
def silver(): return spark.readStream.table("bronze")

@dp.table                                   # quarantine: keep bad rows for review
def silver_quarantine():
    return spark.readStream.table("bronze").filter(f"NOT ({' AND '.join(rules.values())})")
```

### Q: What are the advantages?
Declarative, per-constraint metrics (`passed_records`, `failed_records`, `dropped_records`), reusable rule dictionaries, and atomic fail.

### Q: What are the disadvantages and limitations?
- Constraints can't use Python UDFs, external calls, or subqueries against other tables.
- Names must be unique per dataset.
- Grouping (`expect_all*`) is **Python only**. In SQL you list several `CONSTRAINT` clauses separated by commas.
- **FAIL records no metrics** for that update.
- Not supported on `AUTO CDC FROM SNAPSHOT` flows or on sinks.
- View metrics may be missing or duplicated.
- On classic compute they require the **Advanced** edition.

### Q: When should I use which action?
- **warn**: you want visibility and actively watch the trend.
- **drop**: bad rows are expected and safe to discard (add a quarantine table if you need them).
- **fail**: a broken contract must stop everything, e.g. a null primary key.

### Q: How does FAIL behave in triggered vs continuous mode?
- **Triggered**: the failing flow fails, but parallel flows do **not**.
- **Continuous**: the flow and **all dependent flows** stop.

### Q: Where do I see the metrics?
Event log `event_type='flow_progress'`:
- `details:flow_progress.data_quality.expectations` gives `name`, `dataset`, `passed_records`, `failed_records`.
- `details:flow_progress.data_quality.dropped_records` gives the drop count.

`failed_records` doesn't say whether the action was warn or drop.

### Q: Exam trap: `CONSTRAINT x EXPECT (amount >= 0)` with no `ON VIOLATION`. What happens to violating rows?
They are **written to the target** (warn), and the counts are recorded.

### Q: Exam trap: `@dp.expect_or_drop(rules_dict)`. Valid?
No. A dict needs `@dp.expect_all_or_drop`. `expect_or_drop` takes `(name, condition)`. `@dlt.expect_all_or_drop` is also valid (legacy module).

## §10 AUTO CDC (formerly APPLY CHANGES)

### Q: What is it?
A declarative CDC flow. It **upserts** INSERT/UPDATE events and optionally applies DELETE/TRUNCATE from a change feed into a **pre-declared streaming table**. It handles **out-of-order** events, deduplication and SCD1/SCD2 (and bitemporal). It replaces hand-written `MERGE` in `foreachBatch`.

### Q: How is it used?
```sql
CREATE OR REFRESH STREAMING TABLE dim_customer;
CREATE FLOW dim_customer_cdc AS AUTO CDC INTO dim_customer   -- legacy: APPLY CHANGES INTO dim_customer
FROM STREAM(cdc_customers)
KEYS (customer_id)                              -- required; composite allowed
[IGNORE NULL UPDATES]                           -- nulls keep existing values
APPLY AS DELETE WHEN operation = 'DELETE'
[APPLY AS TRUNCATE WHEN operation = 'TRUNCATE'] -- SCD1 ONLY
SEQUENCE BY op_ts                               -- required; ties: STRUCT(op_ts, lsn)
COLUMNS * EXCEPT (operation, ingest_ts)         -- or COLUMNS (a, b)
STORED AS SCD TYPE 2                            -- default SCD TYPE 1
TRACK HISTORY ON * EXCEPT (last_login);         -- SCD2 only: which cols version
```
```python
dp.create_streaming_table("dim_customer")
dp.create_auto_cdc_flow(                     # legacy dlt.apply_changes(), same signature
  target="dim_customer", source="cdc_customers",
  keys=["customer_id"], sequence_by=col("op_ts"),
  apply_as_deletes=expr("operation = 'DELETE'"),
  except_column_list=["operation", "ingest_ts"],
  stored_as_scd_type="2",                    # 1 | 2 | "bitemporal"
  track_history_except_column_list=["last_login"])
```
Other parameters: `column_list`, `track_history_column_list`, `apply_as_truncates`, `ignore_null_updates[_column_list|_except_column_list]`, `columns_to_update`, `name` (lets multiple flows share one target), `once` (one-time backfill; batch DF).

### Q: What are the advantages over MERGE?
- Correct ordering and deduplication by `SEQUENCE BY`, even when events arrive late.
- SCD2 history (`__START_AT`/`__END_AT`) maintained automatically.
- Delete tombstones handle out-of-order deletes.
- Less code than imperative `MERGE` logic.

### Q: What are the disadvantages and limitations?
- Needs the **Pro or Advanced** edition (or serverless).
- Not in Apache SDP.
- The sequence column must be **sortable and never NULL**, with one distinct update per key per value.
- `APPLY AS TRUNCATE WHEN` is **SCD1 only**.
- To stream **from** an AUTO CDC target, read its **change data feed**.
- An AUTO CDC target accepts only AUTO CDC flows (no `INSERT INTO ONCE` append flow).
- Expectations aren't supported on the `FROM SNAPSHOT` variant.
- Bitemporal: no TRACK HISTORY, no TRUNCATE, no FROM SNAPSHOT.

### Q: How are out-of-order events handled?
Per key, by `SEQUENCE BY`:
- **SCD1**: an event older than the applied state is ignored. In the MS Learn example, an UPDATE at seq 5 arriving after seq 6 is dropped.
- **SCD2**: the late event is placed at the right spot in the history.
- **Deletes**: kept as **tombstones** for `pipelines.cdc.tombstoneGCThresholdInSeconds` (default 2 days). Raise it above the maximum expected lateness.

### Q: When should I use it, and when not?
- **Use it** for Debezium/GoldenGate feeds, Delta CDF, or RDBMS CDC.
- **Use `AUTO CDC ... FROM SNAPSHOT`** (`create_auto_cdc_from_snapshot_flow`) when you only have periodic full snapshots. It has no `SEQUENCE BY`.
- **Don't use it** for pure append data. Use a plain ST.

### Q: What is current adoption, and what replaced what?
`AUTO CDC` / `create_auto_cdc_flow` replaced `APPLY CHANGES` / `apply_changes` with the same syntax. In 2025 the SQL form moved into `CREATE FLOW ... AS AUTO CDC INTO`, adding `name` and `once`. Old names still work.

### Q: Exam trap: events land out of order. `SEQUENCE BY ingest_ts` or `op_ts`?
**`op_ts`**, the source commit/event time. Ingest time only reflects arrival order. Break ties with `STRUCT(op_ts, lsn)`.

### Q: Exam trap: you need SCD2, and email changes must NOT create new versions. `COLUMNS * EXCEPT (email)`?
No, that removes `email` from the target. Use `TRACK HISTORY ON * EXCEPT (email)` (Python: `track_history_except_column_list=["email"]`).

## §11 SCD Type 1 vs SCD Type 2 (in AUTO CDC)

### Q: What are they?
- **SCD1**: overwrite in place; current state only; no history columns.
- **SCD2**: a new row per tracked change, with `__START_AT` and `__END_AT` set from the sequence values. The current row has `__END_AT IS NULL`.

### Q: How are they used?
`STORED AS SCD TYPE 1|2` / `stored_as_scd_type=1|"2"`. The default is **SCD1**. If you declare an SCD2 target schema explicitly, it **must include `__START_AT` and `__END_AT` with the same type as `sequence_by`** (a struct if you sequence by a STRUCT).

### Q: What does SCD2 output look like? (MS Learn example)
| userId | city | __START_AT | __END_AT |
|---|---|---|---|
| 123 | Monterrey | 1 | 5 |
| 123 | Chihuahua | 5 | 6 ← deleted at 6 |
| 125 | Tijuana | 2 | 5 |
| 125 | Mexicali | 5 | 6 ← arrived late, still placed |
| 125 | Guadalajara | 6 | null ← current |

SCD1 on the same input: 123 is gone, and 125 is Guadalajara.

### Q: What are the advantages and disadvantages?
- **SCD1**: small, simple, supports TRUNCATE. No history.
- **SCD2**: full history and point-in-time joins. More storage, no TRUNCATE, and consumers must filter `__END_AT IS NULL`.

### Q: How do `TRACK HISTORY ON` and `COLUMNS` compare?
- `COLUMNS` chooses which columns **exist in the target**.
- `TRACK HISTORY ON` chooses which columns **create a new version** when they change. Changes to untracked columns update the current row in place.

### Q: Exam trap: a feed contains TRUNCATE operations and the target is SCD2. What happens?
It's invalid: `APPLY AS TRUNCATE WHEN` is SCD1-only. Use an SCD1 target or handle truncates differently.

### Q: Exam trap: you want to rename `__START_AT` to `valid_from`. How?
Create a view over the target. Don't alter the CDC columns.

## §12 Pipeline modes: triggered vs continuous

### Q: What are they?
- **Triggered** (default): refreshes every table from the data available when the update started, then stops.
- **Continuous**: runs until stopped, processing data as it arrives. It only updates when dependent Delta tables change.

### Q: How are they used?
- Set **Pipeline mode** in the pipeline settings.
- Databricks now recommends a **continuous Lakeflow Job** wrapping a **triggered**-mode pipeline. The job's schedule **overrides** the pipeline mode in both directions.
- Use a maintenance window on the job to control platform restarts.
- Standalone STs/MVs always run triggered.

### Q: What are the advantages and disadvantages?
| | Triggered | Continuous |
|---|---|---|
| Freshness | Every 10 min, hourly, daily | ~10 s to a few minutes |
| Cost | Compute only while running | Always-on cluster, much more expensive |
| Expectation FAIL | Parallel flows unaffected | Stops the flow and its dependents |
| Built-in setting | — | Discouraged for new pipelines (use a continuous job) |

For sub-second latency, use **real-time mode**, which builds on continuous.

### Q: When should I use which?
- **Triggered** for the vast majority of pipelines.
- **Continuous** only with a proven seconds-to-minutes latency requirement.
- Table type is independent of mode: STs and MVs work in both.

### Q: Exam trap: a pipeline set to Continuous runs inside a triggered (scheduled) job. Which wins?
The **job**. It runs one update and stops.

## §13 Development vs Production mode → update run behavior; editions

### Q: What is it?
How a pipeline update handles clusters and retries. The legacy UI toggle was **Development/Production**. Current docs determine the behavior by **how the update is started**.

| | "Development" (fast-start, debugging) | "Production" (auto retry/restart) |
|---|---|---|
| Started by | **Run now** in UI/editor for non-continuous pipelines | **Jobs, Pipelines API, and all continuous updates** (including continuous started from the editor) |
| Cluster | **Reused**, default 2 h (`pipelines.clusterShutdown.delay`) | Shuts down **immediately** after the run; restarted on recoverable errors (memory leak, stale credentials) |
| Retries | **Disabled** | **Enabled** (e.g., cluster start failure) |

Override one triggered run with **Run now with different settings**. Run behavior never changes the storage location or target schema.

### Q: What are the product editions (classic compute)?
| Edition | Supports |
|---|---|
| Core | Streaming ingest |
| Pro | + CDC (AUTO CDC / APPLY CHANGES) |
| Advanced | + **Expectations** |

**Serverless** pipelines include everything.

### Q: Exam trap: in a UI test run, a transient failure isn't retried and the cluster is still up 90 min later. Misconfiguration?
No. That's development / fast-start behavior by design. Schedule the pipeline via a Job for production behavior.

### Q: Exam trap: a Pro-edition pipeline uses `ON VIOLATION DROP ROW`. What happens?
It fails. Expectations need **Advanced** (or serverless).

## §14 Full refresh & reset

### Q: What are the refresh types?
| Update type | MV | ST |
|---|---|---|
| Refresh (default) | Correct result; incremental if cheaper | **Only new records** |
| **Full refresh** | Recompute | **Truncate** the table, **clear checkpoints**, reprocess **all** source data |
| Reset streaming flow checkpoints (REST API) | n/a | Clear checkpoints and **keep the data**, then reprocess the source |

### Q: How is it used?
Through the UI (Full refresh all / **Select tables for refresh** / **Refresh failed tables**), the API, or `REFRESH ... FULL` for standalone objects.

### Q: What are the risks and limitations?
- A full refresh of an ST can **lose data** if the source no longer retains it (Kafka past retention, purged landing files).
- Downstream: the pipeline fails until dependent tables are also fully refreshed, unless they read with `skipChangeCommits`. Dependent MVs must be fully refreshed.

### Q: When should I use it, and when not?
- **Use it** when a definition or schema change is incompatible with existing data, or when you need to reprocess history after a logic change.
- **Don't** use it routinely; cost scales with the source size.

### Q: Exam trap: how do you prevent anyone from fully refreshing a bronze ST fed by Kafka with 7-day retention?
Set the table property **`pipelines.reset.allowed = false`**.

### Q: Exam trap: you want to reprocess a flow after a logic change but not truncate the existing ST data. Which refresh?
**Reset streaming flow checkpoints**, via the REST API.

## §15 Event log

### Q: What is it?
A per-pipeline **Delta table** of events: update progress, flow progress and metrics, data quality, lineage, audit/user actions and errors. Delivery is best-effort. The account-wide equivalent is the system table `system.lakeflow_pipeline_events_preview.pipeline_events` (Beta; becomes `system.lakeflow.pipeline_events` at GA).

### Q: How is it used?
```sql
SELECT timestamp, details:flow_progress.data_quality.expectations
FROM event_log('<pipeline-id>')            -- or event_log(TABLE(main.silver.orders))
WHERE event_type = 'flow_progress'
ORDER BY timestamp DESC;
```
You can also publish the event log to a UC table in the pipeline settings, and query it in Python with `spark.read.table(...)`.

### Q: Which event types matter?
| event_type | Use |
|---|---|
| `flow_progress` | Rows, backlog (Auto Loader: bytes/files), **data_quality** (expectations, dropped_records), status |
| `flow_definition` | **Lineage**: `input_datasets`, `output_dataset`, schema |
| `update_progress` | Update state (QUEUED … RUNNING … COMPLETED/FAILED/CANCELED) |
| `user_action`, `cluster_resources` | Audit, autoscaling |

### Q: What are the advantages and limitations?
- Advantages: SQL-queryable, easy to build dashboards on, and the UI reads from it too.
- Limitations: best-effort delivery. **Never delete** the event log or its schema, or future updates can fail.
- For alerting, use **event hooks** (Python functions on events) or notifications. Don't put monitoring logic inside dataset definitions.

### Q: Exam trap: you need to know which source tables feed `gold_sales`. Which event type?
`flow_definition`, not `flow_progress`.

## §16 Python API & coding rules

### Q: Which functions should I know?
| Need | API |
|---|---|
| Streaming table | `@dp.table` + `spark.readStream...` |
| Materialized view | `@dp.materialized_view` + `spark.read...` |
| Temporary view | `@dp.temporary_view` |
| Empty ST target | `dp.create_streaming_table("t")` |
| Append multiple sources | `@dp.append_flow(target="t")` |
| CDC | `dp.create_auto_cdc_flow` / `dp.create_auto_cdc_from_snapshot_flow` |
| Expectations | `@dp.expect[_or_drop|_or_fail]`, `@dp.expect_all[_or_drop|_or_fail](dict)` |
| Unpublished table | `@dp.table(private=True)` |
| Parameters | `spark.conf.get("key")` (pipeline configuration) |
| Table options | `name, comment, table_properties, partition_cols, cluster_by, cluster_by_auto, schema, path, row_filter` |

### Q: What's forbidden inside a dataset function?
`collect()`, `count()`, `toPandas()`, `save()`, `saveAsTable()`, `start()`, `toTable()`, and any side effects or custom monitoring. The function is evaluated **multiple times** during planning, so it must only **return a DataFrame**. Don't wrap transformations in broad `try/except` either: the pipeline needs errors to surface.

### Q: Exam trap: a function decorated with `@dp.table` returns `spark.read.table("silver")`. What do you get?
A **materialized view**, the legacy `@table` behavior. The intent is clearer with `@dp.materialized_view`. If you wanted an ST, use `spark.readStream`.

## §17 Rapid-fire decision table

| Scenario says… | Answer |
|---|---|
| Don't stop, don't change schema, keep new data | `rescue` → `_rescued_data` |
| Auto-add new columns | `addNewColumns` + job retries |
| Halt on schema drift | `failOnNewColumns` |
| All JSON columns are STRING | `cloudFiles.inferColumnTypes=true` / `schemaHints` |
| Only files arriving from now on | `includeExistingFiles=false` (first start only) |
| Millions of files, listing slow | File events (`useManagedFileEvents`) |
| SQL team, thousands of files, idempotent | `COPY INTO` |
| Reload an already-loaded file | `COPY INTO ... COPY_OPTIONS('force'='true')` |
| SQL incremental ingestion | `CREATE STREAMING TABLE ... FROM STREAM read_files(...)` |
| Salesforce/SQL Server, managed, incremental | Lakeflow Connect |
| Query external DB in place | Lakehouse Federation |
| Keep bad rows, measure | `EXPECT` (warn) |
| Discard bad rows | `DROP ROW` / `expect_or_drop` / `expect_all_or_drop` |
| Stop on bad data | `FAIL UPDATE` / `expect_or_fail` |
| Keep bad rows aside | Quarantine table (inverse predicate) |
| Latest state from CDC | AUTO CDC SCD1 |
| History from CDC | AUTO CDC SCD2 |
| Version only on some columns | `TRACK HISTORY ON` |
| Out-of-order CDC | `SEQUENCE BY` source commit time (STRUCT for ties) |
| Snapshots only | `AUTO CDC FROM SNAPSHOT` |
| Gold must reflect late changes | Materialized view |
| Protect ST from full refresh | `pipelines.reset.allowed=false` |
| Reprocess source, keep ST data | Reset flow checkpoints (API) |
| Cheapest, hourly | Triggered pipeline on a schedule |
| Seconds latency | Continuous (via a continuous job) |
| Expectations on classic compute | Advanced edition |
| CDC on classic compute | Pro or Advanced edition |
